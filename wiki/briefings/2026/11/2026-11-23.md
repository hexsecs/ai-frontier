# Agentic AI Frontier — November 23, 2026

**Frontier signal:** Agent execution reliability depends on distinguishing retained evidence, reconstructed request state, authorization and independently observed effects. These findings represent different mechanisms and cannot be pooled as a measured performance gain. Four address engineering/research workflows and one explores content automation. Source dates distinguish new repository activity from older releases and research; no experiment was independently reproduced.

## 1. Microsoft Agent Framework Python 1.23

**Source date:** 2026-10-22. **Primary source:** https://github.com/microsoft/agent-framework/releases. **Canonical record:** [[projects/microsoft-agent-framework-python-123]].

**Demonstrated capability:** Atomic memory/Todo writes, background completion waits bound to execution identity, nested-stream closure and owned MCP connection recovery.

**General concept:** Agent state and lifecycle. **Specific mechanism:** Persisting records and matching completion signals to execution identity.

**Novelty:** Incremental SDK release fixing multiple consistency edges.

**Evidence limits:** Maintainer release notes, no independently measured effect correctness.

**Practical implication:** Useful for crash-safe coding orchestration; verify external mutations separately.

**Bounded reproducible experiment (proposed, not executed):** Interrupt 20 disposable workflows during writes and nested stream closure; compare orphan events, recovered records and accepted outputs.

## 2. Measure Before You Manage

**Source date:** 2026-08-31 (older research). **Primary source:** https://arxiv.org/abs/2608.31057. **Canonical record:** [[projects/coding-agent-working-memory-evaluation]].

**Demonstrated capability:** Author analysis of 55 archived coding-agent trajectories and object-aware compression/retrieval strategies.

**General concept:** Semantic working-memory heterogeneity. **Specific mechanism:** Classify instructions, artifacts, outputs and generated state before selecting compression and retrieval policy.

**Novelty:** Four-level distinction: stored state, delivered context, management work and task outcome.

**Evidence limits:** Author-reported; held-out gains may fail to transfer; nominal equal budgets conceal delivered-context differences.

**Practical implication:** Evaluate actual task acceptance, not token counts alone.

**Bounded reproducible experiment (proposed, not executed):** Replay 20 held-out traces under matched token budgets and compare delivered evidence, management work and hidden-test acceptance.

## 3. SandBase Agent Harness

**Source date:** 2026-11-23 (observed organization activity; release date unverified). **Primary source:** https://github.com/sandbaseai. **Canonical record:** [[projects/sandbase-agent-harness]].

**Demonstrated capability:** Vendor describes sessions, tool calls, approvals, sandboxes, replay and auditability.

**General concept:** Delegated authority and execution state. **Specific mechanism:** Managed control-plane features surrounding sandboxed tools.

**Novelty:** A combined agent-runtime offering rather than a novel agent reasoning algorithm.

**Evidence limits:** Vendor claims; the specific runtime's tagged implementation and independent behavior remain unresolved.

**Practical implication:** Candidate for tool-authorization and recovery experiments, not production assurance.

**Bounded reproducible experiment (proposed, not executed):** Use a disposable account for 20 approved/denied actions; crash/restart and audit resulting effects.

## 4. NovelMaker 1.7.0

**Source date:** 2026-10-11 (older release; archived 2026-11-22). **Primary source:** https://github.com/wg-1337/NovelMaker/releases. **Canonical record:** [[projects/novelmaker-agent-tool-message-repair]].

**Demonstrated capability:** Release notes document repairing incomplete tool-call sequences, retaining original stored history and path validation.

**General concept:** Replay versus sanitization and tool authority. **Specific mechanism:** Rebuild valid outbound tool messages without destructive disk-history edits; constrain project-file paths.

**Novelty:** A concrete distinction between preserving evidence and presenting a valid request transcript.

**Evidence limits:** Maintainer notes, no independent testing; project archived.

**Practical implication:** Relevant to any agent resuming from partially recorded tool calls.

**Bounded reproducible experiment (proposed, not executed):** Create 30 malformed transcripts and 20 traversal attempts; score repaired requests, preserved history and denied paths.

## 5. Genfeed content agent

**Source date:** 2026-11-23 (repository activity; initial release unverified). **Primary source:** https://github.com/genfeedai/genfeed.ai. **Canonical record:** [[projects/genfeed-content-agent]].

**Demonstrated capability:** Self-hosted content generation through MCP, CLI and REST with queued tasks and documented human publishing approval.

**General concept:** Approval and publication authority. **Specific mechanism:** Redis/BullMQ work queues and MCP-facing draft operations; publishing gated by review in the standard preset.

**Novelty:** A concrete personal/business automation integration, not a measured new algorithm.

**Evidence limits:** Maintainer demo includes seeded content; approval enforcement across alternate paths is not independently tested.

**Practical implication:** A useful approval-first automation reference for content operations.

**Bounded reproducible experiment (proposed, not executed):** Create ten drafts in a test workspace; attempt direct and indirect publish before/after approval and inspect mock-channel output.

## Cross-item synthesis

The SDK and NovelMaker changes address different forms of execution continuity: atomic state transitions and message-history sanitation. The memory paper warns that retaining more context is not equivalent to delivering more useful evidence or improving task outcomes. SandBase and Genfeed add control-plane claims about approval and auditability; these claims require adversarial tool-path tests before they can support security conclusions. The common proposed evaluation is a disposable task suite with injected interruptions, stale context, unauthorized tool attempts and independently checked external outcomes. There is no demonstrated combined implementation or cross-project benchmark.
