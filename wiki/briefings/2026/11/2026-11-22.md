# Agentic AI Frontier — November 22, 2026

**Frontier signal:** Recent implementation changes increasingly make continuity, recovery barriers, event ordering and per-agent tool surfaces explicit. They address different failure modes: preserved context may be stale, recovery may race effects, idle events may be premature and tool assignment may not enforce authorization. Four findings concern engineering runtimes and coding agents; one explores desktop automation. All five are primary maintainer releases from November 21, not independent replication or deployment measurements.

## 1. Browser4 4.16.9

**Source date:** 2026-11-21 08:26 UTC. **Primary URL:** https://github.com/platonai/Browser4/releases/tag/v4.16.9. **Canonical record:** [[projects/browser4]]. **Verdict:** Worth a controlled browser-continuity test.

**Demonstrated capability:** The release aligns multi-turn browser-agent context with the pi agent loop: context window and reserve accounting, follow-up continuity, transcript carry and rewind. Maintainers say downstream modules compile, while real-browser end-to-end testing of the new prompt shape remains pending.

**General concept:** Session continuity is not the same as replay-safe browser effects. **Specific mechanism:** Carry selected transcript and context state into the next task, with switches that can revert the carry behavior. See [[concepts/agent-state-and-lifecycle]], [[techniques/durable-agent-execution]] and [[concepts/verified-completion-vs-apparent-success]] for the distinct state and acceptance boundaries; for authorization see [[concepts/delegated-authority-and-revocation]]. These are analyst reading connections, not evidence of shared implementations.

**Novelty and evidence limits:** Material update to an existing browser-agent entity, not a new project. The release explicitly discloses missing browser end-to-end evidence. No independent replication or end-to-end experiment is claimed for this briefing.

**Practical implication:** Test whether resumed web research retains useful observations without acting on stale page state.

**Bounded reproducible experiment (proposed, not executed):** On ten local mock sites, perform a multi-turn extraction, change page content between turns, and compare continuity enabled/disabled. Record correct follow-up extraction, stale citations, context tokens and unauthorized repeated actions.

## 2. deja-vu 0.25.0

**Source date:** 2026-11-21 21:43 UTC. **Primary URL:** https://github.com/vshulcz/deja-vu/releases/tag/v0.25.0. **Canonical record:** [[projects/deja-vu]]. **Verdict:** High-value multi-agent repository experiment.

**Demonstrated capability:** The release adds three coding-agent readers, a composite GitHub Action, fast cold recall, compact synced manifests, parallel edit radar, subagent parent briefs and verification-command pass-rate ranking.

**General concept:** Externalized memory and workspace lineage can improve coordination only if historical evidence remains applicable. **Specific mechanism:** Manifest/lineage scans support retrieval, compact parent briefs transmit selected context and edit radar flags concurrent mutations. See [[concepts/agent-state-and-lifecycle]], [[techniques/durable-agent-execution]] and [[concepts/verified-completion-vs-apparent-success]] for the distinct state and acceptance boundaries; for authorization see [[concepts/delegated-authority-and-revocation]]. These are analyst reading connections, not evidence of shared implementations.

**Novelty and evidence limits:** Incremental integration of memory and concurrent-edit visibility; sub-second recall and 2.3 MB manifests are maintainer-reported, not independent task-success results. No independent replication or end-to-end experiment is claimed for this briefing.

**Practical implication:** Potentially useful for multi-agent PR work where two agents may edit overlapping files.

**Bounded reproducible experiment (proposed, not executed):** Run 20 fixed repository issues with and without lineage recall; inject five concurrent edit conflicts. Measure detected conflicts, false alarms, stale memories, accepted patches and tokens.

## 3. Holon 0.60.0

**Source date:** 2026-11-21 03:15 UTC. **Primary URL:** https://github.com/holon-run/holon/releases/tag/v0.60.0. **Canonical record:** [[projects/holon]]. **Verdict:** High-value runtime fault-injection experiment.

**Demonstrated capability:** A runtime reliability release moves read-only operations away from a serialized writer, bounds event pagination and per-round payload/tool admission, and gates dispatch until startup recovery completes.

**General concept:** Durability requires state-transition ordering and bounded queues, not just persisted transcripts. **Specific mechanism:** Recovery-before-dispatch ordering, rollback-safe startup isolation and separate read paths reduce avoidable contention and recovery races. See [[concepts/agent-state-and-lifecycle]], [[techniques/durable-agent-execution]] and [[concepts/verified-completion-vs-apparent-success]] for the distinct state and acceptance boundaries; for authorization see [[concepts/delegated-authority-and-revocation]]. These are analyst reading connections, not evidence of shared implementations.

**Novelty and evidence limits:** Concrete implementation reliability changes, with no independently measured latency or exactly-once guarantees. No independent replication or end-to-end experiment is claimed for this briefing.

**Practical implication:** Use recovery barriers and separate read/write contention measurements in long-running agents.

**Bounded reproducible experiment (proposed, not executed):** Inject crashes at five startup phases over 50 mock tasks; compare pinned versions for duplicate starts, unknown effects, writer wait and independent acceptance.

## Cross-item interpretation

Browser4 and deja-vu preserve different forms of information (conversation context versus coding-history lineage). Holon and Copilot SDK expose different execution guarantees (startup recovery barriers versus event order). Ovis adds a desktop tool-access surface, not a measured enforcement boundary. These are architectural comparisons between independent release notes, not tested integrations.

A useful combined evaluation would fix the same disposable tasks and measure four separate outputs: (1) continuity of relevant context, (2) external effect reconciliation, (3) event/status fidelity and (4) independent task acceptance. Include false success, duplicated effects, stale memories and unauthorized actions. No universal reliability improvement follows from the release descriptions.
