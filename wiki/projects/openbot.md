# OpenBot

## What it is

OpenBot is CopilotKit's open-source (MIT) application workspace for AI coworkers: agents that work through a web app, Slack, Teams, or text message, each with its own browser, logins, files and granted tools. A Bot is any endpoint speaking AG-UI, CopilotKit's open agent-to-user protocol, so agents built on LangGraph, Mastra, CrewAI, Pydantic AI, Google ADK or by hand all arrive the same way, and the governance described below rides the protocol rather than the framework.

The project is maintained by CopilotKit (the AG-UI authors). The application source is MIT-licensed and may be forked, white-labelled or customised; **CopilotKit Intelligence** — durable conversations, memory, Automatic Learning and enterprise governance services — is separately licensed and may be self-hosted. The README's licence table states that a laptop for personal use needs a free local Intelligence licence, Kubernetes evaluation needs a trial licence, and production needs a production licence; "OpenBot for Business" bundles Intelligence. Inference is not included: the deployment supplies an OpenAI-, Anthropic-, Google- or OpenAI-compatible endpoint key.

Version and maturity evidence, from the GitHub API and the repository's own `release-policy.json` and `CHANGELOG.md` fetched on 2026-11-10: the repository was created 2026-08-17 and its first release, `v0.0.1`, was published the same day; 34 GitHub releases exist, with `v1.0.0` published 2026-11-09 and `v1.0.1` published 2026-11-10 (a `v1.0.2-rc.1` was published 2026-11-11). `release-policy.json` names the current version `v1.0.2`, the supported upgrade path `v1.0.1` / `v1.0.0` / `v0.3.x`, `requiresDowntime: true` and `recovery: "restore-backup"`, with a database stamp range ending at `0088_approval_reviewer_guidance` and `rollbackCompatible: false`. The repository is TypeScript-dominant with 3,688 tracked files and 1,051 commits; stars and forks are adoption signals, not product evidence.

**This revision is grounded in the current repository, and it corrects the previous page's framing.** The 2026-11-02 revision of this page described a README that opened with "A template, not a product" and a beta badge. Those sentences are present in the README at commit `38acc94` (2026-10-31) and are **absent from the README fetched on 2026-11-10**, which now leads with "AI coworkers. Ready for the enterprise" and offers signed desktop installers, an OpenBot for Business early-access programme, and a Helm chart. The architecture, the gateway and the policy engine are unchanged in substance; the packaging and the commercial framing around them moved on quickly. Nothing in the repository measures whether any of this governance works.

## Mechanism

The load-bearing mechanism is a single policy gateway on the server. Anything a Bot does to a computer, a file, an MCP server or a component returns to the server first. The file `server/src/computer/gateway.ts` (2,055 lines) states this as its header contract — "The only way an action reaches a Bot's computer" — and implements it as three ordered jobs: resolve the element reference the caller sent into the element it actually points at **from the snapshot this server fetched**, evaluate the current action policy, then write the audit row and only then act. The file's own comment is explicit about why the first step matters: "A gateway that decides on a label supplied by the model is theatre: 'never click Submit' is evaded by sending `{ref: "e13", name: "Continue"}`."

**The audit row precedes the action.** In `gateway.ts` the attempt row is written before `run(address)` is called, with a fresh `attempt` id; a forwarded action that then fails writes a second row carrying the same id, so the trail distinguishes "was sent" from "happened". A refusal writes its own row instead, typed by the decision. `server/src/audit.ts` enumerates 195 event types, among them `computer.action_allowed`, `computer.action_refused`, `computer.action_failed`, `computer.action_stopped`, `computer.help_requested`, `computer.control_taken`, `computer.control_released`, `computer.secret_requested`, `agent.handoff_offered`, `agent.handoff_refused`, `agent.escalated`. The payload records the tool, bot, computer, actor, page, element ref, key, file path and the full command text — but never a file body and never a command's output, both of which the code comments justify as potentially sensitive.

**Policy is CEL, deny-before-allow, fail-closed.** `server/src/computer/policy.ts` evaluates expressions through the `cel-js` library, with case-insensitive `contains()` and `matches()` helpers. The decision order is: every deny expression is evaluated first and any true expression refuses the action, whatever `allow` says; then allow expressions are evaluated; if none permits, the action is refused with "No rule in this deployment's policy permits that action". A broken expression is treated as a match on the deny side and as no-match on the allow side, so one typo refuses rather than admits — `matches()` in `policy.ts` logs a `computer-policy-expression-error` and returns `onError`, `true` for deny and `false` for allow. The attributes a rule can be written against are `tool.name`, `intent`, `bot.id`, `actor.id`, `page.url`, `page.host`, `element.ref/role/name/type`, `key`, `command`, `file.path/name/extension`, `mcp.server/tool/effect` and `initiator.kind/id`. The `intent` field is an effect-level classification (`activate`, `type`, `navigate`, `read`, `read_file`, `download_file`, `write_file`, `list_files`, `read_tool`, `write_tool`, `run_command`) rather than the tool name, because a button can be pressed by a click, Enter or Space — the file comments say so, and `computer_type` carries a `submit` flag so a form submission is visible to a rule that names only clicks. `mcp.effect` is decided from the server's own advertised catalogue crossed with a reviewed write-list and fails closed: anything not positively known to be a read is a write.

**The initiator field is the distinctive part.** `docs/architecture.md` defines `initiator_kind` and `initiator_id` on every audit row: `person` (somebody was in the room, the default), `deployment` (the deployment itself at start-up or refusing an unidentifiable caller), `routine` (a schedule fired it, with nobody there), `responsibility` (a Bot's standing responsibility was triggered), `memory` (memory read a connected app to import facts), `handoff` (another Bot asked, on the person's behalf). The value travels inside the signed run assertion, so "a Bot cannot relabel its own run"; a kind this deployment does not write is read as a person rather than kept. The audit screen's **Nobody watching** filter is exactly `routine`, `handoff`, `responsibility` and `memory`.

**What the shipped default actually is.** `server/src/computer/policy-store.ts` defines `DEFAULT_ACTION_POLICY` as `{ mode: "enforce", deny: [], allow: ["true"] }`, and `docs/architecture.md` states it in the same words: "OpenBot's shipped startup default is explicit: `deny: []` and `allow: ["true"]`". The policy engine is fail-closed — an absent policy permits nothing — but the *default* is an explicit allow-all, with the code comment explaining the choice: "a Bot that can look at a page and touch nothing is not a product". The policy is persisted in PostgreSQL and announced on a Postgres `NOTIFY` topic `action_policy_changed` so that every replica re-reads it; `policy-store.ts` explains that keeping a rule in one process's memory would apply it to roughly one action in N while the admin screen reported success.

**Computers are per person, and they do not hold the deployment token.** `docs/architecture.md` states that a computer made for one person or one Isolated Bot never holds the deployment's `COMPUTER_TOKEN` but its own, derived as `HMAC-SHA256(COMPUTER_TOKEN, "openbot computer token v1\n<kind>:<id>")`. The supervisor exposes only ensure, stop, reset and list operations and holds the Docker socket; the README says to keep it off the network. `agent-computer/src/browser-runtime.ts` decides the launch shape from the environment: a managed Chromium container, or `local-chrome` against the person's own browser, headed by default on Linux and in containers, with `COMPUTER_RUNTIME=runsc` for gVisor. `agent-computer/src/real-browser.ts` is careful that the person's everyday Chrome is launched through the OS (`open -b`, `cmd /c start`, the browser's own launcher script) and is never this process's child, so stopping the computer does not kill the person's tabs.

**Egress is filtered at the computer.** Each computer runs a filter proxy applying the Bot's network policy (`allow_all`, `defaults_plus_allowlist`, `allowlist_only`, `deny_all`); the server pushes the policy before the computer acts and whenever it wakes, and until a policy arrives nothing may leave. Cloud metadata addresses are refused in every mode. `docs/architecture.md` states the limit plainly: a process that ignores the proxy variables and opens a raw socket is not stopped by this, and that layer is assigned to Kubernetes NetworkPolicy.

**Human takeover is a designed path, not a failure.** A Bot that hits a login wall, a 2FA prompt or a bot check files a help request recorded with the page it was made on; a person takes control in the same panel and hands back. While a person is driving, Bot actions are refused rather than queued (`agent-computer/src/action-barrier.ts` implements this as synchronous admission with an asynchronous drain and no queueing or replay), and a run with no browser attached pauses instead.

**Approvals sit beside the boundary.** `docs/approvals.md` describes a second, per-action gate in `server/src/approvals/policy.ts` whose order is: kinds of action (delete, send, share, post, pay, change a credential or account setting — these ask in every edition whatever the switch says), then rules (strictest match wins), then auto-review, then "extra vigilant". The file's header comment says the model is "on the two products this has to match": Dot's custom rules and Grok Bot's auto-review. The answers offered are Allow once, Allow for this conversation, Always allow here, Deny; the code distinguishes an allow saved on a card (which carries its action kind) from a typed rule (which does not, and so never opens a delete, send, share, post, payment or account-setting change).

**Two tools for writing policy against reality.** `server/src/computer/policy-dry-run.ts` replays a candidate policy over the audit history — rebuilding the same `PolicyContext` the gateway built, through the same helpers, so "a rule that behaves one way here and another way live would make this feature worse than absent" — and answers, before the rule is saved, which past actions it would decide differently. It replays both computer actions and app calls, because one policy governs both, and the file notes that replaying computer actions alone answered "this rule changes nothing" about an MCP write rule, and that answer was believed. `server/src/what-if.ts` answers "what would happen if…" in the other direction: the deployment's own model only *names* the action, the administrator confirms it from chips, and the real deciders answer deterministically; a failure is sent back once with what was wrong and refused rather than guessed at when it fails twice.

**Tool narrowing is explicitly not a boundary.** `docs/architecture.md` records the design claim that "a model picks the right tool reliably out of about ten, and unreliably out of thirty" — an assertion with no cited study — and that skills narrow the per-run offer to the skills that match the message plus every granted tool no skill claims. The document is explicit that narrowing is not a boundary: "a narrowing that failed closed would remove capability an administrator granted, silently." A separate `search_tools` mechanism holds a large app's tools behind one ordinary tool past fifty tools, and the code notes that Chat Completions refuses a request with more than 128 tools.

**State is split between the deployment and Intelligence.** The deployment's PostgreSQL (with pgvector) holds product data: policy, audit, credentials, grants, channels and component metadata. Threads and memory live in CopilotKit Intelligence, which holds the content and does the recall; OpenBot keeps what Intelligence has no field for — provenance, review state, which Bot formed a memory, which source imported it — and drops project-scoped results so one person's Bot never sees another person's memory. `docs/web-research.md` documents the public-web research providers in the MCP catalogue (Parallel, Exa, Firecrawl) and their read/write classification.

**A Bot can be someone else's endpoint.** The README's "Bring your own agent" section specifies that a Bot may carry a name, title, role description, visibility, an optional AG-UI endpoint and an optional write-only authorization header. The server validates agent endpoints "with the same target checks used for browser navigation, at registration and again on every redirect the endpoint answers with", and a private address is refused unless it is listed in `AGENT_ENDPOINT_ALLOWED_HOSTS`, where matching is exact — "no wildcards, no suffixes", and an entry written as a URL or containing `*` "stops startup and names that entry". The README is careful about what that list does and does not do: "listing an address permits registering an agent there rather than granting that agent anything".

**Bot-to-Bot handoff is typed and bounded.** `docs/architecture.md` describes `message_bot` as a tool offered beside a Bot's granted tools, so reachability is an ordinary grant (`plugin_grants` with a `bot` kind). The asking model must "name the task, anything that bounds it and what a good answer looks like, rather than writing a paragraph", because "Free text is the commonest way a handoff goes quietly wrong". Four things are decided by the deployment and never by the model: who is addressed, where the answer lands (from the signed run assertion), who is asking (stamped from the deployment's own row, so "a Bot able to write its own attribution could claim to be another one"), and how deep the chain may go. `BOT_HANDOFF_MAX_DEPTH` and `BOT_HANDOFF_MAX_PER_RUN` are ceilings and "both refuse rather than truncate". The answer returns as a message whose id names the Bot that said it (`bot-answer:<bot>:<run>`), drawn under the answering Bot's face and name, with no model running for the second hop. Beside it sits `ask_person`, and the document's argument for why it must not be disabled is worth quoting: "A deployment able to switch off the safe exit and keep the expensive one would be backwards."

## Evidence

What the repository demonstrably contains, and what it merely claims.

**Code-inspected.** The gateway, policy engine, policy store, dry-run replay, what-if checker, audit store and approval policy were read as source. The mechanism described above is established by that source, not by prose. The repository's own test suite is large and structured: 1,315 files named `*.test.ts`, `*.test.tsx` or `*.test.py` across the server, app, agents and computer, including `server/tests/policy-dry-run.test.ts`, `server/tests/what-if.integration.test.ts`, `server/tests/approval-rule-backtest.test.ts` and `agent-computer/tests/egress-policy.test.ts`.

**CI, from `.github/workflows/ci.yml`.** The workflow defines a `static` job, a `deployables` job, a `mobile` job, a `computer-browser` job, a `chart` job, a five-shard `test` job, a `test-total` aggregate, a `startup` job on macOS and Windows, a `python-harness` job, `build`, `migrations`, `image` and `component-dockerfiles` jobs, and a `verify` job that requires every one of them to have succeeded. The test job runs against a `pgvector/pgvector:pg17` service and enforces a floor: `scripts/test-floor.ts` exports `MINIMUM_TESTS = 400` and fails the aggregate when the shards' counts fall below it, because "a test file that throws while it is being imported never runs its tests and never reports them as failures". The chart job renders six targets (vanilla, self-hosted, eks, eks-sandbox, gke, aks) and then asserts that specific *refusals* fire — a managed agent URL with no token, an embedded browser across replicas, an egress proxy the network policy blocks, a residential proxy with no path, an OpenTag switch with no shared secret, a SCIM switch with no bearer token, and several boot-time server refusals. The `image` job boots the published container, waits for `/api/capabilities`, checks that the supervision tree is not respawning, and then runs a set of containment probes: that a `pwuser` shell cannot read `KEY_ENCRYPTION_KEY` from a sibling process's `/proc/<pid>/environ` or from `/run/s6/container_environment`, that `sudo -n -l` grants exactly `(root) NOPASSWD: /usr/local/sbin/openbot-apt` with `env_reset`, that a dozen `apt`/`dpkg` root-escape routes are refused, and that `pwuser` cannot write `/app`. A `security_zizmor.yml` workflow scans the workflows themselves.

**Examples and configuration.** The README ships a "Try it" path (`httpbin.org` forms, `/admin/audit`, `/admin/boundaries`), a YAML tenant-package format (`brand.yaml`, `agents.yaml`, `channels.yaml`, `model.yaml`, `knowledge.yaml`, optional `skills.yaml`, `theme.css`), a Helm chart, a desktop installer set and a `prompt.txt` setup script that the README says is "checked against this repository". `docs/architecture.md` lists the required package files and states that the server validates the package at startup, that channel agent IDs must match declared agents, and that connector credentials are "stored through the credential vault and referenced by id, not stored inline in YAML".

**Deployment shapes.** The README documents four: a laptop (Docker Compose with PostgreSQL, the app on 3010 and the API on 3001), a single container (`ghcr.io/copilotkit/openbot:latest` with `EMBEDDED_POSTGRES=on`, everything on 3001), a Helm chart on EKS, AKS, GKE or any cluster, and a desktop application bundled with a container runtime. `docs/architecture.md` records that `scripts/start.sh` starts PostgreSQL, the agent containers and the supervisor through Compose and then runs the server, the routines worker (`bun worker/src/index.ts`, the local stand-in for the routines CronJob) and the app on the host; `scripts/stop.sh` takes the same down "including each Bot's computer, which compose does not own". The services table in the README assigns ports: app 3010, server 3001, `agent-computer` 4100, `agent-bot` 4200, `agent-langgraph` 4201, `supervisor` 4500 host / 4300 container, PostgreSQL with pgvector 5432, and Intelligence external.

**README claims, not measurements.** The repository contains **no benchmark, no task-success rate, no latency figure, no evaluation result and no usage statistic for OpenBot itself**. The 100k–200k-style performance language in the README is absent; the only quantitative-sounding claims are operational parameters — a 15-minute floor and a cap of 20 enabled routines, a routine disabled after ten consecutive failures, an audit CSV export capped at 5,000 rows with an `X-Audit-Export-Truncated` header, and "a model picks the right tool reliably out of about ten, and unreliably out of thirty", which is asserted without a cited study. The upstream CopilotKit claim that it is "used in production by a majority of Fortune 500 companies" links to the vendor's own blog. The measurable claims here are structural — the tests, the CI gates, the chart refusal checks, the container containment probes — and they test that the mechanism exists and behaves as specified, not that it improves outcomes.

## Limitations

**Stated by the project.** The architecture document is unusually candid about its own non-controls, and this page repeats them rather than presenting them as discoveries: `knowledge.yaml` accepts Google Drive and OneDrive declarations and is validated, but "nothing reads it yet"; `channels.allowed_groups` is declared and stored but is not part of the membership decision, because `users.groups` is never populated by any sign-in path, so a group-based rule "has nothing to evaluate" — "Treat it as a declaration waiting on group membership from the identity provider, not as a control that is running"; the egress filter governs traffic that honours the proxy variables, and a raw socket bypasses it; the computer exposes lower-level token-protected endpoints beside the gateway, and the README warns operators to keep them private and not to use them to bypass the gateway. `docs/architecture.md` also states that a group conversation gives each Bot its own Intelligence thread because a thread admits exactly one agent.

**Assessed from the repository.**

- **The shipped default permits everything.** `DEFAULT_ACTION_POLICY` is `deny: []` / `allow: ["true"]`. The fail-closed engine protects a deployment only once an operator replaces the default; out of the box the audit trail records permitted actions, not enforced refusals. Establishing the safety property requires writing policy, and there is no measurement of how many deployments do.
- **A Bot at its own endpoint runs outside the gateway.** A remote AG-UI endpoint runs its own loop; the gateway governs the tool calls that route back through the server, and `docs/architecture.md` says as much when describing `message_bot` and `ask_person` dispatching through the signed callback route. What such an endpoint does between tool calls is outside the boundary by construction.
- **The egress filter is a filter, not a network boundary.** The documentation says so itself; a raw socket escapes it and Kubernetes NetworkPolicy is the intended backstop, so the guarantee is only as strong as the cluster configuration.
- **Approval allow-rules do not compose with action kinds.** An "Always allow here" saved from an ordinary click does not let a Bot press Send or Place your order; this is deliberate, but it means an operator reading the Settings page as "allowed" is reading a narrower thing than the label suggests.
- **Single-vendor control and no independent review.** There is no third-party audit, no published security review and no adversarial evaluation of the gateway in the repository. The CI containment probes test the container, not the policy engine against a hostile Bot.
- **The dry-run replay depends on the trail being complete.** A rule written against history can only be replayed over actions that were recorded with the facts the policy judged them on; a deployment that starts with the permissive default accrues a history of permitted actions with no refusals in it.
- **Policy is per deployment, and the store is one row.** `policy-store.ts` states "There is one boundary per deployment, so there is one row"; there is no per-team or per-Bot boundary object beyond what a CEL rule can express with `bot.id` and `initiator.*`.
- **The "Nobody watching" filter is a query, not a control.** It tells an auditor which rows had nobody present; nothing in the repository prevents an unattended run.

## Competing approaches

Only what the repository or its documents name.

Against **hosted assistants**: the earlier README (commit `38acc94`, 2026-10-31) positioned OpenBot as "the AI assistant your company can actually own… Same shape as ChatGPT, Claude or Grok, with one difference that matters: it runs on your infrastructure and you can change anything about it." The 2026-11-10 README no longer names those three products, and instead lists the AG-UI ecosystem it integrates with (Claude Agent SDK, Microsoft Agent Framework and Agent Harness, Google ADK, AWS Strands, Oracle Agent Spec, LangChain, Mastra, Pydantic AI, Agno, CrewAI) and the execution platforms an agent may live on (Amazon Bedrock AgentCore, Claude Managed Agents, Google Agent Platform, LangChain Managed Deep Agents, Microsoft Foundry Agent Service). These are integration claims, not comparisons.

Against **framework lock-in**: a Bot is any AG-UI endpoint, so "the governance rides the protocol rather than the framework" — a vendor claim about OpenBot's own design.

Against **ungoverned tool access**: the README's framing is that the gateway is "the difference between an agent that can use your tools and an agent you can let near them" — a positioning claim, not a measurement.

Inside the approval layer, `server/src/approvals/policy.ts` names the two products it is modelled on: **Dot**'s custom rules, where each action takes one of four behaviours and some sensitive tasks always stay with the person, and **Grok Bot**'s auto-review, which checks risky actions before they run and lets "ask first" win any conflict.

Inside the policy engine, `server/src/computer/policy.ts` says it "Mirrors the policy engine in CopilotKit's enterprise agent gateway rather than being re-derived, so a rule written here means the same thing there" — the same vendor on both sides of the comparison.

## Implications

The following is analysis by the KB maintainers, not a claim of the project.

The transferable design idea is the ordering: make the audit row a **precondition** of the action rather than a by-product of it, so the record can serve as an account. OpenBot's implementation makes the stronger point that the record alone is not enough — the gateway resolves the element from a snapshot the server fetched, because a policy that decides on a caller-supplied label is "theatre". Together these are a concrete answer to the question [[concepts/verified-completion-vs-apparent-success]] raises for physical actions: a trail is only evidence if what is recorded is what was acted on.

Second, the initiator field is the most reusable idea in the repository. Most agent-governance designs cannot distinguish a person asking from a routine firing, because both arrive with the same credentials. OpenBot's signed run assertion makes that distinction expressible and makes it a queryable column — "Nobody watching" — which is the kind of property that changes what an auditor can ask. That is [[concepts/structural-constraint-over-instruction]] applied to an audit schema rather than to a prompt.

Third, the two policy-writing surfaces — dry-run replay over history and the deterministic what-if checker — are a pattern worth copying independently of the product. A rule written blind is a rule whose effect is unknown; replaying a candidate against the recorded facts converts that unknown into a diff, and the repository's own reasoning is explicit that this only works because the replay and the live path share the same context-building helpers.

Fourth, the fail-closed engine with a permissive default is a real tension rather than a solved problem, and the repository is honest about it. Fail-closed semantics are valuable only once policy exists; a default of `allow: ["true"]` means the safe property is available rather than deployed. Any team adopting a pattern like this should decide explicitly whether the shipped default is the right one for them, and measure how often the boundary actually refuses something (see [[techniques/secure-agent-operations]]).

Finally, nothing here establishes effectiveness. Whether the gateway's policies catch real misuse, and at what cost in refused legitimate work, is unmeasured; the CI checks establish that the mechanism exists and behaves as specified, which is a different and much weaker claim, and the post-hoc checks that would be needed to say more are the subject of [[techniques/verification-and-evidence]].

## Reproducible experiment

No experiment was run for this page. The protocol below is for a reader with a disposable deployment; the first two steps are the README's own suggested trials.

1. **Audit-first invariant.** Install from the quick start on a disposable laptop or VM, ask a Bot to open a page and fill a form (the README suggests `httpbin.org/forms/post`), then inspect `/admin/audit` and confirm a decision row exists for each action and that the row was written before the action took effect. A failure mode worth testing explicitly: an action that is refused must also have a row, and a forwarded action that fails must produce a second row with the same `attempt` id rather than overwriting the first.
2. **Deny path.** Add a deny rule at `/admin/boundaries` matching that action and retry; the action should be refused with the refusal naming the rule, and the refusal should appear in the audit export.
3. **Default check.** On a fresh deployment, confirm the effective policy is the shipped `allow: ["true"]` default (readable from the policy store, `DEFAULT_ACTION_POLICY`), then set a malformed `AGENT_COMPUTER_POLICY` and confirm the server refuses to start rather than starting open. Note that the malformed-policy refusal is a *startup* refusal; it is a different check from the permissive default and both must be run.
4. **The bypass the documentation concedes.** Attempt a raw-socket connection from inside the Bot's container to a host that the egress filter would otherwise block, and record whether it succeeds. A success is the documented behaviour, not a bug, and it establishes what a deployment must add (Kubernetes NetworkPolicy) to close the gap.
5. **Policy replay against live behaviour.** Write a deny rule for an action the trail already contains, use the dry-run replay to see which past actions it would decide differently, then apply it and compare the replayed verdicts with the live ones. The repository's own claim is that replay and live must agree because they share the context-building helpers; a disagreement is a bug in one of the two, and this is the check that establishes it.

Pass criteria: a decision row for every action including refusals; a refusal that names its rule; a startup refusal on malformed policy; the raw-socket bypass reproducing as documented; and replayed verdicts matching live verdicts on the sampled actions.
