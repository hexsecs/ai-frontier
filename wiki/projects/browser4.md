# Browser4

## What it is

Browser4 is an open-source "AI-native browser engine for autonomous agents, intelligent extraction, and large-scale web automation" (the repository description, fetched 2026-11-10). It is maintained by platonai (the Pulsar project; the CLI distributes from `downloads`/`browser4.oss-cn-beijing.aliyuncs.com` and a Gitee mirror is published). The licence is **Apache 2.0** (`LICENSE`), and the primary language is Kotlin with a Rust CLI; the README badges point at a Maven Central artifact `ai.platon.pulsar:browser4-core` and the npm package `browser4-cli`.

Version and maturity evidence from the GitHub API and the repository on 2026-11-10: the repository was created 2018-03-12 (a long-lived repository whose project identity is the recent `Browser4` renaming — the Apache licence and the `2018` creation date are inherited), the current `VERSION` file reads `4.16.4-SNAPSHOT`, and five releases are published in the examined window: `v4.16.0` (2026-11-02), `v4.16.1` (2026-11-04), `v4.16.2` (2026-11-06), `v4.16.3` (2026-11-07), `v4.16.4` (2026-11-08). The last commit on `main` is dated 2026-11-09. The repository tree holds 5,171 entries (3,988 files), 10,590 commits and 1,179 stars.

The previous revision of this page was a canonical backfill of the 2026-11-06 briefing's assessment, not an independent review. This revision grounds the page in the repository itself: the mechanism below is read from source and documentation, and the one performance claim the project makes is identified as such.

## Mechanism

**The stack, from the README's architecture diagram and the module table.** `browser4-cli (Rust) ──MCP over HTTP──▶ browser4-rest (Kotlin/Spring) ──▶ PulsarWebDriver (Kotlin/CDP)`. The CLI is a native Rust binary (11,641 lines in `cli/browser4-cli/src/commands.rs`, 211 `CommandDef` registrations); the backend is a Spring Boot server that dispatches MCP tools to browser drivers; the driver wraps the Chrome DevTools Protocol directly. Replaceable browser behaviour (stealth and interaction humanization) sits behind an SPI pair — `browser4-behavior-api` and `browser4-behavior-default` — so "the current implementation is the default (community) edition, and a professional/custom edition replaces the module". The README's module table lists `browser4-core` (sessions, scheduling, DOM, browser control), `browser4-agentic` (agents, MCP integration, skill registration), `browser4-coding` (the programming-agent kernel), `browser4-agent-tools` (scraping, crawling, stateful page interaction), `browser4-rest`, `browser4-plugins`, `browser4-tests`, `cdp-protocol` (CDP JSON definitions), and a `coworker/` builtin AI coworker.

**Two page views, and they are the core design decision.** The README is explicit that `snapshot` is for interactive work and returns accessibility-tree refs such as `e15`, while `htmlsnapshot` is for DOM/X-SQL extraction with CSS selectors; `htmlsnapshot` commands work on a *fresh* snapshot of the active page (capturing the tab without navigating), and `--expires <dur>` serves the stored snapshot instead. The docs' phrasing: `snapshot` is "live accessibility tree → refs like e15"; `htmlsnapshot` is "a fresh snapshot of the active page (every command captures the tab first, then reads)". The skill reference `x-sql-dom-load-select.md` shows the extraction primitive: `DOM_LOAD_AND_SELECT(url, cssQuery [, offset, limit])` returns a `ResultSet` of DOM objects usable as a SQL table source, e.g. `SELECT DOM_FIRST_TEXT(DOM, '.price') AS price FROM DOM_LOAD_AND_SELECT(@url, '.item')`. `browser4-agent-tools/.../crawl/common/XSqlExecutor.kt` is the single place a statement is executed: "Two callers reach this point from opposite directions — a submitted hyperlink … and a crawl round", and "only the statement itself reaches h2: the page is resolved by the `load_and_select()` UDF from inside the engine". The README calls this "Zero-Token Extraction", and the point is that extraction runs against a deterministic DOM/CSS query rather than a model.

**The acting loop.** `browser4-agentic/.../inference/chat/AgentToolCallLoop.kt` implements the multi-turn tool-calling loop over LangChain4j's native function-calling protocol: it sends the initial messages plus the tool specifications, executes each `ToolExecutionRequest` through a `ToolExecutionCoordinator`, appends the assistant and tool-result messages, and repeats "until the model returns a text-only response or `maxIterations` is reached" — the default is 40. The same file carries a `RequestTokenLimiter` and a per-call inference timeout that is applied to each model round-trip rather than to the whole loop, deliberately "so a slow/hung provider call fails fast while long multi-round tool chains keep making progress". `docs-dev/copilot/agent-run-flow.md` (dated 2026-09-09) traces the full `agent run` path: Rust CLI → `POST /mcp/call-tool` with `command_run` → `MCPToolController` → `CommandToolExecutor` → `UserCommandExecutor` → `StatefulAgentRunner` → `RobustBrowserAgent` in `CLI_TOOL_LOOP` mode → `AgentToolCallLoop` → `b4.run` → a browser4-cli subprocess → the same backend browser. The CLI submits asynchronously and receives a task ID it polls with `command_status`/`command_result`; `--wait` blocks with a default 600 s timeout.

**Context economy inside the loop.** Three source files implement the mechanisms that keep a browser loop affordable, and each documents the failure it fixes. `ToolDisclosure.kt` is the **progressive tool disclosure**: exposing the full registry ("coding ×51, b4, shell, fs, custom plugins…") cost "tens of thousands of tokens of JSON schemas per round", so the loop now starts from a curated set of the `tab`, `browser`, `agent` and `system` domains and adds two meta tools — `system.listTools` and `system.exposeTools` — which "cost ~200 tokens and are always exposed"; the model pulls in what it needs and the exposed set persists for the rest of the task. `ToolResultDigest.kt` bounds tool-result excerpts to a head (160 chars) and a tail (280 chars), because a digest that kept "the first line only" replaced forty shell commands with forty session ids — the file records "the observed churn (23 overflows / 567 shell calls / 20M input tokens in one run)". `PageViewDeduper.kt` folds exact-duplicate tool results inside one loop and replaces a heavily-overlapping new page view with a compact unified-style diff, "all rewriting happens at **append time**, before the message is ever sent".

**Retrieval: the progressive experience memory (PEM).** `docs/experience-memory.md` is the reference for this layer, implemented in `browser4-agentic/.../tools/experience/`. Knowledge flows through three tiers of file-backed YAML keyed by `(domain, intent)`: **Traces** (`traces/<domain>/`, immutable, 30-day TTL, raw execution records), **Stats** (`experience/<domain>/`, mutable, aggregated success/failure counts from which confidence is derived) and **Facts** (`facts/<domain>/`, immutable once VERIFIED, holding authoritative selectors, blockers and interaction hints). A fourth layer, `patterns/` with `families/`, `categories/` and `universal/`, is "reserved for cross-site generalizations: the query fallback chain reads these directories when they exist, but **nothing in the current implementation writes to them** (cross-site promotion is planned, not active)". The four MCP tools are `experience_save`, `experience_query`, `experience_list` and `experience_deep_learn`.

Confidence is computed, never stored: `confidence = α × success_ratio + (1 − α) × recency_factor`, with `success_ratio = (successes + 1) / (successes + failures + 2)` (Laplace smoothing), `recency_factor = 0.5 ^ (days_since_last_update / 60)` (60-day half-life), `α = 0.7`, initial 0.50, cap 0.95, floor 0.05. Confidence maps to a retrieval tier: P1 direct replay (≥0.85), P2 verify-before-replay (0.60–0.84), P3 hint mode (0.40–0.59), P4 advisory (<0.40), P5 cold start (no data). A recorded failure whose category has `degradeRetrieval = true` — only `ANTI_BOT` does — drops the tier one level. Knowledge itself moves through HYPOTHESIS → CANDIDATE → VERIFIED (locked, immutable) with a CONTESTED state for disconfirmations, and promotion thresholds are `confidence ≥ 0.85 AND successes ≥ 5` for VERIFIED, `confidence ≥ 0.60 AND successes ≥ 2` for CANDIDATE. `KnowledgeStore.kt` implements the six-level query fallback: (domain, intent) → (domain, url_pattern) → (site_family, intent) → (site_category, intent) → (site_universal, intent) → cold start.

Intent classification is keyword scoring over thirteen intents (`BUY`, `SEARCH`, `BOOK`, `EXTRACT`, `COMPARE`, `PUBLISH`, `DOWNLOAD`, `READ`, `LOGIN`, `CHECKOUT`, `FILL_FORM`, `MONITOR`, `OTHER`) with canonical action sequences, and failure classification is keyword matching over twelve categories (`SELECTOR_DRIFT`, `VISUAL_DRIFT`, `NETWORK`, `AUTH_REQUIRED`, `PERMISSION_DENIED`, `OVERLAY_BLOCKED`, `TIMING`, `ANTI_BOT`, `LAZY_LOADING`, `AB_EXPERIMENT`, `UNEXPECTED_REDIRECT`, `UNKNOWN`).

**A second, separate memory layer.** `docs/mcp-tools.md` documents a `memory` domain with `memory_note`, `memory_read`, `memory_search` and `memory_forget` — working-memory notes "re-injected into the conversation every round and survive context compression", plus a search over past tasks and tool executions whose hits "are HISTORIC — not results of the current run — so live data must be re-read before it is reported". `browser4-agentic/.../memory/AgentMemory.kt` shows the engine-side design: an event log with a TTL, a bounded buffer, a disposable SQLite FTS5 search index ("a missing/corrupt index only degrades search"), a scratchpad, a recall section injected at run start, and `MemoryConsolidator` → `PemKnowledgeProvider` depositing completed tasks into the PEM knowledge layer.

**The programming-agent kernel.** `browser4-coding` is described as "dependency-light" — "only SLF4J + Jackson + coroutines", so it can be reused by non-agent hosts — and the README counts "50+ `coding.*` tools" in four groups: shell and filesystem, artifact creation and validation, self-development, and LSP. `browser4-agentic/.../builtin/CodingToolExecutor.kt` registers 57 distinct tool specs, matching the README's "50+" claim. The shell has a command whitelist, the file-edit primitives are snapshot-based with `revert` and `diff` (Myers/Patience), and `coding.protect` blocks destructive operations on protected files (VERSION, AGENTS.md, CLAUDE.md, the root pom, BOM, CI).

**Scale-out.** `swarm` (aliased `co`) runs parallel browser contexts and returns task IDs; `crawl` walks from a seed file or URL with `--depth`, `--out-link-selector`, `--parallel`, a checkpoint, and `crawl resume`; `batch` chains client-side steps (the README states plainly that the steps are "**not** packed into a single backend request — each one is its own call"); `loop` runs a task repeatedly on an interval. The `htmlsnapshot`/`X-SQL` path is what makes extraction at scale token-free, and WebMiner (a separate repository, `platonai/web-miner`) is the ML-clustering pipeline that turns an HTML directory into spreadsheets and an interactive report without an LLM.

**Observability.** The README documents a web status panel at `http://127.0.0.1:18182/status`, backed by an aggregated `GET /api/system/status`, with sections for health, build, runtime, llm, sessions, pulsar-sessions, swarm, url-pool, browsers, drivers, privacy, plugins, skills, metrics and logs, and a separate `pages.html` grid that captures a screenshot of every open page across sessions asynchronously ("`202 Accepted` with `Retry-After` while capturing, cached `image/png` when ready"). `doctor` covers build info, LLM status, stale daemon cleanup and optional repair; `doctor log` and `doctor metrics` list, grep and tail the backend logs and metrics. The MCP error-code table in `docs/mcp-tools.md` is part of the same contract: `SESSION_UNHEALTHY` (retryable, "the browser may have exited"), `TARGET_NOT_FOUND` ("Re-run `snapshot` for fresh refs"), `DIALOG_PENDING` ("Run dialog-accept or dialog-dismiss to release the page").

**Configuration.** `docs/experience-memory.md` documents the PEM properties (`browser4.experience.enabled`, default true; `knowledge.dir`, default `knowledge`, resolved relative to the backend's working directory, with every construction path reading the same property "so one `-Dknowledge.dir=<path>` relocates the whole knowledge base instead of forking it in two"). The README documents the LLM provider order and the trap it warns about: "the first one in Browser4's provider order wins — … a leftover `DEEPSEEK_API_KEY` silently wins over `OPENAI_*`", with `browser4-cli doctor` printing the winning key and the active model.

**The plugin and skill surface.** The README distinguishes two "skill" surfaces that are easy to conflate: bundled CLI skill documents that ship with the CLI (`skills list`, `skills get`, `skills unpack`) and installed runtime skills exposed by the backend (`skill-install`, `skill-info`, `skill-reload`, `skill-uninstall`). Plugins are server-side JARs; the first-party set is `browser4-swarm`, `browser4-images`, `browser4-markdown`, `browser4-media` and `browser4-seo` (opt-in behind `-Dbrowser4.plugins.enable=browser4-seo`), with `browser4-{captcha,pptx,profile-import,summary-demo}` installed on demand. Plugin tool names are "the snake_case form of `domain.method` (`image.detectImages` → `image_detect_images`)", and `browser4-cli tool list` (or `GET /mcp/tools`) enumerates them.

**The browser session and its state.** Sessions are named or default, held as CLI state under `~/.browser4` (`cli-state.json`, `sessions/<name>.json`, `loops/<name>.json`), while the runtime bundle lives in a platform-conventional application-data directory "so clearing session state does not force a re-download of Browser4 itself". `open` supports a profile path and a profile mode (`DEFAULT`, `SYSTEM_DEFAULT`, `SEQUENTIAL`, `TEMPORARY`), with `SYSTEM_DEFAULT` "deprecated and unsupported on Chrome ≥ 143"; `attach` connects to an existing browser over CDP or the Browser4 extension and prints which browser actually connected, warning on a channel conflict because "requested msedge but Chrome connected" is a real failure mode. Cookies, localStorage and sessionStorage are all directly readable and writable, with `state-save`/`state-load` for reuse. The README also documents a `webdb` — a browser-side web database with `webdb export` and `webdb normalize` that turns visited pages into a data asset feeding the WebMiner pipeline.

**Agent tool authority is a named preset, not a free-for-all.** `agent run` takes `--access <preset>` with the values `full`, `write`, `read-build` and `read`, narrowing the coding tools available to a submitted task and "reset when the task ends". The README describes the refusal path: "a refused step is not a dead end — `coding.requestAccess` files a non-blocking pending request and an operator approves it through `POST /api/agent/<taskId>/access/<requestId>/approve`, while `denyTools`, protected paths and sensitive paths are never approved". A task with no TTY derives `full` with outbound network rather than the server-wide preset, which `browser4.agent.access.unattended` narrows.

## Evidence

**Code-inspected.** The acting loop, the three context-economy mechanisms, the experience store and its tier/confidence logic, the X-SQL execution path, the agent memory facade, the coding kernel's tool set, the MCP tool reference and the CI workflows were read as source or as generated documentation. The behaviours described in "Mechanism" are established by that reading.

**Test suite and CI.** The repository contains 553 test files under `test`/`tests` directories, distributed across `browser4-agentic` (170), `browser4-core` (107), `browser4-rest` (76), `browser4-coding` (60), `browser4-tests` (59), `browser4-plugins` (42), `browser4-agent-tools` (19), `browser4-boot` (10) and `cli` (10). `docs/TESTING.md` defines a four-dimensional taxonomy — level (Unit/Integration/E2E/SDK), cost (Fast/Slow/Heavy), environment (`RequiresServer`, `RequiresBrowser`, `RequiresAI`, `RequiresDocker`) and policy (`ManualOnly`, `SkippableLowerLevel`, `TestInfraCheck`) — with the stated principle that "`mvn test` **must always be fast, always safe**" and that "all high-cost tests **must be explicitly enabled**". The CI split is visible in the workflow files: `pr.yml` runs a fast subset with a **JaCoCo coverage floor of 0.20 instruction coverage per module**; `ci.yml` runs on release tags only (`v[0-9]+.[0-9]+.[0-9]+-ci.[0-9]+` and `-rc.[0-9]+-ci.[0-9]+`) plus manual dispatch; `nightly.yml` runs at 00:00 UTC and carries "All JVM tests (Fast + Slow + HeavyTest + TestInfraCheck + Integration* + E2E/E2ETest) minus ManualOnly / RequiresAI", the Docker image build, and the full browser4-cli e2e suite of "204 scenarios" at `--level=EXTENDED --enable-all --max-failures=0`; `nightly-cli.yml` runs a SMOKE subset of the CLI e2e scenarios on Linux, macOS and Windows. The `browser4-tests/real-world-scenarios/` tree holds markdown task files plus PowerShell runners that "evaluate browser4-cli usability through an LLM agent" using `dsh`, `opencode`, `claude`, `kimi` or `codex` — this is an agent-driven usability evaluation, and its README is careful that host-environment diagnostics ("Workspace not trusted", "Model missing from Claude Code's catalog") "silently degrade a run" and that the harness must not let "client noise … pass for agent output or a Browser4 finding". A MockSite fixture server serves static pages for testing and demos.

**The tool surface, as generated documentation.** `docs/mcp-tools.md` is generated by `ToolDocGenerator` and states "146 tools across 11 domains", with domains `batch`, `browser`, `command`, `crawl`, `experience`, `html_snapshot`, `memory`, `page`, `skill`, `tab` and `webdb`, and a documented error-code table (`TARGET_NOT_FOUND` telling the caller to re-run `snapshot` for fresh refs; `ENDPOINT_WRONG_BROWSER` for a channel mismatch; `DIALOG_PENDING`; and so on).

**The one performance evaluation inside the repository.** `docs-dev/copilot/20261029-agent-run-bulk-collection-evaluation.md` is an author-run retrospective dated 2026-10-29 on a single 20-ASIN Amazon task, with a real trace. It reports that `crawl --seed-file … --parallel 4` fetched and extracted 20 product pages in **202.2 s** (3 pages: 33.5 s; the same 20 pages re-extracted from the page store with `--expires 1h`: 71.6 s), against roughly **555 s** for a hand-written loop of 40 CLI subprocesses that dumped 52.8 MB of annotated HTML and needed 26 Python scripts; the trace totals 878.2 s, 105 steps and 2.03 M tokens. It also reports the opposite case: the hand-written loop won on context (one command's summary versus 105 steps and 2.03 M tokens) and on failure semantics (per-page reasons, checkpoint, `crawl resume`), and it records the precondition — "crawl uses a new profile in the `SEQUENTIAL` pool, not the same context as the live session", so the locale must be pre-warmed or "the same URL renders as a different site and price/stock columns silently distort". `skills/browser4-cli/references/bulk-collection.md` adds a second measured observation: on 2026-10-28 a 20-product task "crawled the same 20 pages **four times** and, after 29 minutes, still had no deliverable — because nothing had been written to disk between rounds", and a measured locale finding that the URL parameter, the header override and a hand-written `i18n-prefs` cookie all left the tab on a Chinese-preferences interstitial, "only driving the page … produced English content".

**The project's headline throughput claim, and its status.** The README's Key Capabilities bullet says: "Coroutine-safe, CDP-native engine designed for 100k–200k complex page visits per machine per day via swarm/crawl scale-out." The repository's own competitive-analysis document (`docs-dev/copilot/browser4-competitive-advantages.md`, dated 2026-07-14) is more careful than the README: "性能数字为 README 的 'designed for' 设计目标，未见公开 benchmark" — the performance figures are the README's *design goal* and no public benchmark was found. The document's comparison table likewise marks the scale row as "宣称" (claimed). There is no benchmark harness, no throughput measurement, and no third-party reproduction anywhere in the repository. The repository's strongest evidence of throughput is the single-task bulk-collection retrospective above.

## Limitations

**Stated by the project.** The competitive-analysis document flags the throughput figure as a design target rather than a measurement, and the README's own capability wording is "designed for". `docs/experience-memory.md` is explicit that the cross-site pattern layer is inert: "nothing in the current implementation writes to them (cross-site promotion is planned, not active)". `ToolDisclosure.kt` and `ToolResultDigest.kt` document the token costs that motivated the context mechanisms, and `docs-dev/copilot/agent-run-flow.md` records the CLI's dependence on a running backend and on the host's agent CLI. The bulk-collection retrospective is unusually frank about failure: the hand-written approach beat the built-in tool on context budget and failure semantics, and the built-in tool lost on locale unless the profile was pre-warmed.

**Assessed from the reporting.**

- **The 100k–200k figure is unbenchmarked and internally downgraded.** The README states it as a capability; the repository's own analysis calls it a design target with no public benchmark. No measurement of pages/hour, pages/machine/day, concurrency, or memory footprint appears anywhere.
- **The only end-to-end timing evidence is one task, one site, one run.** The 202 s vs 555 s comparison is a 20-page Amazon scrape on a developer machine with `--parallel 4`, with no variance, no repetition and no comparison against another browser automation stack on the same task.
- **The agent-side evaluation is a usability probe, not an accuracy benchmark.** The `real-world-scenarios` suite asks an LLM agent to complete scenarios and evaluates discoverability, documentation and reliability from a first-time user's perspective; its own README is at pains to separate host diagnostics from agent findings. It does not produce a task-success rate for Browser4 against a baseline.
- **Heavy tests are nightly, not per-commit.** `ci.yml` runs only on release tags; the per-PR gate excludes E2E, Integration, Slow, Heavy and RequiresAI classes and the 0.20 JaCoCo floor is low. A regression in the end-to-end path can pass the PR gate.
- **The experience store's cross-site generalization is not implemented.** Levels 3–5 of the query fallback chain read directories nothing writes to, so the "reusable browser knowledge" claim is currently site-local.
- **Deterministic extraction is still DOM-dependent.** The bulk-collection skill states that "post-processing localized values … is not extraction and produces a silently wrong dataset", and that a form can submit from a keypress — the same class of bypass OpenBot's policy layer is built to catch. X-SQL extracts what the DOM says; it does not verify that the DOM is what the task wanted.
- **The selector-experience loop has a stated hazard.** Facts become immutable once VERIFIED and locks are the selectors; a site change after promotion is precisely the drift the `SELECTOR_DRIFT` category names, and the mitigation is a failure record, not a re-verification pass.
- **Single-vendor control and no security review.** No third-party audit of the browser engine, the experience store or the coding kernel's sandbox appears in the repository. `coding.shell` runs with a command whitelist, and the `agent access` presets (`full`/`write`/`read-build`/`read`) plus `coding.requestAccess` are the permission model, but no evaluation of bypasses is published.
- **Geographic and infrastructure assumptions.** The distribution endpoints are Chinese (`browser4.oss-cn-beijing.aliyuncs.com`), the mirror is Gitee, the documentation is bilingual with a Chinese original for several design documents, and the model provider order prioritises Chinese providers. The engine itself is protocol-level and portable, but the deployment path is not neutral.
- **Version churn.** The project shipped five releases in the seven days before 2026-11-10, with `VERSION` at a `-SNAPSHOT` suffix on `main`; the CLI explicitly refuses to run against a runtime bundle built from a different project version, which is a correctness guard but also means the checked-out tree and the published bundle must be kept in step.

## Competing approaches

Only alternatives the repository names, in its own competitive-analysis document (`docs-dev/copilot/browser4-competitive-advantages.md`), which compares Browser4 against three systems on nineteen dimensions:

- **Playwright MCP (Microsoft)** — MCP over stdio/HTTP, Playwright driving CDP/WebKit/Firefox; "only a11y snapshot text, handed to the LLM", no built-in deterministic extraction, single instance and single browser, with no experience memory.
- **Browser Use** — a Python library plus API whose core is the LLM, so "every step burns tokens"; partial profile reuse; no built-in extraction.
- **Scrapy** — an HTTP-level crawler, "extremely fast at pure HTTP", with XPath/CSS and item pipelines but "no browser, no AI, no MCP".

The document's own one-line conclusions: "to let an LLM manipulate a browser, the Playwright MCP / Browser Use ecosystems are more mature"; "for large-scale, low-cost, deterministic extraction plus a shared human login state plus operability, Browser4's X-SQL + swarm + attach/state combination is unique"; "for pure-HTTP extreme-speed crawling without JS rendering, Scrapy is still sharp". Its one-line competitive summary is a positioning claim, not a measurement.

The repository also names **WebMiner** (`platonai/web-miner`) as a separate project for the ML-clustering stage, with a free tier using the SMILE library for single-machine clustering under 1,000 pages and a commercial tier using Apache Spark ML for distributed clustering at larger scale — the extraction stage is delegated rather than built in.

Within this knowledge base, the related records are [[domains/computer-and-device-use]], the general domain page; [[projects/weavebench]], a comparative browser-agent evaluation reference; and [[concepts/verified-completion-vs-apparent-success]], which the browser-agent setting raises directly. These are analyst comparisons, not direct dependencies.

## Implications

The following is analysis by the KB maintainers.

The most transferable idea is the **split between a view for acting and a view for extracting**. The accessibility-tree snapshot gives an agent stable element handles; the DOM snapshot plus X-SQL gives a deterministic query language over the same page with no tokens. Treating "perception for a model" and "perception for a program" as two different surfaces of one browser is a design that generalises well beyond this repository, and it is the concrete form of the "deterministic where you can, generative where you must" pattern.

Second, the three context mechanisms are worth copying as a set, because together they attack a cost that browser agents pay and that is rarely itemised: the tool-schema bill (progressive disclosure), the tool-result bill (bounded head+tail excerpts), and the re-view bill (exact-duplicate folding and view diffing). The `ToolResultDigest.kt` comment is the sharpest form of the lesson: a digest that kept only the first line of each shell result turned forty commands into forty session ids, and the cost was measured — "23 overflows / 567 shell calls / 20M input tokens in one run".

Third, the experience store's tier-and-confidence design is a reusable pattern for *self-improving* agents, and its honest mechanics matter more than its polish: confidence is computed rather than stored, replay is gated on a confidence band, and promotion to an immutable VERIFIED state has explicit thresholds. The failure-category taxonomy with a single tier-degrading category (`ANTI_BOT`) is a nice piece of restraint — most categories degrade the environment, not the retrieval policy. Note the parallel to [[projects/tigerless-agent-memory]], which reaches for a similar problem with a different substrate (Markdown files rather than YAML tiers); the two are worth comparing as implementations of "learned selectors and facts that outlive a session".

Fourth, the bulk-collection retrospective is a model of honest engineering writing. It reports the built-in tool winning by 2.7× on wall clock and losing on context budget and failure semantics, names the precondition that must hold for the win (a pre-warmed browser profile), and states the locale failure with the specific evidence that a request header and a cookie do not fix it while driving the page does. This is the level of reporting a self-improving agent project should aspire to, and it is a reminder that an agent's "extraction" is only as good as the environment it extracted from — the [[concepts/improvement-lives-in-external-state]] point in operational form.

Finally, the throughput claim should not be repeated as a result. The repository itself downgrades it, and a browser agent's real bottleneck is rarely page fetches per hour; it is the cost of the model's decisions over them, which the project measures far better than the pages-per-day figure it leads with.

## Reproducible experiment

No experiment was run for this page. The protocol below is for a reader with a disposable environment.

1. **Establish the extraction path is deterministic.** Install the CLI, open a controlled fixture page (the repository ships a MockSite with generated demo pages), and run the same `htmlsnapshot query --sql` three times. The pass criterion is byte-identical rows across runs and zero LLM tokens in the output — the claim under test is "Zero-Token Extraction", and the check is that no provider key is needed and the result does not vary.
2. **Reproduce the bulk-collection comparison.** Take 20 URLs of your own (not Amazon, to avoid account and locale confounds), and run the same extraction two ways: the built-in `crawl --seed-file … --sql … --format csv` with `--parallel 4`, and a hand-written loop of `goto` + `htmlsnapshot export` followed by local parsing. Record wall clock, tokens consumed, bytes written to disk, number of commands, and behaviour on a deliberately failing URL. The repository's reference numbers are 202.2 s vs ≈555 s on 20 Amazon pages with 2.03 M tokens for the hand-written path; a directionally similar result on a different site would be informative, and a reversal would be a finding worth reporting. Repeat each arm three times — the published comparison has no variance.
3. **Test the experience store's premise.** Run a scripted task against a local fixture site, record the trace with `experience save`, then re-run the same task with the same intent, and check which tier the second run reaches (P1 replay, P2 verify, or P5 cold). Repeat with a deliberately changed DOM to see whether a stale VERIFIED selector is caught or silently used. The pass criterion is that the tier advances and that drift is detected rather than replayed; a silent replay of a broken selector is the failure mode the `SELECTOR_DRIFT` category exists to name.
4. **Test the context mechanisms against their stated costs.** Run a long tool loop (a multi-page crawl driven through the agent path) and record input tokens per round with progressive disclosure on and off, and with the digest and deduper on and off. The repository's own figure — "23 overflows / 567 shell calls / 20M input tokens in one run" — is the reference point for the pathology; the pass criterion is that the mechanisms measurably reduce input tokens or overflow count relative to the same task with them disabled.
5. **Check the extraction-validity assumption.** Run the same X-SQL query against a page rendered under two different locale profiles and diff the rows. If the rows differ, an extraction that is deterministic per page is still not deterministic per task, and the correct conclusion is that locale must be pinned in the browser profile — the finding the bulk-collection skill already states.

Report token counts, wall clock, command counts and per-task results rather than averages, and keep the model, provider and tool set identical across arms.
