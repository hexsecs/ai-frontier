# Agensh

## What it is

Agensh is an open-source multi-agent harness from Microsoft Research, published under the MIT License and hosted at github.com/microsoft/Agensh with a project page at aka.ms/Agensh. The repository metadata records it as created on 2026-08-27, last pushed 2026-11-03, updated 2026-11-10, written in Python, with 909 stars, 104 forks and 4 open issues. The tree at `main` holds 236 paths.

The project has two published surfaces. The paper is the arXiv preprint "Agensh: Scaling Organizational Intelligence to 1,024 Agents" (arXiv:2609.26781, submitted 22 September 2026, classified cs.CL and cs.MA, 13 pages and 6 figures, by Zhihao Zhan, Ting Song, Li Dong, Shaohan Huang, Jianxun Lian, Yan Xia and Furu Wei of Microsoft Research). The arXiv record carries a perpetual non-exclusive licence and names no peer-reviewed venue. The code is the harness itself: the README's news entries record the preprint on 2026-09-22, the open-source release of the harness, launch scripts and reproduction guide on 2026-10-24, and on 2026-10-29 support for Copilot, Codex, Claude Code and Pi as single-agent backends.

The claim the source makes is specific. The abstract states that the scalability of current multi-agent harnesses "is often constrained by a central orchestrator's capacity to allocate tasks and coordinate workers", and that Agensh removes that component: "a scalable self-organized multi-agent harness without a central orchestrator". The five-actor comparison in the paper's Figure 2 and its related-work section name the harnesses it positions against: Codex sub-agent, Claude Code sub-agent and agent teams, Copilot fleet, and Kimi Agent Swarm.

The repository ships a `SECURITY.md`, but it is the unmodified Microsoft template: it points at https://aka.ms/SECURITY.md for reporting policy and contains no project-specific threat model, support boundary, or issue-handling promise. The only project-specific security statements are in the operational documentation.

## Mechanism

Files inspected: `README.md`, `REPRODUCE.md`, `SECURITY.md`, `agensh/README.md`, `agent/README.md`, `board-service/README.md`, `board-service/verifier.py`, `mini-router/README.md`, `secret-service/README.md`, `docker/README.md`, `scripts/egress_filter.py`, plus the arXiv HTML full text.

**The cooperation loop.** The paper's §2.1 defines a five-step loop each worker runs concurrently and asynchronously: gather context; claim a sub-task by appending a `CLAIM` to the shared context; take action locally; verify results against the sub-task's acceptance criteria and revise until the criteria are met; merge progress into the shared workspace and publish what changed, the underlying idea, and verification evidence. Allocation emerges because workers propose and claim their own sub-tasks: "By proposing and claiming their own sub-tasks, workers self-organize sub-task discovery and allocation across the organization."

**The three infrastructure components.** The paper's §2.2 and the repository agree on the same split. *Shared workspace*: a Git platform (Gitea) holding under-development and integrated work, with private checkouts and branches integrated into a `main` branch, issues and pull requests for everything, and Git providing provenance and textual merge-conflict detection. *Message interface*: Mattermost, with a shared task channel for announcements and direct messages for urgent one-to-one traffic; low-priority channel messages are delivered at the start of a loop iteration and direct messages "at the end of each infrastructure tool call", so a direct message reaches a peer mid-turn. *Shared context*: an append-only store of typed notes — `OBSERVED`, `FACT`, `FAIL`, `CLAIM` and `PATCH_SUMMARY` — with a recent in-memory view for prompt delivery and a grep tool over the full retained history. The paper attributes the shared-context idea to DeLM (arXiv:2606.10662) and says the implementation "adapts its tool formats and worker instructions."

**Where the coordination code actually lives.** `agensh/README.md` lists task-neutral Python for the driver: `team_run.py` runs one task end to end (prepare hook, services, seed push, Mattermost setup, task issue, staggered wake, idle watchdog, reminders, export hook, quiesce, archives, evaluation); `pack.py` loads and validates `tasks/<pack>/pack.toml`; `schedule.py` holds the budget, wake, idle and nudge timing as pure functions; `allocate.py` assigns port and subnet slots; `backlog.py` synchronises live board claims that cite `#<n>` into issue assignees, one-way, "the board stays the source of truth for who is working on what"; `quality.py` renders the CI merge gate workflow; `project.py` handles repository packs.

**The event-driven runtime** is described in the paper's Appendix B.1 and implemented in `mini-router/`. Each worker has a paired TypeScript sidecar. Gitea activity arrives as a server-sent event that triggers a token-authenticated notification fetch; Mattermost uses a live WebSocket with a REST catch-up for messages missed while disconnected. Both listeners normalise activity into unified event messages, ingest them into MySQL with per-agent deduplication, and wake a dispatcher that "orders and combines pending events into the next prompt, delivers it to the worker's persistent session, and marks the events as sent when the turn completes." `mini-router/README.md` gives the state machine: delivery follows `pending → sending → sent`, failed attempts enter `failed` then `retrying`, with at most five recorded attempts, and startup returns interrupted `sending` rows to `pending`.

**The shared-context service** is `board-service/`, a FastAPI application over MySQL. Its HTTP surface includes `GET /snapshot` for unread context across boards (which advances the viewer's cursors), `/board/{id}/read` for the live view, `/read_all` for the raw retained window including expired claims, `/board/{id}/grep` over persisted history with `&`, `|` and parentheses and a default and maximum window of 500 matches, and `/board/{id}/unfold` for details behind short gists. `board-service/README.md` gives the retention rules: `FACT`, `OBSERVED`, `FAIL` and `CLAIM` content is capped at 100 characters and `PATCH_SUMMARY` at 300; claims are hidden from live reads and turn-start snapshots after one hour by default; the recent view holds at most 2,000 entries; a matching `FAIL` invalidates that author's latest candidate; and "MySQL retains all admitted revisions for grep."

**What "verify" means here — and does not.** `board-service/verifier.py` is the whole of the board's verification, and its module comment is explicit: "Verification is a deterministic text check; it does not execute the claimed tests." `verify_note` normalises the note type and content, applies the character cap, and for a `PATCH_SUMMARY` rejects placeholder evidence, listing the phrases that count as invalid: `tbd`, `pending`, `not verified`, `unverified`, `should work`, `should pass`, `looks right`, `looks correct`, `seems to work`, `to be verified`, `will verify`, `n/a`. A note whose evidence field matches one of these is rejected with the marker `ps_invalid_ev=1`. So a peer's claim that it "verified" something is checked for phrasing, not checked against the artefact.

**The peer-integration gate is a CI workflow, not an agent judgement.** `agensh/README.md` describes the `[acceptance] ci_gate` mechanism: the prepare hook commits a generated `.gitea/workflows/agensh.yml` on top of the seed, pull requests run fast checks as `agensh / pr` and pushes to `main` run the full suite as `agensh / main`, and the driver posts `agensh/main-health` on every open PR head. While `main` passes, that check is `success`; when the full suite fails on `main`, a `FAIL` entry goes on the board and only PRs labelled `fix-main` or titled `[fix-main] ...` get `success`, the rest are `pending`, with the restriction lifting after 60 minutes so "a flaky suite cannot stall the team."

**What is enforced inside the container.** `agent/README.md` documents a shared MCP allowlist and deny list: `config/mcp_allowed_tools.json` is the model-visible allowlist enforced by the notice wrapper, `config/mcp_deny_tools.json` is the native-client exclusion list for Copilot, Pi and Codex, and `config/mcp_tool_metadata.json` holds reviewed description overrides. The policy "keeps 13 Gitea, 12 Mattermost and 4 board tools." The `mini-router` MCP notice shim "enforces the shared MCP allowlist before advertising or forwarding tools; it blocks unreviewed upstream additions by default." Codex's native multi-agent tools, web search, app connectors and automatic updates are disabled for the experiment, and Claude Code's general `Agent` tool remains excluded.

**Network containment.** `docker/README.md` describes the default topology: the default network is internal, the model proxy also joins `egress`, and the edge proxy joins `edge` for host access. `scripts/egress_filter.py` is the allowlist-mode forward proxy: it permits only a fixed list of package registries (pypi.org, files.pythonhosted.org, registry.npmjs.org, registry.yarnpkg.com, crates.io, index.crates.io, static.crates.io, proxy.golang.org, sum.golang.org, deb.debian.org, security.debian.org, archive.ubuntu.com, security.ubuntu.com, ports.ubuntu.com) plus the project's `ALLOW_DOMAINS`, on ports 80 and 443 only, and it refuses literal addresses because "Registries are named; literal addresses would bypass the list". Every decision — allowed, denied or error — is written as a JSON line to `EGRESS_LOG`; a denied request gets a 403 whose body names the host and points at the project's `allow_domains` setting.

**Credential handling.** `secret-service/README.md` describes a small standard-library HTTP service that serves bootstrap-issued worker tokens to routers on the private Compose network: `GET /tokens/<agent>` requires an `X-Internal-Auth` header matching `SECRET_SERVICE_INTERNAL_AUTH`, agent names are limited to 1–64 letters, digits, dots, underscores or hyphens, and resolved token paths "must stay inside that directory". The bootstrap token directory arrives as a read-only mount. Separately, the model API credential never reaches a worker: the egress proxy injects the real credential and workers receive only a local proxy credential.

**Process and resource boundaries.** `REPRODUCE.md` states that workers "run as UID/GID 10000" and can execute the root-owned, mode-0111 task reference at `/opt/pbench/executable` "without reading its bytes" — the reference program is the specification and reading it is out of bounds by construction. Worker containers keep a 64 GiB memory ceiling and no CPU limit by default, routers get 8 GiB, and the host cgroup slice `agensh.slice` caps the team at 80% of host RAM with no swap.

**The team-level accounting.** `agensh/README.md` records the budget mechanics: at 90% of the token budget every worker gets a budget-warning prompt, and at 100% "the egress proxy refuses model requests with HTTP 429 and the driver pauses". A `resume` segment clears the stored ACP session ids so each worker starts a fresh native session, and the run state is recorded as `running`, `paused`, `finalized` or `failed`. `REPRODUCE.md` gives the idle behaviour: the team watchdog checks every 60 seconds and nudges after 600 seconds of inactivity, with at least 600 seconds between nudges, and the ACP silence watchdog defaults to 20 minutes.

## Evidence

All quantitative results below are **author-reported** from the preprint or from the repository's own documentation. None has been independently replicated.

**The scaling result.** The paper's Figure 5 and §3.1 report that with the same model (GPT-5.6-sol, high reasoning effort), the same harness (Copilot) and the same six-hour budget, the mean final test-pass rate across the five hardest ProgramBench tasks rises from **19.31% with 1 agent** to **20.68% with 8**, **26.52% with 32** and **28.78% with 128** — a 9.47 percentage-point gain, described as "approximately 49% relative". On pandoc alone the paper reports 33.89% at 1 agent, 50.94% at 128 and 55.06% at 1,024 agents, the largest organisation improving on the 128-agent result by 4.12 points.

**A second model on one task.** With GPT-6.1-sol at high reasoning effort, the paper reports the six-hour pandoc test-pass rate rising from 56.19% with 1 agent to 79.59% with 32 agents, "a relative improvement of 41.64%".

**Latency, not only final quality.** Figure 6 is described in the text as showing that larger organisations reach comparable pass rates earlier: on pandoc, 128 agents exceed a 30% test-pass rate at the 30-minute checkpoint, while 32 and 8 agents first exceed that threshold at the 60- and 90-minute checkpoints, and the single-agent run stays below it throughout the first two hours.

**The task set.** The five tasks are FFmpeg (10,090 files, 1,549,005 lines, 75.51 MB), gromacs (8,982 files, 815,539 lines, 47.30 MB), pandoc (2,767 files, 104,336 lines, 4.86 MB), PHP-src (26,266 files, 2,812,757 lines, 119.76 MB) and ctags (7,313 files, 246,228 lines, 9.15 MB), selected as "the five most difficult tasks among ProgramBench's 200 instances".

**Qualitative evidence.** The paper's §3.2 reads worker trajectories for emergent organisation, not just scores: at 8 agents, workers "agree on a concrete technical interface and independently implement components that conform to it"; at 32, one worker's counterexample caused peers to withdraw an approval before the author fixed the problem; at 128, workers choose reviewers by prior experience and reuse review relationships, and two workers establish "a standardized integration protocol" that other workers then reuse and later revise; at 1,024, multiple workers take the integrator role and a worker "could contact several candidate integrators, select the first valid responder, cancel the other requests".

**Tests in the repository.** `board-service/README.md` records standard-library unit tests for the recent view, verification, grep parsing and unfolding, run with `python3 -m unittest discover -s board-service/tests`, with the explicit caveat that "the HTTP routes and MySQL persistence in `main.py` are not covered". `mini-router/README.md` records Node's built-in test runner covering listener normalisation, group-message backlogs and dispatcher delivery "against in-memory stand-ins; the MySQL event store is not covered". The repository also has `tests/unit`, `tests/smoke` and `tests/live` directories.

**The threat model the evidence covers.** The inspected files contain real containment mechanisms with observable boundaries: per-tool MCP allowlists enforced in the notice wrapper, an internal-network default with a separately joined egress bridge, an allowlist proxy that logs every decision and refuses literal addresses, a token service that authenticates by header and confines path resolution, a non-root worker UID that can execute but not read the reference binary, and a token budget that the egress proxy enforces by refusing model requests. These are the mechanisms the repository's own documentation describes.

**The threat model the evidence does not cover.** No source inspected contains a security evaluation of the harness itself. There is no independent audit, no adversarial test against the coordination layer, and no measurement of what happens when a worker emits a false `FACT` or a fraudulent `PATCH_SUMMARY`: the board's verifier is a text check, as stated above, and no file inspected compares a peer's claimed verification against an independent artefact. The paper's §2.1 step 4 ("Verify results. The worker matches its local progress against the sub-task's acceptance criteria") describes a self-check by the same worker that produced the work. The peer-review mechanisms that do exist — the `agensh/main-health` check, `review_paths` gating, and the `FAIL` entry on the board — are integration-level gates over repository state, and the board's own README records that "a matching `FAIL` invalidates that author's latest candidate", which is a coordination rule rather than an authenticity check.

## Limitations

**Stated by the authors.** The reproduction guide is unusually explicit about non-reproducibility of exact historical numbers: "The historical main experiment seeded the older `task_cleanroom` reference; its binary differs from v6 even when version strings match. These infrastructure updates mean a new release run should record its own revision rather than claim exact historical reproduction." The single-agent baseline is also not a like-for-like control: the paper's Appendix C states that "in practice, a single-agent run can rarely sustain the full 6-hour runtime", so a stop hook with a new-work prompt was added for the baseline, paired with an idle detector for the team. `REPRODUCE.md` records that the harness's latest-release pins are deliberate — "Claude Code and the Codex CLI install at their latest release by default … a standing pin hides that."

**Assessed from the reporting.**

- **Cost is not normalized.** Every headline number is a pass rate under a fixed six-hour wall clock and a fixed model, with agent count varying. The paper does not report inference tokens, currency cost, or coordination overhead per agent, so "49% relative improvement" cannot be compared with a cost per point. The 1,024-agent pandoc result differs from the 128-agent result by 4.12 points; the marginal return per additional agent at that scale is not characterised.
- **One task carries the largest organisation.** The 1,024-agent result is pandoc only, and the paper's own related-work and README material make pandoc the most-reproduced of the five. The mean-across-five-tasks series stops at 128 agents.
- **Baselines and evaluators are external and author-run.** The pass rate is ProgramBench's own canonical-kept score, computed with ProgramBench v1.2.5 pinned to a specific commit; `REPRODUCE.md` documents a pytest-identity hazard ("submitted project configuration can change JUnit test identities") and a separate helper for the canonical-kept score, which suggests the raw attempt count and the kept score differ.
- **The single-agent baseline was assisted.** The stop hook quoted in Appendix C pushes the single agent to keep working; no equivalent prompt appears for the team cells, so the 1-agent column is not a neutral control.
- **Verification is asserted, not demonstrated.** The board's evidence check is a phrase blacklist. The paper's emergent-cooperation analysis reads worker trajectories, which are self-reports of what happened. Nothing inspected shows the pass rate being re-scored by a second party.
- **The coordination substrate is trusted infrastructure.** Gitea, Mattermost and MySQL are assumed correct and available. The board service "checks text deterministically, without running the verification commands an agent reports", and membership "uses the supplied agent identity within the private network" — an in-network agent can therefore write claims about what other agents did.
- **Merge governance is permissive by default.** `docker/README.md` and `REPRODUCE.md` both record that bootstrap makes `agensh / pr (pull_request)` and `agensh/main-health` required checks on `main`, that coders can merge PRs with zero required approvals, that direct pushes to `main` are restricted to the administrator, and that the CI merge gate is disabled in the released configuration. A member of the team can therefore land work in `main` without a peer approval, subject to the two checks.
- **Host prerequisites are heavy and shared.** `REPRODUCE.md` requires Linux with Docker Engine, Compose v2, systemd and cgroup v2, a systemd reboot guard installed on the host, passwordless `sudo`, and cgroup and network configuration; it also warns "Do not restart Docker, move shared image tags or stop other experiments", which describes a shared, multi-tenant host.
- **No Python package, no release series.** The distribution is a repository clone with Docker Compose files, not a published library, and the README names no version.

## Competing approaches

Only alternatives the source itself names.

**Orchestrator-worker harnesses.** The paper's related work states that "Claude Code supports persistent sub-agents and asynchronous agent teams, but the collaboration is still organized around a fixed lead session that spawns other agents, manages shared tasks, and coordinates inter-agent messages", that "Codex supports sub-agent workflows with delegated parallel workers whose results are routed back to the parent for consolidation", and that "Kimi Agent Swarm trains an orchestrator to decompose tasks and schedule sub-agents concurrently for lower latency, but the harness remains an orchestrator-worker parallelization scheme". Copilot's `/fleet` command and the AgentNet paper are cited as further examples of centralised allocation. The stated difference is architectural, not measured: Agensh removes the allocating component.

**Shared-context and decentralised-coordination work.** The paper positions itself against DeLM, which "combines asynchronous workers, a task queue, and shared context so that agents can build on accumulated progress without routing every update through a central controller"; ChatCollab, which places human and AI participants in Slack as peers; SlackAgents, which embeds AI agents into Slack workspaces; Carlini's compiler-building experiment, which "coordinates 16 Claude agents through a Git repository and task-lock files, with workers selecting tasks and merging changes without an orchestration agent"; and STORM, which "reframes multi-agent coding as a state-management problem, replacing isolated multi-agent worktrees with a shared workspace that enforces local state consistency and detects stale or conflicting edits at write time".

**Merge conflict as a coordination primitive.** Git's textual merge-conflict detection is the mechanism the paper credits for surfacing integration problems to workers, in place of an orchestrator deciding what integrates.

## Implications

This section is analysis by the KB maintainers, not a claim of the authors.

The most transferable idea is the **claim-then-verify artifact**, not the multi-agent topology. Agensh's board makes the state of the team's work a first-class, typed, queryable object with an append-only history, so that a peer can ask "has anyone already established this?" without asking the producing agent. The value is concentrated in the `FAIL` type, which the paper's own prompt describes as "the highest-value entry: it stops peers spending budget on it". In a single-agent setting the same artifact is a durable negative-result cache; the multi-agent framing is one use of it, not the only one.

The second idea, and the one with the sharpest security consequence, is that **the board is an append-only log of claims, not a log of facts** — and the project is unusually clear about this in `verifier.py`'s comment that verification "does not execute the claimed tests". The design consequence is that a system which treats peer reports as evidence inherits the producing agent's incentives. Anyone adopting a shared-context board should decide explicitly whether a claim can be trusted, and if so on what basis, before scaling the number of writers; a board with 1,024 writers and a phrase-based verifier scales the *volume* of unverified assertion far faster than it scales the *verification*.

Third, the **integration gate is placed in CI rather than in an agent's judgement**. The `agensh / pr` and `agensh / main` checks, the `main-health` mechanism with its deliberate 60-minute auto-lift, and the `fix-main` label are mechanisms that treat "the team cannot merge" as a system state rather than a conversational negotiation. The auto-lift is the interesting part: it encodes an explicit trade-off between a stalled team and a stuck gate, and it is documented rather than incidental.

Fourth, the **cost of decentralization is deferred and unbudgeted**. The paper's central claim is that removing the orchestrator raises the ceiling on team size, and the evidence supports that the ceiling is higher. But a harness that can run 1,024 agents without a coordinating component also has no natural place to hold a global budget, which is why the budget enforcement lives in the egress proxy (refusing model requests with HTTP 429 at 100% of the token budget) rather than in a scheduler. That is a useful pattern — enforce the expensive resource at the boundary that mediates it, where enforcement is already happening — but it means the budget's granularity is the proxy's, and a single worker can exhaust a shared team budget.

Finally, the **harness-versus-model separation** is a practical portability result. Agensh implements the cooperation loop "through workflow instructions in each worker's prompt rather than hard-coding the loop into the runtime infrastructure", and the paper's Appendix A shows the prompt is identical for every worker except the worker ID. The consequence is that the same organisation protocol ran over four different single-agent harnesses with adapters only. Teams expecting to change their agent runtime frequently should note that the loop lived in the prompt, which means it is editable by whoever writes the prompt — a property that is also a governance question.

## Reproducible experiment

Proposed, not executed by the KB maintainers. Use a small private repository and a local or self-hosted model gateway; do not use the ProgramBench cleanroom images or the published experiment scripts for a first run.

1. **Does the loop work with a small team?** Run the same bounded repository task with 1, 2, 4 and 8 workers using the released team launcher on a disposable Docker host, with fixed token and wall budgets. Measure accepted test-pass rate, wall time, total tokens, merge conflicts, duplicated work (claims covering the same files), and reviewer intervention. A scaling curve that does not rise at all would contradict the paper's core claim; a curve that rises only with rising token spend would still be consistent with it.
2. **Does the shared context save budget?** Instrument the board to count how many times a worker retries a path already recorded as `FAIL` by a peer. The paper's prompt treats a `FAIL` entry as "the highest-value entry", so a measurable reduction in repeated failures is the claim's most direct test. The negative control is the same run with the board's `FAIL` type disabled.
3. **Can the peer claims be falsified?** Separately, and as a measurement of the trust boundary rather than of the harness's quality: have the harness record, for a sample of `PATCH_SUMMARY` entries, whether the claimed evidence actually corresponds to the artefacts on disk. The `verifier.py` blacklist is known not to do this, so the experiment measures the gap it leaves. Report the rate of unsupported claims as a property of the coordination substrate.
4. **What happens when the substrate is degraded?** Run the team with the board service unavailable for a bounded interval and observe whether workers idle, duplicate work, or continue. The paper's Appendix B describes retry and recovery for the event router but the coordination substrate's failure behaviour is not evaluated in the sources inspected.
5. **Cost normalisation.** For each worker count, record total model tokens and wall-clock cost alongside the pass rate. Publish the cost per accepted test, since the paper does not.

Freeze the model and harness versions, the dataset and the prompts; preserve raw trajectories, the board's retained history, tool receipts and the decision logs; and report numerator and denominator with uncertainty, a baseline and a held-out task set. Never promote a scaling claim without the actual independent acceptance record, and do not present a self-reported peer claim as verified work.
