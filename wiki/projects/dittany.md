# Dittany

## What it is

Dittany is a runtime repair framework for LLM-based multi-agent system (MAS) applications, presented in the arXiv preprint "Dittany: Contribution-Guided Repair Framework for MAS Applications" (arXiv:2610.42144v1, cs.SE, submitted 30 October 2026) by Hanqi Sun, Yuchen Shao, Hanyi Si, Beibei Xu, Lisheng Wang, and Chengcheng Wan (corresponding author), all at East China Normal University, with Shao and Wan additionally at the Shanghai Innovation Institute. The paper states no venue; as presented, it is a preprint.

The problem, in the authors' framing, is that MAS applications "can produce useful intermediate results while leaving task requirements unsatisfied. Repairing such executions requires identifying the work still needed and the completed results that can support it." A failed execution is rarely uniformly broken: an incorrect or incomplete result can enter the shared context and propagate, while other branches have already produced valid work. The naive remedies both fail — retrying the latest action with the same inputs leaves missing information and unresolved constraints unaddressed, and restarting the whole run repeats work that was already correct and may reproduce the same failure.

The paper poses three challenges. Detection must go beyond explicit errors (C1): individually valid results can violate a requirement in combination — lodging and transport each acceptable, their total over budget — and some requirements can only be checked once results from several actions are available. Repair scope must be decided (C2): a failure detected in one action may require changes elsewhere, so the repair must determine which actions to repeat, add, or revise, and which existing results can support it. And repair itself must be correct (C3): a revised result may fix one violation while introducing another, so it must satisfy the affected action's requirements plus the constraints of the task and subsequent actions.

Dittany's answer is to derive, for each subtask, an **expected contribution** — the result it is expected to produce together with the acceptance conditions that result must satisfy — from the task requirements and the MAS's method specifications, and to connect the contributions in a **contribution graph** whose edges link outputs to the inputs that consume them. Runtime checks against this graph drive repair at two scopes. **Action-level repair** fixes the current action using the inputs it already has. **Graph-level repair** adds missing prerequisite subtasks or revises unfinished work. Both scopes retain validated contributions throughout, and repaired outputs are checked before downstream work consumes them.

The paper's running example (a 7-day trip for five across three cities on a $3,000 budget) makes the scope boundary concrete. If local research returns a truncated response, the inputs are already available and an action-level retry suffices. If lodging ($2,880) plus transport ($720) totals $3,600 against the budget, no local fix works: keeping the transport leaves $2,280 for lodging and no existing option satisfies both budget and family requirements, so new accommodation research must be added at graph level while the route and transport results are reused.

## Mechanism

Dittany runs as a Python library interposed on the host MAS through framework adapters. An offline extractor builds a specification of the application; a per-request modeler builds the contribution graph; runtime checkers then monitor execution and trigger repair.

### Specification extraction and task modeling

The **MAS Specification Extractor** statically scans the application source and records agent definitions and instructions, the executable methods available to each agent (callable reference, input parameters with defaults and types, output structure, behavior, input/output meanings), each method's **conditions of use** (extracted from explicit checks and stated restrictions), and output-to-input dependencies in any declared workflow, followed through the call graph. An LLM writes the natural-language descriptions of method behavior and input/output meaning; a second LLM pass validates those descriptions against the code and text, flagging contradictions or unsupported claims for revision before the specification is used.

For each user request, the **Task Modeler** first extracts a **task contract**: the requested deliverable, content, and restrictions, distinguishing mandatory obligations and limits from explicitly stated preferences. A comparison pass against the request corrects omissions or changed meanings. Mandatory requirements define completion; preferences rank candidate plans and repairs.

The **initial contribution graph** is built from the contract and specification. If the host has a plan, its steps are linked to method descriptions and their outputs matched — by an LLM, on information, object, and scope — to task requirements; uncovered requirements mark results needing additional steps. With no plan, construction starts from all required results: each result lacking a producer gets a subtask and a method whose output and conditions of use fit, and each method's required inputs are matched to request values, available results, or planned outputs — an input with no suitable source spawning another producing subtask, recursively. Method and parameter references, source types, and dependency order are validated programmatically.

Each expected result then receives **acceptance conditions** derived from its linked mandatory requirements and the receiving methods' input requirements. Conditions are compiled into executable **verification policies**: an LLM identifies the required judgment and supporting inputs, then selects procedures — schema checkers (fields and types), numerical evaluators (expressions and bounds), reference checkers (resolving records and comparing fields), and, for judgments beyond those operations, an LLM-based checker configured with the condition and supporting material. Conditions may combine several procedures. Operands are bound to request fields, available results, or planned outputs; if the evidence for a check lacks a source, a producing subtask is added and itself receives conditions and checks.

### Detection and action-level repair

A four-stage checker runs at method selection, input preparation, execution, and return. Before dispatch, the action is associated with a subtask and its expected result; the method's behavior and conditions of use are compared against that result and the task requirements, using an LLM for semantic judgments. Input checks follow the subtask's bindings — source availability and acceptance, required parameters, types, explicit bounds, reference/version/scope agreement — programmatically, plus LLM content comparison. A missing source **defers** the action into contribution assessment; available-but-omitted or inaccessible information calls for input or handover repair. After execution, status and errors are inspected and the returned result is checked against the output interface and the linked verification policies, including omissions and relations with earlier inputs. Each condition is labelled **satisfied**, **violated**, or **unestablished**, and pending checks resume when their inputs arrive. Content passing its applicable conditions is retained as an **accepted result**, with its evidence and check outcomes.

Repair candidates are constructed from the failed condition and the available inputs, by failure kind: method substitution or reassignment to an agent holding the required method (selection failures); value adjustment or supplying omitted available content (argument failures); reference correction or rebinding (inconsistent references); retry, adjustment, or substitution (execution errors); correction or regeneration methods (output failures). Alongside native methods, Dittany provides three built-in supplementary operators: **Recomputation**, which re-evaluates a failed calculation's expression with a supported evaluator and corrects the field; **Evidence-constrained revision**, in which an LLM corrects or extends content given the affected content, the unmet condition, and the evidence, with output re-verified under the same policy; and **Constrained reassignment**, in which an LLM proposes assignments for adjustable choices, mandatory requirements are checked programmatically, and passing assignments are ranked by task preferences. Applications may also supply scenario repair templates that guide candidate configuration. Every candidate is validated against the specification and available data before execution; previously failed choices with unchanged inputs and conditions are excluded. Candidates are ordered (by an LLM, guided by templates and prior outcomes) and executed within budget, then re-checked. If action-level repair ends with unmet conditions, Dittany waits for viable planned producers, escalating to graph-level repair only when recovery needs missing prerequisites or changes to unfinished work and budget remains — budgets are not reset by escalation — and otherwise records the recovery target as unresolved.

### Graph-level repair

After each checked return or execution update, results and checking records are credited to subtasks; accumulated content is compared with the expected result and consumer input requirements. Missing content and unestablished or violated conditions form the **contribution gap**. Accepted results keep their evidence even when a combination fails. Progress is assessed per update — new accepted results or evidence, newly satisfied conditions, corrected violations, verified exclusions — and three consecutive assessments without progress count as stagnation. A node closes when its results satisfy all acceptance conditions, releasing successors whose inputs are available.

When a subtask with unmet conditions ends, stagnates, or cannot continue, Dittany checks whether the remaining plan can still satisfy them; a missing producer, or a necessary change to a subtask or dependency, triggers graph-level repair. The unmet conditions and policies, reusable results and evidence, and affected unfinished nodes are recorded as the **recovery target**. Repair construction compares what each unmet condition requires against the accepted results — missing content calls for production, unestablished support for the evidence the policy requires, a demonstrated violation for revision of the responsible content or selection — and proposes recovery methods from the specification, the unfinished plan, and the repair history. Their required inputs are traced and bound to request values, accepted results, or planned outputs; an input with no source spawns a producing subtask recursively, forming a **repair subgraph** whose new results receive acceptance conditions and verification policies as in initial construction. Candidates depending on a result still under construction on the current path are rejected as cyclic, and a suitable planned producer is reused rather than duplicated. Before execution, the subgraph is checked for coverage of the recovery target.

Plan reconstruction then re-checks each unfinished node that will receive a recovery output against the proposed input: suitable nodes are retained with updated bindings, missing input information extends the subgraph, and unsuitable nodes have their expected result and unmet conditions returned to the recovery target for replacement subtasks. The check propagates along output dependencies to affected successors. If rechecking invalidates a previously accepted result, that contribution — and completed consumers that depended on it — is reopened for regeneration, while independent contributions whose conditions remain satisfied are retained.

Finally, once the mandatory conditions checkable before final-answer generation are satisfied, Dittany takes a complete host response or initiates final-answer generation from the accepted results, then verifies the actual answer against the final-deliverable policies. Defects confined to the current action return to action-level repair; missing underlying results return to contribution assessment. If recovery exhausts its budget, Dittany reports the unresolved conditions together with the retained accepted results — it does not relax mandatory requirements or supply unsupported values.

## Evidence

All results below are author-reported. The evaluation testbed comprises **30 open-source MAS applications** — five each from AutoGen/AG2, CrewAI, LangGraph, Google ADK, HelloAgents, and the OpenAI Agents SDK, collected from GitHub and framework example repositories, totaling 25,460 lines of code and 151 agent roles — with **300 inputs and reference outcomes per application, 9,000 application–task instances** in all. Task data is drawn from published sources per domain (among them QASPER, SWE-bench-Live, TravelPlanner adaptations, tau2-bench and Synthea adaptations, FinQA, MathDial, FEVER), with frozen source records and initial environments, and reference outcomes reserved for offline evaluation. Task accuracy is the fraction of inputs whose final outputs satisfy the reference requirements, by executable checks where possible and otherwise by semantic assessment. **All runtime inference — host agents, Dittany's extraction, checking, and repair, and the assessor — runs on a single backbone, DeepSeek V4 Flash**, via remote APIs at temperature 0 with thinking disabled.

**Detection (RQ1).** Scored per execution against task requirements over **8,758 executions with resolved detection labels** (164 ambiguous and 78 format-only-discrepancy runs excluded), Dittany reports 4,257 flagged failures, of which 3,758 are true positives and 499 false positives; it detects 3,758 of the 4,746 executions containing failures — **88.28% precision and 79.18% recall**, with F1 83.48% and accuracy 83.02%. The per-framework spread is wide: precision runs from 65.52% (CrewAI) to 100.00% (HelloAgents), recall from 65.40% (HelloAgents) to 96.53% (LangGraph). Of the true-positive executions, single-point defects (invalid tool calls, malformed outputs) are documented in 40.82% and task-content defects (incorrect calculations, unsupported claims, violated planning constraints) in 28.31%.

**Repair effectiveness (RQ2).** Dittany achieves **84.76% task accuracy, compared with 58.01% for Native execution and 63.48% for Reflexion**, the strongest aggregate recovery baseline — gains of 26.74 and 21.28 percentage points, or 2,407 and 1,915 additional correct outcomes across 9,000 tasks. The full baseline table: Native 58.01%, Reflexion 63.48%, Iterative Rollback 58.21%, SupervisorAgent 48.39%, AgentTether 50.41%. In the paired comparison with Native, **Dittany passes 2,838 of the 3,779 inputs Native fails (75.10%)**, while Native passes 431 that Dittany fails; both pass 4,790 and both fail 941. Notably, 47.29% of the inputs Dittany recovers also fail under both Reflexion and Iterative Rollback. Requirement-group results show where the gains concentrate: among 279 Stock Analysis tasks with an unmet Native volatility requirement, Dittany passes 276, against 4 for Reflexion and 5 for Rollback; it passes all 114 AG2 Travel Planner tasks with missing routes between activities (65 and 33 for the baselines), and 79 of 86 Agents Deep Research tasks with correct claim values but incomplete source bindings (53 and 59). The improvement extends to 24 of 30 applications and all six frameworks in aggregate, with two applications tying Native; omitting any single application leaves an aggregate gain of at least 24.22 points over Native.

**Ablation (RQ3).** The scope ablation is the paper's most informative table. Native scores 58.01%; **action-level repair alone scores 52.54%**; graph-level repair alone scores 69.17%; the full system scores 84.76%. Adding graph-level repair to action-only raises accuracy by 32.21 points (2,899 additional correct outcomes). Adding action-level repair to graph-only simultaneously raises accuracy from 69.17% to 84.76% and cuts token consumption from 451.397M to 374.948M — within the combined system, the action scope's contribution is efficiency as much as accuracy: cheap local fixes keep the expensive graph machinery in reserve.

**Cost.** Dittany consumes **374.948M tokens in total, 17.92% more than Native** (317.963M), while producing 2,407 additional correct outcomes — and fewer tokens than every recovery baseline (Reflexion 494.565M, Iterative Rollback 431.231M, SupervisorAgent 494.658M, AgentTether 451.353M). The paper is transparent that these totals combine recorded usage with estimates for executions lacking complete measurements, applying the same comparable-call estimation rule across methods; monetary cost and elapsed time are not reported.

## Limitations

**Action-level repair alone is worse than doing nothing.** At 52.54%, the action-only ablation falls *below* Native's 58.01%: local repair, applied without the graph scope, destroys more correct outcomes than it creates. The headline win belongs entirely to the combination, and specifically to graph-level repair — adding the graph scope to action-only is worth 32.21 points. The paper reports the ablation table but never headlines this inversion, and a reader who took "two repair scopes" as two independently useful mechanisms would be misled: the action scope's standalone accuracy effect is negative, and its demonstrated value is cost containment inside the combined system.

**Dittany does not win everywhere.** It leads the recovery techniques in only four of six frameworks: on LangGraph, Reflexion reaches 86.20% against Dittany's 77.33%, and on OpenAI Agents, SupervisorAgent reaches 77.93% against 69.67%. At application level, four of the 30 applications score *lower* with Dittany than with Native execution, and two tie. The aggregate margin is real — it survives leave-one-application-out removal — but it is an average over a distribution that includes outright losses.

**Two of the four recovery baselines are mostly literature numbers.** SupervisorAgent and AgentTether were re-executed under matched conditions on only five of the 30 applications; their other 25 results are "the reported configurations and assessments" from those systems' own papers, on potentially different task instances and assessments. The 21.28-point margin over Reflexion is therefore the solid comparison — and even Reflexion here is the authors' MAS-level adaptation of a single-agent method, not the original design. Margins over SupervisorAgent and AgentTether rest partly on non-comparable rows.

**The entire testbed runs on one model.** Host agents, Dittany's own LLM-based extraction, checking, and repair, and the semantic assessor that grades final outputs all use DeepSeek V4 Flash. Detection, repair, and assessment thus share a model family: the assessor judging an output is the same kind of judge that checked and repaired it, a configuration in which correlated blind spots can inflate measured accuracy in ways the design cannot detect — the evaluation-side instance of [[concepts/evaluator-circularity]]. Nothing in the paper shows the gains transfer to other backbones, and part of the detection and repair loop's semantic-judgment quality is a property of this one model.

**Detection coverage is partial.** Recall of 79.18% leaves a fifth of failure-containing executions undetected, and detection is evaluated only on the 8,758 resolved labels, with 242 runs excluded as ambiguous or format-only. Precision also varies sharply by framework (65.52% on CrewAI), so the pooled 88.28% overstates detection reliability on the weakest hosts.

The authors' own threats to validity (§7) acknowledge the main structural risks. Specification and checking: Dittany "derives method descriptions and task conditions from source code, documentation, and user requests. Incomplete descriptions or ambiguous requests can lead to omitted requirements or incorrect associations," and reuse "depends on the coverage of the configured checks and whether their conditions still apply to the new use of a result." Outcome assessment: "Semantic judgments can contain correlated errors or admit multiple interpretations, and excluding unresolved labels limits detection conclusions to the resolved subset." Execution: model responses, tools, and service updates can change trajectories, and "temperature zero does not ensure identical responses across repeated remote calls." Coverage: the evaluated applications and six frameworks "cover a finite set of tasks and execution patterns" that limit generalization, and "unobservable state or external effects can prevent the verification needed to reuse a result or continue affected work." Finally, costs are tokens only, partly estimated; the checking Dittany inserts — including LLM semantic checks before results may flow downstream — has latency and dollar costs the paper does not measure.

## Competing approaches

The paper positions Dittany against four recovery families, benchmarked head-to-head on task accuracy (Dittany 84.76% throughout, with the baseline-provenance caveats under Limitations):

- **Native execution** — the host application with no recovery: 58.01%. This is the honest floor, and two of the recovery baselines fall below it.
- **Reflection (Reflexion)** — verbal self-feedback carried into the next attempt, here adapted by the authors to the MAS level with task, trajectory, and application-visible feedback: 63.48%, the strongest aggregate baseline, using 24.19% more tokens than Dittany — and the winner on LangGraph (86.20% vs 77.33%).
- **Rollback (Iterative Rollback)** — the authors' checkpoint-restore baseline, restoring the latest supported checkpoint before a failure and falling back to earlier checkpoints on persistent failure: 58.21%, barely above Native.
- **Runtime supervision (SupervisorAgent)** — an LLM-free filter triggering supervisory review and corrective guidance: 48.39% in aggregate, below Native, yet the best of all methods on OpenAI Agents (77.93% vs Dittany's 69.67%).
- **Post-hoc diagnosis (AgentTether)** — dependency-aware trajectory diagnosis with repair memory guiding re-execution (memory disabled in the matched runs): 50.41%, also below Native.

Related work the paper discusses but does not benchmark includes DoVer (intervention at selected trajectory points with re-execution), MARS (rollback plus guided repair searched in an MCTS over candidate repairs), and Who&When failure attribution. Dittany's stated differentiator is that its recovery target is derived by comparing required results and acceptance conditions against accumulated results and remaining producers: repair scope is decided by unmet contributions and available inputs rather than by trajectory position alone, and reuse of prior work is conditional on re-verification under the conditions of the new use.

## Implications

For builders of multi-agent systems, the central lesson is that intermediate results are simultaneously an asset and a liability, and the difference is verification. Retaining validated work is where Dittany's gains live — three quarters of the inputs Native fails are recovered without discarding the run — but retention is only safe because every reused result carries acceptance conditions checked under the conditions of its new use. Systems that keep intermediate results in a shared context without per-use conditions are holding the liability without the asset.

Second, repair *scope* matters more than repair *effort*. The ablation shows a repair mechanism can be net-negative when its scope is wrong: retrying and patching locally, however diligently, underperforms no repair at all, while deciding scope from the dependency structure — what is missing, what depends on it, what can be reused — is worth over thirty points. Frameworks that expose only a retry hook are offering the weakest form of recovery.

Third, the approach front-loads specification work. Contribution-guided repair is only possible because acceptance conditions exist before failure occurs; Dittany derives them automatically from code, documentation, and requests, but the threats to validity are explicit that derivation gaps become repair blind spots. Teams adopting this pattern should expect to invest in the quality of extracted specifications and domain verification procedures, which the library accepts as developer-supplied inputs.

For evaluators, the paper is also a cautionary example: aggregate recovery margins conceal per-framework losses, and baseline provenance — re-run under matched conditions versus carried from the literature — changes which comparisons a reader should trust. The Reflexion margin (re-run, matched) and the SupervisorAgent margin (mostly literature numbers) sit in the same table with different epistemic weight.

## Reproducible experiment

A full replication is not extractable: the paper releases no code or data (see Evidence status), the testbed is 30 third-party applications with 300 constructed inputs each, inference ran against a remote API model, and two baselines' numbers partly come from their own papers. Two smaller checks *are* extractable from the published tables alone:

1. **Internal-consistency audit of the headline numbers.** The published figures reconcile exactly. Detection: 3,758 / 4,257 = 88.28% (precision) and 3,758 / 4,746 = 79.18% (recall). Paired outcomes: 4,790 both-pass + 2,838 Dittany-only = 7,628 = 84.76% of 9,000 for Dittany; 4,790 + 431 Native-only = 5,221 = 58.01% for Native — consistent across the results, ablation, and cost tables. Cost ratio: 374.948 / 317.963 = 1.1792, i.e. the reported +17.92%. Ablation saving: (451.397 − 374.948) / 451.397 = 16.94%, as reported. A reader can verify each of these from the paper text with no code.
2. **Worked-example spot-check.** The travel example is fully specified numerically — $3,000 budget; lodging $2,880 + transport $720 = a $3,600 violation; retaining transport leaves $2,280 for lodging; constrained reassignment selects lodging at $1,980 for a $2,700 total within budget. A reader can verify the reassignment arithmetic and, more importantly, the action-versus-graph decision boundary it illustrates (inputs sufficient → retry at action level; inputs insufficient → add a producing subtask at graph level) directly from the text.

## Evidence status

Every quantitative result on this page is **author-reported**: a single research team's measurements, on a single backbone model, with no independent replication cited by the paper and none performed for this page. Baseline provenance is mixed and labelled where it matters: Reflexion was re-run as the authors' own MAS-level adaptation, Iterative Rollback is the authors' baseline, and SupervisorAgent and AgentTether figures are mostly literature-reported numbers outside five matched applications. Despite describing a Python implementation in detail, **the paper releases no code and no data** — no repository URL appears anywhere in the text, and the constructed 9,000-instance test set, reference outcomes, and rubrics are not published — so none of the experiments can currently be independently re-run. This page is based on a full reading of the paper's arXiv HTML full text (v1), including tables, the baseline-configuration caveats, and the threats-to-validity section; nothing was executed or reproduced beyond the arithmetic consistency checks described above.
