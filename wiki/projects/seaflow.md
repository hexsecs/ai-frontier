# SeaFlow

## What it is

SeaFlow is a self-evolving agentic-workflow framework for competitive economic games, reported in the arXiv paper "Self-Evolving Agentic Workflows via Semantic Decomposition of Complex Tasks" (arXiv:2611.01840, submitted 1 November 2026; cs.AI, cs.CL, cs.MA). The paper lists seven authors: Zichuan Fu, Junjia Qi, Wenlin Zhang, Yimin Deng and Xiangyu Zhao (City University of Hong Kong) and Xian Wu (Tencent Jarvis Lab), with Zhao as corresponding author. Its arXiv comment field states that it was accepted as a **Spotlight at the NeurIPS 2026 Workshop on Interpreting Agent Behavior (IAB), GLEE Competition Track**, and that it took **1st place in the GLEE competition**; the paper itself is therefore a workshop paper rather than a main-conference publication, and the competition result is the paper's headline evidence. The abstract links code at https://github.com/Applied-Machine-Learning-Lab/NeurIPS2026_SeaFlow.

The problem the paper names is that agentic workflows invoke a model at every step, which multiplies inference cost and delay, and that some of those steps already have defined solutions. Its answer is *semantic task decomposition*: the workflow names the situations it handles as explicit applicability conditions, attaches a procedure to each condition, and lets that procedure execute code or invoke a model. Between interactions, a separate agent uses execution feedback to revise the workflow — refining the decomposition, the parameters, the fitted models or the procedures — and keeps a revision only if it survives evaluation.

## Mechanism

**Separation of the workflow from the improver.** The workflow is executable code and stays fixed during an interaction: at iteration k it maps input x_t and history h_t to an action a_t and an execution trace τ_t. The program may use conditions, function calls, nesting and loops, so the structure is not restricted to a decision tree. Each operation either executes code directly or invokes a model — an LLM for unresolved language-dependent decisions, or a learned predictor for an estimated quantity. The surrounding program decides when an operation runs, supplies its inputs and processes its output; model inference happens only where the workflow says so.

**Revision loop.** After executing W_k, the agent collects execution traces and task outcomes D_k, examines poorly handled cases to find problems in the decomposition, the parameters or the procedures, and constructs a candidate W̃_{k+1} from W_k and D_k. The paper names four revision operations: task decomposition (split subtasks through observable conditions, or reorganize branches when distinct cases need different decisions), parameter adjustment (tune thresholds, weights or other numeric settings within an otherwise suitable procedure), model fitting (train or update classification or regression models to estimate acceptance probabilities or continuation values), and procedure redesign (devise an alternative strategy and implement it through code or model reasoning). The candidate is evaluated using replay, held-out records or bounded deployment, to assess the targeted behaviour and check for regressions; if retained it becomes W_{k+1}, otherwise W_{k+1} = W_k.

**Revision protocol, as reconstructed from the repository** (paper Appendix B.1). The recurring protocol uses a shared history-inspector prompt followed by a strategy prompt and one family-specific routing prompt. The coding agent is instructed to open the exact replay, reconstruct decision-time state, compute payoffs or continuation values with diagnostic code, record the visited route, modify only the affected node, preserve sibling behaviour and the parent fallback, and add a named replay. A revision names the target node, the semantic distinction, the executor, the fallback and the validation condition. The paper notes that the repository retains these instructions and the accepted code, but not one fixed design-time model identifier or a complete proposal ledger.

**What the repository shows.** The released tree is organised as `glee_agent/` (workflows, runtime helpers, judge, diagnostics, fitted artefacts), `glee_runtime/` (game queue, move scheduling, networking), `scripts/` (replay diagnosis, reference building, model fitting) and `tests/`. Files inspected directly for this page:

- `glee_agent/workflows/tree.py` — builds decision-path labels of the form `bargaining/<regime>/<plan.procedure>/<action_type>`, `negotiation/<regime>/<band>/<proc>/<action_type>` and `persuasion/<regime>/<proc>/<action_type>`. Its docstring states that live play still uses the per-family `play()`, so the path is a label over the same decision structure rather than a separate dispatcher.
- `glee_agent/route.py` — maps each family to its `play` function and each regime to a handler; an unknown family returns `{"decision": "reject"}`, and a `fail_closed` helper returns the same, i.e. the deterministic fallback is a rejection.
- `glee_agent/workflows/bargaining/classify.py` — the situation classifier, with the constants `PATIENT = 0.99`, `IMPATIENT = 0.97`, `HOT = 0.85`, and an `inflation_band` helper. `classify()` returns one of eleven regimes: deadline, penultimate, powerless, impatient_hot, impatient_vs_hotter, impatient, patient_vs_impatient, patient, unknown_horizon, incomplete and symmetric. `situation()` returns the tuple (regime, information band, inflation band, horizon phase). This is the applicability-condition layer the method is about, in code.
- `WORKFLOW.md` — the live-play pipeline as documented: game JSON → `rules.parse` → family classify → canonical `scenario_id` / `state_id` → one cell / one procedure (deterministic fallback) → exact-cell evidence lookup → candidate accept/continue/payoff estimates → evidence-gated action selector → diagnose snapshot (path + calc) → legal alternatives (code) → scenario ambiguity gate → model pick among those names (≤ 1 call / 8 s, 4 s timeout) → deterministic message → sanitize → POST. It states that the model "only handles ambiguous scenarios and picks among precomputed legal alternatives; it never invents a price, split, or EV", and that a timeout or bad pick falls back to the heuristic.
- `docs/modeling-workflow.md` — the decision-modelling contract. Every decision carries a `scenario_id` (decision-time static variables; hidden opponent values are recorded as `hidden`, never read from the completed replay) and a `state_id` (scenario plus action type, current procedure, observed opponent style and an evidence-count band). A six-level parent order is fixed, from exact `state_id` down to the existing deterministic workflow; message pooling is the only static-variable relaxation, because a chronological ablation found no stable message-availability effect. A response policy may act from a pooled-message parent only with at least eight effective games, three chronological-holdout improvements, zero holdout regressions and positive train and holdout gain. The six-part **evidence gate** requires enough effective games and both required outcomes present, an improvement in chronological holdout on the same feature set, an improvement in normalized payoff on train and holdout, no material regression in the nearest sibling cell, model support for the candidate action, and a predicted advantage above the stored uncertainty guard; otherwise the selector moves to the next parent and, if no fitted parent passes, the existing workflow decides. Money scale is excluded from the task identifier because the games are scale-invariant and a five-window ablation found no stable predictive gain. `glee_agent.segments.MODEL_SCHEMA` is the executable registry: a family must declare its indicators, estimated targets, candidate set, objective, non-overridable constraints and fallback, and adding a fitted cell may change an estimate but may not silently change the objective or the legal candidate space.
- `docs/patch.md` — the optimization workflow. It states the objective is percentile-adjusted payoff on the current field and warns that "a green test suite proves legality and regression coverage; it does not prove rating gain". A change must carry one of four evidence types (dominance, continuation value, scenario reference, repeated current-field behaviour); `logs/mistakes/` alone is described as selection-biased; and verification is `pytest -q`, `scripts/check_patch.py` and `git diff --check`, with a named replay test for every non-trivial branch that must check both the new action and the nearest case that must remain unchanged.
- `scripts/evolve.py` — a second, simpler evolutionary loop shipped alongside the paper's method: play a batch, mutate **one numeric policy knob**, and keep it only if the family rating rose, otherwise roll back to the parent. It logs each generation (family, key, kept, before/after ratings, fail rate, batch size) to `logs/evolve.jsonl`, and it holds an exclusive lock so only one evolution run executes at a time. The default in this script is `GLEE_EVOLVE_GAMES=24`, `GLEE_EVOLVE_GENERATIONS=0` (unbounded) and `GLEE_CONCURRENCY=8`.
- `.env.example` — `GLEE_API_URL=https://glee-competition.com`, `GLEE_CONCURRENCY=3`, `GLEE_LLM_MESSAGES=0`, `GLEE_LLM_JUDGE=1`, `GLEE_EVOLVE_GAMES=24`, `GLEE_LLM_MODEL=grok-4.6`, with `XAI_API_KEY` optional.
- `README.md` — describes the agent as first overall on the GLEE leaderboard with an overall rating of **2594.5** at revision `a1875a0`; documents `run_agent.py`, the diagnosis tool `scripts/diagnose.py --file REPLAY.json --round N --action offer`, and a test suite of "500+ unit and replay tests"; and points to the separate OpenProgram repository (https://github.com/fzkuji-neo/OpenProgram) that the self-evolution is built on. The README's quick-start clones `https://github.com/fzkuji2026/SeaFlow.git`, a different path from the repository the arXiv abstract links.

**Scoring invariants the repository treats as fixed.** `WORKFLOW.md` records that only the agent's own payoff percentile within the exact configuration and role is optimized, that a per-game rating tick is opponent-strength adjusted and its sign is evidence about that game rather than proof that an action is generally right, and that the workflow must generalize across **960 configurations**. It also records that a timeout or five invalid moves is scored at the 5th percentile and that a legal `WalkAway` is a game action, not abandonment. The reference baselines in `glee_agent/reference.json` are public GLEE medians per configuration, generated from **77,467 official games** by `scripts/build_reference.py`.

## Evidence

All numbers in this section are **author-reported** from the paper; the repository inspection establishes what the released code contains and how it is documented, not the paper's performance claims. No result here has been independently replicated.

**Setup.** The evaluation is in the GLEE competition across the Bargaining, Negotiation and Persuasion environments. GPT-5.5 revises the workflows from execution feedback through the authors' OpenProgram framework, and Grok-4.6 serves the optional runtime LLM modules. Workflows stay fixed within a game. Performance is the official GLEE rating; efficiency is the local decision time per action. The paper analyses **725 development iterations** and **12,249 action records** collected with fixed workflows.

**Final-workflow statistics (Table 1, revision a1875a0).** The official rating is reported per environment; the repository README additionally reports an overall rating of 2594.5 for the same revision.

| Measure | Bargaining | Negotiation | Persuasion |
|---|---|---|---|
| Official rating | 2760.27 | 2761.67 | 2261.58 |
| Mean branches per strategy node | 2.13 | 2.25 | 2.24 |
| Mean strategy judgments per action | 37.61 | 22.95 | 7.42 |
| Mean local decision time (ms) | 0.118 | 0.198 | 0.122 |

The paper states that in all three environments the final workflows make each decision locally within a millisecond, and that code and fitted models decide in under a millisecond while the measured LLM calls take seconds and mostly fail.

**Competition record (Appendix C).** The September 1 snapshot contains 42,917 cumulative games across the three environments — 8,256 Bargaining, 27,226 Negotiation and 7,435 Persuasion. The separate fixed-workflow analysis sample holds 1,112 games and 12,249 action records (512 Bargaining games / 2,344 actions; 199 / 1,912; 401 / 7,993), with mean recorded actions per game of 4.58, 9.61 and 19.93. In those samples runtime LLM judging, LLM-generated messages and policy updates during deployment were all off, and there were **0 recorded valid LLM selections**.

**Workflow evolution (RQ2).** The 26 representative strategy changes span iterations 12 to 689, four of them after iteration 600. A model judge enters Bargaining at iteration 40 and is disabled at 186; the plateau exit enters at 552 and is withdrawn at 564, and a separate Bargaining responder policy returns to shadow mode at iteration 557. Negotiation separates roles and hidden types at iteration 12, probes the acceptance interval at 415, mirrors seller concessions at 462 and remembers opponents across games at 468; Persuasion switches signals at 31 and 62 and sells a low-quality product after trust is built at 612; Bargaining protects its payoff at 285 and mirrors revealed demands at 313. The initial workflows contain none of these procedures. All three environments' ratings rise together around iterations 236–244. The paper is explicit that the figure "does not isolate the effect of any single change on the rating", and that the competition rating rewards only a player's own payoff. The final Bargaining workflow opens at a 55% self-share in all 63 eligible states; its reservation lock rejects in 382 states, and from iteration 285 it also rejects non-final offers leaving it at most 10%.

**Revision activity across the 725 iterations (Appendix B.6).** The first 258 iterations lie on the main line; from iteration 259 onward most work happens on experimental branches, with selected changes later returning. Decomposition changes 738 code units in 458 commits and redesign changes 591 units in 188 commits, while parameter adjustment and model fitting each change fewer than 35 units. Test functions on the main line grow from 165 to 595, and of the 527 commits that change strategy code, 493 also change tests. Evolution includes withdrawal: 13 commits restore an earlier strategy policy, most after iteration 300, and Table 2 records three policies that change direction during development — the Persuasion seller goes skip → recommend → skip → recommend-until-first-sale over iterations 1, 22, 29 and 31; the Bargaining plateau exit goes shadow → live → reverted → live-with-guard → split-by-horizon at 548, 552, 564, 579 and 585; and the Bargaining Rubinstein responder goes shadow → live → shadow → live-on-a-narrower-band → shadow at 553, 556, 557, 559 and 560.

**Behaviour analysis (RQ3, Appendices C, D).** Code makes up most of the designed modules throughout development; fitted models join as the workflows learn from recorded games; LLM modules remain as optional interfaces. These shares count designed modules rather than decisions. In play, the LLM judge decides rarely and less over time: early on it answers about one in eleven non-message actions, almost all of them Persuasion buyer decisions, and its answers agree with the code in all but one case. The agent then makes these decisions deterministic and judge responses almost vanish after iteration 90.

**LLM-judge quantification (Appendix D.5).** Windows 72–89 and 90–223 contain 189 valid picks in 2,468 recorded non-message actions and 44 valid picks in 54,711 actions, of which only 2 and 8 respectively change the action — valid-pick rates of 7.66% and 0.080%, and action-changing rates of 0.081% and 0.015%. Over the whole logged span the totals are 57,179 actions, 233 valid selections and 10 action-changing selections. In iterations 72–82 the judge answers 9.1% of non-message actions, and 185 of its 189 responses are Persuasion buyer decisions, agreeing with the code in 184 of 185.

**Condition-to-action checks (Appendix D.3).** In the fixed Bargaining batch, opening imitation selects a 55% self-share in all 63 eligible states, spanning 60 games with no action violation. The reservation condition applies to 451 states but its rejection procedure handles only 382; the remaining 69 take higher-precedence branches, producing 57 rejections and 12 acceptances. The low-share predictor gate activates eight times, all followed by rejection. A separate legality pass finds zero schema or offer-budget violations among all 2,344 Bargaining action rows from 512 games. The paper stresses that these checks "establish behavior on logged states, not counterfactual route coverage or the accuracy of every upstream semantic classification".

**Visited decision units (Appendix A.5).** Deduplicating final selection node IDs in Bargaining and final procedure names in Negotiation and Persuasion yields 58, 15 and 16 observed units. Bargaining has 53 code units, one predictor unit and four unclassified units; Negotiation has 14 code units and one procedure whose nine fitted-eligible actions do not reveal whether the predictor displaced its numerical fallback; Persuasion has 16 code units. Runtime LLM judging was disabled in these samples.

**Rating movements (Appendix C.1).** The recorded interval ending at position 243 contains increases of 107.16 rating points over 267 Bargaining games, 147.19 over 262 Negotiation games and 139.64 over 267 Persuasion games. The Bargaining rating rises from 2331.96 to 2631.70 at the same recorded revision and then reaches 2760.27 at a subsequent deployment, while Negotiation declines from 2923.32 to 1844.08 before recovering. The paper states these are changes between rating observations, not single-match effects or controlled estimates of a code edit.

## Limitations

**Stated by the authors.** The conclusion states directly that "controlled comparisons are needed to quantify performance gains and costs across workflow construction, execution, and revision" — the paper does not run the counterfactual of the same agent without the workflow, nor an ablation over the four revision operations. The rating figure is described as a segmented summary retaining one observation per plotted revision, and deployment hashes locate observations but do not establish which edit caused a rating change. The operation labels in Appendix B come from syntactic rules, so a changed condition may fix a bug without splitting a subtask, and a mixed change counts once for each operation it contains; the counts measure code change and not its effect on rating. Commit messages show how the agent describes a change but do not prove that the described validation ran. Branch-usage shares come from replayed development states rather than a new tournament and "do not measure how much each branch adds to the rating or whether its decisions are optimal". The fitted offer model is described as currently inert: the serialized accept and continuation tables have no shared segment, so offer fitting returns the rule fallback. On release, the local research package contains exporter scripts and the derived CSV/JSON used for the figures but "is not yet a public reproduction artifact: raw interaction logs cannot be redistributed, and the exporter contains local deployment identifiers."

**Assessed from the reporting.**

- **No controlled comparison of any kind.** The headline is a competition ranking among agents whose internals are not disclosed. There is no baseline of the same agent with a model call at every step, no ablation of the four revision operations, and no measurement of what the workflow construction and revision cost in tokens or wall-clock time. The paper's own summary sentence concedes this.
- **Self-competition evidence, partially circular.** The agent's workflows were revised against the same opponents it is then ranked against, and the branch-usage figures come from replaying development states. The paper flags both, and the observed rating changes are explicitly not attributable to individual edits.
- **The evaluation is a game, not a task suite.** Bargaining, Negotiation and Persuasion are economic games with clean, API-provided state and legal-action metadata. There is no evidence about repository engineering, browser automation, tool use in the wild, or any environment where the workflow must also *produce* artefacts rather than choose among legal actions.
- **The model-fitted layer is largely dormant in the reported deployments.** With runtime LLM judging off and 0 recorded valid LLM selections in the fixed sample, the deployed agent is essentially a hand-evolved rule-and-numeric code base. Appendix A.3 states that the serialized accept and continuation tables share no segment, so the fitted offer path returns its rule fallback. "Most final-decision procedures are implemented in code" is therefore accurate but should not be read as "the method's model-fitting component was demonstrated in play".
- **Two different evolution mechanisms are shipped.** The paper describes a GPT-5.5 agent performing semantic revisions through OpenProgram across 725 iterations, while the released `scripts/evolve.py` implements a separate single-numeric-knob mutation loop that keeps a change only if the family rating rose, over batches of about 24 games by default. Which of the two produced the reported artefacts is not documented in the inspected files.
- **Rating-based retention is a fragile signal.** The repository's own optimisation loop keeps a mutation on the basis of a rating delta measured over a small batch; `WORKFLOW.md` itself warns that a per-game tick is opponent-strength adjusted and that "latest 20/50 views are operational diagnostics only and never authorize a mid-batch code change". A retention rule driven by rating at that sample size is exposed to noise, which is presumably why the paper's protocol leans on replay, holdout and regression tests instead.
- **The public-vs-local repository split is unresolved.** The arXiv abstract links `Applied-Machine-Learning-Lab/NeurIPS2026_SeaFlow`, which is the repository inspected here, while the README's quick start clones `fzkuji2026/SeaFlow.git`. Which is canonical was not determined from the inspected material, and no code from either was executed.
- **No independent replication.** Nothing here has been reproduced by a third party, and the released package explicitly cannot regenerate the historical export end to end without the non-redistributable raw logs.

## Competing approaches

Only approaches the paper itself compares against or cites as related.

**Workflow representations.** DSPy composes declarative model-call modules; SEW connects role-based agents whose tasks are specified by prompts; AFlow writes model calls and operators as code; HyEvo combines language model and code nodes; LLM-as-Code keeps control flow in code and calls models only for reasoning. The paper's differentiation is that these designs organise a workflow around interfaces and roles, leaving the situation each step serves implicit, whereas SeaFlow names the situations as explicit conditions and attaches a procedure to each one. The related-work section cites the authors' own LLM-as-Code (arXiv:2606.15874) and HyEvo (arXiv:2603.19639) explicitly, as well as Tandem (Fu et al., ACL 2026 Findings) on pairing large and small models for efficient reasoning.

**Self-evolving agents.** TRACE updates program components from execution traces and feedback; ADAS generates programs from an archive of evaluated agents; LLEGO guides tree crossover and mutation with semantic priors; EvoSkillRec evolves recommender architectures by recombining validated skills; Co-π-tree revises problematic branches; Trace2Policy patches rules from grouped errors; HexMachina refines policies through simulation. The paper's differentiation is that these generate or revise programs while the situations each part handles remain implicit, whereas SeaFlow names the situations and revises their boundaries, so a revision can split or merge the game situations one subtask handles.

**Environment.** GLEE (Shapira et al., 2024) is the benchmark and the competition. The paper's Appendix F states the compliance position: GLEE permits hand-coded heuristics and agent-code updates; the workflow uses only API-provided game state, visible history and legal-action metadata; and it does not automate the Human Track, select actions through live human intervention, coordinate accounts or exploit undocumented game behaviour.

**Self-evolution infrastructure.** The workflow revisions are performed through OpenProgram (https://github.com/fzkuji-neo/OpenProgram), the authors' open-source agentic programming environment, in which the program governs all control flow and calls the model only where a task needs reasoning — the same principle the workflows follow.

Within this knowledge base, the closest relative is [[projects/skillcompiler]], which also moves stable behaviour out of the model and into validated programs but gates the promotion of an operation with explicit executability criteria and an asset bank, whereas SeaFlow's unit of decomposition is the *situation* rather than the operation, and its refinement signal is game records rather than skill-level execution traces. [[projects/agentos]] is a useful contrast only: durable task execution and checkpoint recovery are not the contribution here. These are analyst-level **compares_with** links, not dependency claims. See also [[evaluations/briefing-synthesis-2026-11-03-to-09]].

## Implications

The following is analysis by the KB maintainers, not a claim of the authors.

The most transferable engineering idea is that the *situation* is the right unit of decomposition for an agentic workflow, and that naming situations explicitly is what makes the workflow editable at all. The repository's classifier is the concrete form: eleven named regimes, each with explicit thresholds, each mapped to a procedure, each labelled in the trace so that a decision can be traced to the branch that produced it. A workflow whose steps are named only by the interface they use — "call the model", "call the tool" — can be *measured* but not *revised*, because the revision has nothing to attach to. Adding a regime to a classifier is a far smaller and more reviewable change than adding a branch to a nested prompt, and it is the difference between a change that can be regression-tested and one that cannot. This is the [[concepts/structural-constraint-over-instruction]] idea in a different guise: the applicability condition *is* the constraint.

Second, the separation of "the thing that decides" from "the thing that improves the decider" is what makes the whole scheme auditable. Because the workflow is fixed during an interaction, a single decision can be replayed exactly; because the improver works between interactions, its edits can be compared against the traces that motivated them. The paper's case studies exploit this — a revision at position 236 that turns an opponent *category* into an *observed state*, with a check-in regression expectation that a repeated 45.2% self-share is accepted while a 48% variant still rejects, and a later rollback at position 291 of a mirroring branch that was added at 289. A workflow that was being rewritten live while it was playing could not produce that evidence.

Third, the shipped evidence gate is the most immediately reusable artefact for anyone building this themselves, and its shape matters more than its constants. The gate requires, in order: enough effective games and both outcomes present; the same feature set improving the metric in chronological holdout; the proposed policy improving normalized payoff on train and holdout; no material regression in the nearest sibling cell; model support for the candidate action; and a predicted advantage above a stored uncertainty guard — with a deterministic fallback at every level and no global-model action fallback at all. That is a shape that could be transplanted almost verbatim: a fitted estimate may change an estimate, but it may not silently change the objective or the legal candidate space. Combined with the fixed six-level parent order, it is a concrete answer to the failure mode that an over-broad applicability condition routes work to the wrong procedure.

Fourth, the paper's own honesty is instructive for evaluation design: it states that the rating curve does not isolate the effect of any single change, that the counts measure code change and not rating effect, and that commit messages do not prove the described validation ran. A benchmark or report that quietly converts "the rating went up over 725 iterations" into "the method works" is making exactly the inference this paper refuses. The reviewable unit here is the individual revision with its regression test, not the trajectory.

Fifth, the gap between the paper's method and the repository's shipped evolution loop deserves attention from anyone adopting this. The paper describes semantic decomposition refined by a coding agent with a large model; the repository ships a numeric-knob mutation loop that keeps changes on a rating delta. Both are legitimate, but they have very different evidence requirements: the first is reviewed as a code change against named replays, the second is accepted on a noisy batch statistic. If a team adopts the first pattern, they should keep the second's simplicity out of the retention decision.

Finally, the fixed-workflow numbers set a realistic expectation for anyone planning a similar system: the model, when used at all, contributed almost nothing measurable in the reported deployments — 233 valid selections across 57,179 actions and 10 that changed the action. The practical lesson is not that models are useless in loops, but that in a loop where the state is rich, the legal actions are enumerable and the value of an action is computable, the model's contribution shrinks to a narrow ambiguity band, and the engineering effort belongs in the conditions, the fallbacks and the traces rather than in the model call.

## Reproducible experiment

No code from the repository was run, cloned or executed by the KB maintainers, and no result above was reproduced. The paper states that the research package is not yet a public reproduction artifact, so a check means reimplementation from the method and appendices, or use of the public GLEE competition with the authors' own tooling if a key is available. A feasible independent test of the paper's central, admittedly untested claim:

1. **The counterfactual the paper asks for.** Play the same GLEE environment set with (A) the evolved workflow, (B) the same workflow with every fitted cell removed and the deterministic fallback forced at every parent level, and (C) a baseline that calls a model at every decision. Pass criterion: if the fitted and decomposed workflow does not beat (B) on rating or on an outcome metric the platform exposes, the paper's central claim — that decomposition into applicability-conditioned procedures is what produces the performance — is not supported, whatever the leaderboard says. The paper states that such controlled comparisons are needed; this is that comparison.
2. **The applicability-condition test.** Take one condition in the classifier and deliberately widen it, so that states it should not handle are routed to it, and measure three things separately: task success, the rate of wrong-procedure selections, and the rate of unnecessary model invocations. The paper's own risk framing — an over-broad condition routes a task to inappropriate deterministic code, an over-narrow one increases fallback calls and erases efficiency gains — predicts a U-shaped curve. Also test the reverse ablation, tightening a condition, to check that the two failure modes are distinguishable rather than both showing up as a score drop.
3. **Replay fidelity.** Take recorded decision states, replay them through the final workflow, and check that the executed route, the computed quantities and the recorded branch label agree for every action, and that the recorded outputs satisfy the platform's legal-action schema and budget. The paper reports zero schema or offer-budget violations across 2,344 Bargaining action rows and no branch violations across 63 opening-imitation states; a check that finds schema violations or label mismatches would falsify the inspectability claim on which the whole "every decision is traceable" story rests.
4. **Judgement cost, measured.** Count model calls and non-model calls per action over a fixed batch, with the judge enabled and disabled, and report the change in rating and in wall-clock time per action. The paper's numbers to beat are 0.118–0.198 ms mean local decision time with the judge effectively off, and roughly 233 valid selections changing 10 actions across 57,179 recorded actions. A configuration in which enabling the judge raises per-action latency by orders of magnitude without a measurable rating change would be a directly actionable negative result.
5. **Retention rule robustness.** For a set of single-knob mutations, compute the family rating delta over batches of the size the shipped `scripts/evolve.py` uses (24 games by default) and over larger windows, and compare the keep/rollback decision each window makes against a replay-based validation on the same changes. If the two disagree on a substantial fraction of changes, then rating-based retention at that sample size is unreliable, which is a testable consequence of the paper's and repository's own caveats.

Substituting available models for GPT-5.5 and Grok-4.6 is unavoidable, and the substitutions, the GLEE configuration and any seeding should be reported with the results.
