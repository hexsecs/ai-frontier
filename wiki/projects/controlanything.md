# ControlAnything: On-Demand Device Integration by a Coding Agent

## What it is

ControlAnything is a mixed-reality (MR) system in which a coding agent writes, tests and binds the integration between a wearer's hand input and a nearby physical device at the moment the wearer asks for it. It is reported in the arXiv preprint "ControlAnything: Generative UI and On-Demand Device Integration for Mixed-Reality Hand Interaction by a Coding Agent" (arXiv:2611.08321, submitted 5 November 2026, cs.HC; preprint, no peer-reviewed venue claimed). The paper lists a single author, Bektur Ryskeldiev (Tokyo, Japan), and marks the manuscript "A Preprint". The abstract page states 10 pages, 2 figures and 1 table, and links code and video at https://github.com/Apolotary/controlanything under the MIT license. The acknowledgments state the project was built for the Meta Global AI Developer Hackathon (Indie track), November 2026, and that the work is not affiliated with or endorsed by Meta.

The problem it names is that every connection between hand input and a device requires an integration specific to that device, its transport and the intended mapping, so a developer must write that integration ahead of time. The paper's stated contribution is the combination, in one loop, of selecting a real object in MR, an agent that writes and tests the device connection on demand, and generative UI in MR (AR controls or a per-frame hand program) bound to that connection. The authors state, as an author claim "to our knowledge", that no published system combines these three.

## Mechanism

The system has three parts (paper §4.1). The **headset client** is a three.js WebXR `immersive-ar` application running in Quest Browser. The **server** is a Node program on the wearer's laptop that holds the model keys, the agent and the connector host behind a WebSocket hub. **Executors** on the same laptop perform operations for the three transports and report whether each was accepted: a companion page in Chrome sends Web MIDI, a second Chrome page bridges to the gimbal over Web Bluetooth, and AppleScript System Events presses keys.

**Interaction walkthrough (§3).** The interaction has five steps. *Select:* in Annotate mode SAM 3.1 outlines objects and a pinch on an outline creates the tag and its card; tagging does not start control. *Ask:* in a separate Control mode the card offers "Ask Muse" without a setup step, and the wearer speaks a goal or taps a suggestion chip; a request may name a device reachable from the tagged object, as the OP-1 and gimbal requests did. *Generate and test:* a code card streams the agent's commands and files. *Use:* controls appear, a hand program starts, or both. *Stop:* the wearer stops generation, a running program or everything at once, and a new request on the card replaces the previous connection.

**Design goals (§3).** Four goals are derived from three observations: an integration is specific to a device, its transport and the mapping, so it cannot be prepared for every device a wearer may encounter; code generated at the time of use has not been reviewed, and a wearer occupied in MR cannot be expected to read it; and hand interaction requires a response on every frame, whereas a model call takes seconds. DG1 is integration at the time of use — no device-specific connector, control layout or hand mapping is prepared in advance, although documented general transports such as MIDI may be. DG2 is grounded and checked output — every control and hand-program output binds to an action of a running connector whose main action has been exercised on the live device, and generated code passes automated checks before it reaches the headset. DG3 is no model in the control loop — after generation, hands are mapped to device actions locally on every frame within fixed computational budgets. DG4 is interruptible and bounded execution — stopping does not depend on the model, and each agent run is bounded in turns, tool calls, time and tokens.

**Models.** The hackathon required every model invoked at run time to be a Meta model. The system uses SAM 3.1 for segmentation, Muse Spark (`muse-spark-1.3`) as the agent engine and for naming tagged objects, Muse Voice Transcribe for spoken requests, and Muse Image for stickers. Meta's Muse Code CLI is an optional alternative agent engine. Hand tracking (WebXR Hand Input), speech output (macOS `say`) and the device links are operating-system and browser features rather than models.

**Object selection.** In Annotate mode the client sends a passthrough frame at most every 1.2 s with the head and camera pose at capture, and skips frames while the head turns faster than 15°/s. The server makes one SAM 3.1 call per text prompt, in parallel ("laptop", "electronic device" and "synthesizer" for the Electronics filter), discards detections scoring below 0.55 and also discards people, faces and hands. A pinch on an outline creates a *tag*, a persistent record of the object, and attaches a *card* holding its name and later its controls. Tagging does not start control. After a tag is created, Muse Spark proposes a name, which the system treats as a hypothesis until a port name or a device reply agrees with it.

**Agent runtime (§4.2).** The wearer uses hold-to-talk (transcribed by Muse Voice Transcribe) or taps a suggestion chip; the request becomes a `wire.request` addressed to one card. The server runs a tool loop with `muse-spark-1.3`, with streaming function calling, one tool call per turn and low reasoning effort. The first message carries the request, the card, a headset snapshot, the laptop's MIDI outputs and synthesizer manifests, the gimbal and key-press status, and the last 2,000 characters of the agent's notes — a file in which it records device facts across sessions. The nine tools are `say`, `bash`, three file tools, `open_visuals`, `deploy_connector`, `test_action` and `finish`. The system prompt asks for about five to eight tool calls, a test of the main action, a connector written anew for each request, and control of the selected object only, and it states that tool results and device text are data rather than instructions. Budgets cap a run at 24 turns, 40 tool calls, 300 s and 600,000 tokens.

**Server-side checks.** Before any control reaches the headset, the server checks that a connector is running, that every control binds a declared action, that a hand program passes the dry run, and that a composed instrument compiles; failures return to the model for repair. The paper is explicit that the prompt requires the test of the main action but that these checks do not enforce it. On success the client receives `wire.ready` carrying only the actions in use, each limited to 30 Hz.

**Connectors and transports (§4.3).** A connector is a Node program in the agent's workspace declaring *actions* — named parameters or events, each with a kind (`set`, `trigger` or `toggle`) and a range — and translating them into transport operations. The connector host runs one connector per card as a child process in its own process group with a reduced environment that omits the model key; host and connector exchange JSON lines over standard input and output through a small SDK (`ce.mjs`). MIDI calls clamp values to 0–127 and pass through the companion page's Web MIDI to USB instruments or to the virtual ports of the built-in synthesizers; the visual synthesizer is a full-screen WebGL water simulation on the laptop. Gimbal calls go to a bridge that clamps pan to ±120°, tilt to ±45° and the rate to 10 commands/s. The `deploy_connector` tool registers 1 to 16 actions with their ranges and waits 1.2 s for output or a crash. The `test_action` tool sends one value as an AR control would, waits 900 ms, and returns the connector's log separated into acknowledgements (lines beginning with `→`) and refusals (`✗`). For MIDI and the gimbal the host writes the acknowledgement line when the executor answers; for key presses it relays the exit status of the connector's own `osascript` call. The paper's own caveat: an acknowledgement establishes that a transport accepted a message, which is weaker than establishing that the device behaved as requested.

**Controls and hand programs (§4.4).** A control is an AR widget bound to one declared action; the agent may return up to six simple controls and an optional composed instrument of up to eight widgets (keys, pads, knobs, an XY surface), and the prompt instructs it never to require pinch-and-drag gestures. A hand program is a JavaScript function `wire(s, out, mem)` of at most 4,096 characters that the headset calls on every frame. It reads per-hand signals (height, push and lateral position in a head-relative zone, smoothed with a One Euro filter, plus pinch, fist, palm and speed) and, once a screen has been found, the fingertip's position on the screen and a touch flag; it acts through `out.set` and `out.trigger`. The server rejects forbidden tokens such as imports, timers and `eval`, and runs the program on 480 synthetic frames in an empty `node:vm` context, requiring an average below 2 ms per frame and valid, correctly scaled output. On the headset the program runs in a Web Worker without network, storage or timer APIs, under a 4 ms budget per call, a 50 ms watchdog and a three-strike limit. An output gate passes only the actions in `wire.ready`, clamped to their ranges and limited to 30 Hz. No model is called per hand frame.

For touch on the laptop screen the client estimates the screen's plane from the SAM bounding box and a prior on display size; the paper states the estimate can be off by more than 10 cm. Screen signals remain null until a fingertip approaches the estimated plane and rests near it; the plane is then moved along the line of sight to pass through that fingertip.

**Safety and stopping (§4.5).** The `bash` tool passes through a deny-list of 20 regular expressions (covering `sudo`, any `kill`, the server's ports, credential files, `git push` and others), and the file tools write only inside the workspace; connectors themselves are not sandboxed. Stopping does not depend on the model: the host sends `stop` to the connector, queues neutral releases (MIDI panic, sustain off, touched controllers set to zero, gimbal stop) and sends SIGTERM to the process group at 250 ms and SIGKILL at 600 ms; for 1.7 s afterwards only neutral releases from the retired connector pass. The wearer can stop generation on the card, stop a running program by holding both palms out for 400 ms, or stop everything from the wrist menu, and a new request on the card retires the previous connector.

**Pose recording (§4.6).** Any session can be saved as a *take*: a JSON-lines file beginning with approximate camera intrinsics and tracking metadata and continuing with head and 25-joint hand poses at 30 Hz, the protocol messages and input events, all timed from the start of the take. A hand that loses tracking is recorded as `null`, never as its last known pose. The Quest's system recording supplies the video, and a review page plays video and poses on one timeline and exports the take.

## Evidence

All numbers in this section are **author-reported** from the single preprint; none has been independently replicated.

**Setup.** A technical evaluation of one session on a Meta Quest 3 in Quest Browser, with the server on a MacBook. The targets were the built-in visual synthesizer, Instagram Reels in Chrome, the laptop itself, an OP-1 Field synthesizer connected over USB-MIDI, and a DJI Osmo Mobile 4 gimbal reached over Bluetooth through the Chrome bridge. One session was recorded on 5 November 2026 (06:21–07:07 JST) with the author as the only wearer. Ten requests (R1–R10) were phrased freely rather than drawn from a fixed task set; eight were spoken and two used a suggestion chip. The server was restarted once, between R8 and R9. All ten requests addressed the laptop's tag, which had been created and named two days earlier, so the session contains no tagging or naming call; the wearer named the OP-1 and the gimbal in the request text, so pinch selection of those devices was not exercised. The agent's notes, which persist across sessions, already contained the OP-1's port name, its filter controller numbers and how to move the gimbal, and R3 added the Reels keys. The paper states that several requests re-ask an earlier goal (R2/R3, R4/R5, R1/R9), so the requests are not independent trials.

**Per-request record (Table 1).** Time to ready is the interval from the start of the server's handling of a `wire.request` to the corresponding `wire.ready`, excluding speech transcription, which took 1.2–3.4 s.

| Run | Request (paraphrased) | Target | Via | Returned | Ready (s) | Calls |
|---|---|---|---|---|---|---|
| R1 | Touch the visual synth with a finger | Visual synth | voice | hand program | 31.6 | 9 |
| R2 | Scroll Reels by touch in the browser | Reels in Chrome | voice | hand program | 57.8 | 8 |
| R3 | Scroll Reels with gestures | Reels in Chrome | voice | hand program + 3 controls | 54.5 | 9 |
| R4 | Knobs for the OP-1 filter | OP-1 Field | voice | 2 controls | 24.9 | 7 |
| R5 | Control the OP-1 Field with fingers | OP-1 Field | voice | hand program | 36.7 | 7 |
| R6 | "Give me knobs for this" | Laptop | chip | stopped by the wearer at 18.5 s | n/a | 2 |
| R7 | Connect the gimbal to my fingers | Osmo Mobile 4 | voice | hand program + 4 controls | 30.0 | 6 |
| R8 | Controls for the water visualization | Visual synth | voice | 4 controls | 46.7 | 12 |
| R9 | Control the water with fingers | Visual synth | voice | hand program | 32.5 | 6 |
| R10 | "Give me knobs for this" | Laptop | chip | 4 controls | 25.9 | 7 |

**Outcomes.** Nine of the ten requests reached a ready state and none failed; the wearer stopped R6 after 18.5 s and the log does not record the reason. Six runs returned a hand program and five returned controls, two of them both. The connectors were 15 to 42 lines long. All three transports were exercised. R10's controls set the laptop's volume, scrolling, playback and mute; its connector made the volume calls through AppleScript directly, outside the three transports.

**Where the time goes.** Time to ready had a median of 32.5 s (mean 37.8 s, range 24.9–57.8 s, n=9). The ten runs used 73 model calls, with a median per-call latency of 3.48 s and a 90th percentile of 8.88 s. Model calls accounted for a median of 89.9% of each run's time to ready (range 82.5–96.2%); the remaining time had a median of 3.0 s (range 2.1–5.5 s). In R9 and R10, where per-call start and end times were available, that remaining time consisted almost entirely of fixed waits — about 1.2 s after `deploy_connector` and 0.9 s after each `test_action` — while the other tools took 1–6 ms. Of 656,844 input tokens, 91.7% were served from the prompt cache; from R2 onward every run reused a 5,489-token prefix consisting of the system prompt and the tool schemas. A repeated request cost as much as the first, because every connector is written anew: R1 and R9, both requests to touch the water simulation, took 31.6 s and 32.5 s.

**What "ready" means.** A run counts as ready when the server's checks pass and `wire.ready` is emitted: a connector is running, every control binds a declared action, a hand program has passed the dry run, and a composed instrument compiles. The paper notes that the prompt requires the test of the main action but that the checks do not enforce it, so "ready" is a statement about binding and code validity, not about a verified device effect.

**Evidence of effect.** The system's evidence of effect consists of acknowledgements. The gimbal bridge logged 889 rotate answers from the Osmo Mobile 4, all with status `00` (ok); of these, 881 came from the agent's code (2 from `test_action`, 879 while the wearer steered) and 8 from stop and release commands. At the bridge's limit of 10 commands/s, 879 moves imply at least 87.9 s of steering. An answer indicates that the gimbal accepted a command; the logs contain no reliable angle. The author observed the ripples, the scrolling, the OP-1's sound and the gimbal's motion, which appear in the accompanying video, but the system measured none of these effects.

**Pose recording and other model calls.** The take covered R9 and R10. It lasted 111.6 s, contained 3,247 pose frames at a mean of 30.01 Hz, and ended when it reached the 24 MiB cap. The left hand was untracked in 3.2% of frames and the right hand in 2.6%, including one interval of about 2.8 s in which both were lost. SAM 3.1 answered 336 prompt calls with a median latency of 0.83 s, and 40% of the calls returned no object.

**Explicitly not measured** (§5.1). The paper lists what the evaluation did not measure: headset frame time, the latency from hand movement to device response, the physical effect of any command, the error of the screen-plane estimate, and the detection accuracy of SAM 3.1.

## Limitations

**Stated by the authors.** The evaluation has one wearer (the author), one session, one laptop and one tag; the requests are not independent trials; pinch selection of the OP-1 and the gimbal was not exercised; and a request addresses one card, so rules spanning several devices are out of reach. Apart from R10's volume calls, every target was reached through the three hand-written transports, so the evaluation does not show that the agent can integrate a device that has no transport. This is a technical evaluation rather than a user study, so the paper makes no claims about learnability, comfort, ease of use or naturalness, and a study with first-time wearers is planned. Accessibility was not evaluated; the design relies on two tracked hands for the palms-out stop, the left hand for the wrist menu, fine pinches and intelligible speech. On safety, the paper states that connectors are ordinary Node processes with the laptop user's permissions and are not sandboxed, that the deny-list does not inspect their code, that a connector is arbitrary Node and can bypass the SDK's limits, and that prompt injection through camera-visible text or device output is handled by a prompt rule alone — so runtime-generated device code needs operating-system containment before use outside a controlled setting. On the effect gap, the agent's notes from the day before the session record OP-1 MIDI messages that were acknowledged while the instrument remained silent, until its MIDI receive setting was turned on, and the paper notes that because `test_action` classifies log lines by their first character, a connector could itself print an acknowledgement.

**Assessed from the reporting.**

- **Single source, no artifact inspected.** Everything rests on one arXiv preprint (v1, 5 November 2026) by a single author. The paper links a code and video repository, but that repository was not fetched or read for this page, and no independent party has rerun the session.
- **The evidence stops one level short of the claim.** "Ready" means the server's binding and dry-run checks passed; the only measured effect is a transport acknowledgement. Nine of ten ready states therefore establish connector readiness, not physical actuation, safety, persistence or permission isolation.
- **n = 1, one wearer, no statistics.** There is no confidence interval, no second session and no second wearer; the 32.5 s median and the 89.9% model-call share come from nine and ten observations respectively.
- **The protocol is favourable by construction.** Every target was reachable through one of three transports that the authors wrote by hand and documented in the prompt, and the agent's cross-session notes already contained the OP-1's port name, filter controller numbers and gimbal procedure. The reported readiness times are therefore times for an integration the authors had already prepared, not for an unknown device.
- **Non-independent requests.** R1/R9, R2/R3 and R4/R5 re-ask earlier goals, and the paper says so; the ten rows are not ten independent trials of the mechanism.
- **The prompt, not the checks, carries the load.** The server enforces binding, dry-run and compilation, but the central "test the main action" obligation is a prompt instruction, which is exactly the kind of guarantee the agent may satisfy by printing its own acknowledgement line.

## Competing approaches

Only approaches the paper itself compares against or cites as related.

**Spatial interfaces for physical devices.** The Reality Editor reprograms instrumented objects through a handheld AR view; Snap-To-It opens an appliance's control panel from a photograph; Scenariot maps smart things within AR scenes; the Personal Universal Controller (PUC) generates remote-control interfaces from appliance specifications; XR-Objects segments real objects and attaches menus powered by multimodal LLMs; Khelifi and Morris place LLM agents that control IoT devices in MR smart spaces; VisionClaw delegates smart-glasses tasks including IoT control through existing agent skills. Closest to the generated controls, LORIOT and JUIC-IoT use an LLM to assemble spatially registered AR control panels from device metadata or W3C Thing Descriptions. The paper's differentiation: all of these reach devices through integrations prepared in advance, whereas ControlAnything writes the integration after selection.

**From trigger-action rules to LLM-written device integrations.** Trigger-action programming (IFTTT) made device automation accessible within services a platform already integrates; Tell-XR builds XR smart-home rules through conversation with end users; LLMind and AutoIOT synthesize control scripts and AIoT programs; AutoEmbed develops embedded firmware with hardware in the loop. The paper calls **AutoBridge** the closest system on the code side: it generates smart-home integrations for new devices, debugs them against virtual devices, then drives the real device while a human answers yes/no questions about the outcome. The paper's contrast is that ControlAnything runs its loop when the wearer asks and its evidence is weaker than a human observer's.

**Coding agents and generative UI.** ReAct, Code as Policies for robot control, Voyager, SWE-agent and Self-Debugging for tool-and-code agents; AppAgent for third-party applications. On generative UI, the paper cites SUPPLE and the PUC for specification-derived interfaces before LLMs, Google's Generative UI report, generative and malleable task-driven interfaces, LLMR's self-debugging MR scenes, agentAR, and Vibe Coding XR. ControlAnything's difference is that its generated interface controls a physical device, so it tests the device connection live and binds every widget to an action its connector declared. In the hands-as-data section it compares itself with GestureGPT (grounding free-form gestures with LLM agents, with a model interpreting each gesture) and Auto-HSI (generating gesture-to-behavior state machines for robot swarms), noting that ControlAnything generates the mapping as code so that no model runs per frame, and it cites the 1 € filter for signal smoothing and Wessel and Wright for musical-control latency.

## Implications

The following is analysis by the KB maintainers, not a claim of the authors.

The most transferable engineering idea is the separation of three trust levels that a mixed-reality agent loop must keep apart: *the interface was generated*, *the binding was checked*, and *the device did the thing*. The paper's architecture makes the first two mechanically checkable — every widget must bind a declared action of a running connector, and a hand program must survive a 480-frame dry run under a 2 ms average budget — while the third remains invisible. Any system in this shape should treat its acknowledgement log as a necessary but weak signal, and should be designed so that a cheap independent observer (a camera, a microphone, a device query) can upgrade the evidence when it matters. This is the concrete instance of [[concepts/verified-completion-vs-apparent-success]] in this page's domain, and it is the same boundary that [[concepts/scoped-assurance]] asks to be stated explicitly: the assurance obtained is transport-level, and it should be labelled as such.

Second, the latency profile is a useful design constraint in its own right. With roughly 90% of a 32.5 s setup inside sequential model calls and only about 3 s of actual waiting on tools, the system is model-bound, not transport-bound: a repeated request costs as much as the first because the prompt requires a fresh connector each time. Teams expecting to reuse generated integrations should expect that reuse to be the single largest latency lever, and should notice that the paper treats reuse as future work rather than as a measured result.

Third, the safety asymmetry in the paper is instructive and generalizable. The code that runs on the headset is confined — token blocklist, empty `node:vm` dry run, a Web Worker with no network, storage or timer APIs, a 4 ms budget, a watchdog and a three-strike limit — while the code that runs on the laptop to talk to the device is an ordinary unsandboxed Node process with the user's permissions. That is exactly backwards from a risk standpoint, since the laptop-side connector is the one that can reach keyboards, files and credentials. The paper says so plainly; the transferable point is to budget containment effort by what a component can reach, not by how small or how new its code is.

Fourth, the "data not instructions" prompt rule is the only defence the paper offers against camera-visible or device-returned prompt injection, and a prompt rule is a weak control. Combined with the stated observation that `test_action` classifies log lines by their first character — so a connector can manufacture its own acknowledgement — the episode demonstrates that a self-reported test result is not evidence, which is the same lesson [[projects/receipt]] draws from the opposite direction.

Fifth, the paper's own numbers separate the latency floor from the model cost. Only about 3.0 s of a 32.5 s median setup was non-model time, and within that, roughly 1.2 s is the fixed `deploy_connector` wait and 0.9 s the fixed `test_action` wait, while every other tool takes 1–6 ms. The tool plumbing is therefore effectively free; a deployment that needs a faster path to a usable control should attack the number of sequential model calls, not the transport. That also means the two waits are a design target in their own right: a system that could overlap the deploy wait with generation, or replace the fixed `test_action` timeout with a completion signal, would remove roughly two seconds per request without touching the model budget.

Within this knowledge base the closest relatives are [[projects/skillcompiler]] and [[projects/seaflow]], which both move stable behaviour out of the model and into code; ControlAnything's distinctive move is to place the generation inside a latency-sensitive, physical, safety-relevant loop where the code is unreviewed, the wearer is occupied, and the only cheap feedback is a transport-level ack. Two further relationships are analyst-level rather than author-endorsed: a generated interface for a physical device raises the same class of question as other [[domains/computer-and-device-use]] work and as [[projects/cua-agentenv]], and the design move of making the *constraint* (a declared action, a bound, a checked binding) carry the safety burden rather than a prompt is the [[concepts/structural-constraint-over-instruction]] pattern in this setting. The questions this page raises about what may be claimed and what must not be quietly discarded when a workflow improves are tracked in [[concepts/preservation-aware-agent-improvement]], and the page contributes to [[evaluations/briefing-synthesis-2026-11-03-to-09]]. These links are evidence-guided conceptual comparisons, not assertions that the projects cite, implement or depend on each other.

## Reproducible experiment

No claim here was executed by the KB maintainers. A feasible independent check of the paper's central gap is an *effect-verification* experiment, since the paper itself names that gap as the main open problem.

1. **Instrumented transport suite with an independent effect witness.** Build 10–20 connectors over the three transports the paper uses (MIDI, Bluetooth bridge, key press) against devices whose state can be read back independently of the transport — a MIDI synth whose parameter value can be polled, a browser page whose DOM can be read, a system whose volume can be queried. For each request, record three things separately: the transport acknowledgement, the device state read back independently, and the wearer's subjective report. Pass criterion: the acknowledgement rate should be high (the paper's runs are all acknowledged) while the independently verified effect rate should be materially lower; a system in which acknowledgements predict verified effects at ~100% would falsify the paper's "acknowledgement is not effect" claim on your device mix.
2. **Reproduce the acknowledgement-to-silence case.** Deliberately construct the failure the paper's notes record: a device that is connected but silent (MIDI receive disabled, muted output). Check whether the agent still reports the action as ready and whether the acknowledgement appears. The paper's claim is that it does; a system that detects the silence would be a stronger design than the paper's.
3. **Latency and reuse.** Run the same request twice with the same device and measure time to ready both times. The paper's numbers are 31.6 s and 32.5 s for two requests to the same target because every connector is written anew. A reuse-permitting implementation should show a large drop; if it does not, the connector-writing cost dominates and the latency budget cannot be met by caching alone.
4. **The stop path.** With the agent mid-generation and a live connector running, exercise all three stop routes (card, palms-out for 400 ms, wrist menu) and verify from the device side that the neutral-release queue (MIDI panic, sustain off, gimbal stop) and the SIGTERM/SIGKILL escalation at 250 ms and 600 ms leave the device in a safe state, with no command other than neutral releases passing during the 1.7 s window. The paper describes this mechanism but reports no test of it; this is the cheapest safety claim to check.
5. **Frame-budget check.** Run the dry-run harness on your own hand programs: 480 synthetic frames, average below 2 ms per frame, then the headset-side 4 ms budget and 50 ms watchdog. Any hand program that passes locally but breaches the budget in the headset would be a per-frame latency failure invisible to the paper's reported metrics.

Substituting the paper's 2026 Meta models with available ones is unavoidable; the substitution and any device differences should be reported with the results.
