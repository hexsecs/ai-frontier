# tigerless agent-memory

## What it is

agent-memory is Tigerless's long-term memory runtime for AI agents: a local-first store in which **Markdown files are the single source of truth**, a SQLite FTS5 index beside them that is a rebuildable cache, deterministic writes triggered at conversation boundaries, and a separate sleep-time **Manage** layer that consolidates and forgets on its own clock. The README's framing is that Claude Code, Codex CLI, Muse Code, Hermes and anything else that can run a shell command share one store.

Version and maturity evidence, fetched on 2026-11-10 from the GitHub API and the repository files: MIT licence, Python 3.12+, `pyproject.toml` version `0.1.0` with a `uv` workspace of six packages (`core`, `cli`, `adapters`, `mcp`, `executor`, `harness`). The repository was created 2026-09-01 and pushed to on 2026-11-10; it has 4,311 stars and 206 forks. **There is no GitHub release and no git tag**, and the README states plainly that "There is no release on PyPI yet, so install from a checkout" — `uv sync --all-packages` builds `mem`, `mem-mcp` and `mem-hook` into `.venv/bin`. The README badge says the same version `0.1.0`. So this is a pre-1.0 project with no published artifact, and the numbers it reports are therefore not independently checkable against a fixed release.

The project is maintained by tigerless-labs. `CLAUDE.md` states the wedge as a competitive claim: "the only memory system with a true independent Manage layer (value-based forgetting, sleep-time consolidation with authority tiers) on top of file truth — every competitor either has no M, or buries it in the write path." That is the vendor's own framing and is not established by the repository.

The previous revision of this page was a canonical backfill of the 2026-11-05 briefing's assessment rather than an independent source review. This revision is a repository-grounded re-read: the mechanisms below are inspected from the source, and the benchmark figures in the "Evidence" section are explicitly separated as README claims.

## Mechanism

**The store layout.** The README specifies one directory, `$AGENT_MEMORY_STORE` (default `~/agent-memory-store`), containing `MEMORY.md` (the root index, "the only resident injection"), `config.toml` ("every tunable; an unknown knob is refused at load"), `schemas/` (one file per type: key fields, the field it groups by, write mode), `decision/` (memories at `<type>/<group>/<name>.md`, placed by the schema), `archive/` (append-only, with `provenance/` for distillation evidence and `sessions/` for full trace copies), `dream-reports/` (one per sleep), `.index/` (content-hash manifest, FTS5, access log) and `.state/` (distillation watermark, write lock).

**How a memory is stored.** One memory is one file. `packages/core/src/agent_memory/core/store.py` is headed "The single write path (Invariant 2). Every adapter, and Manage itself, enters here. A write names a type and fills that type's fields; the store derives the path (ADR-008), decides update versus replacement (ADR-009), and reprojects. Nothing here deletes a file." A memory carries `valid_from` and an optional `invalid_at` defining its validity interval; replaced and deleted files stay in the store so `recall --as-of` can answer as of a date. Frontmatter carries the stable name, a one-sentence abstract, the type and its schema fields, timestamps, links, weight and provenance; the body is free markdown. `docs/design/management-operation-boundaries.md` states the file-level rule directly: "One file holds knowledge that expires as a whole… a file is active or invalid, nothing in between, and invalidation comes only from replacement or deletion."

**How memories are retrieved.** `packages/core/src/agent_memory/core/recall.py` is headed "Eligibility before relevance, then relevance × weight × recency. Zero LLM (ADR-002)." The pipeline is: match candidates in the FTS5 index on the **active** surface (`SURFACE_ACTIVE`), filter them by eligibility (scope prefix on the path, validity interval at the requested `--as-of` moment), rank them, and return hits. Ranking is `score = relevance × weight × recency`, with relevance drawn from the BM25 candidate (`search_index.py`: "BM25 over abstract + body (ADR-003). Projection only: never a source of truth"), weight from the record's frontmatter, and recency a decay `recency_decay_base ^ (age_days / recency_half_life_days)` floored at `recency_floor`. Body-level and abstract-level candidates are weighted differently by `bm25_body_weight` / `bm25_abstract_weight`. An optional dense index is fused by **reciprocal-rank fusion** with `RRF_K = 60` over chunk identity `(name, kind, anchor, heading)`.

Recall answers with paths, not pasted text: an L0 list of one-line abstract, file path, anchor and score, which the agent opens to the depth the task needs. `packages/core/src/agent_memory/core/context.py` offers the same retrieval as one call — it runs the recall, opens the top `context_full_text_entries` entries to full text and returns a context block — and its docstring explains why: "an agent driving its own retrieval swings the same store's answers by seven per hundred between identical replays, and scores well below the same store read on a fixed policy". `packages/core/src/agent_memory/core/injection.py` implements the third read track, the deterministic `MEMORY.md` byte-prefix injected at session start, which "costs no tool call and cannot miss". The README names three tracks in total: deterministic `MEMORY.md` injection, BM25 over FTS5 (with the optional vector plugin fused by RRF), and the plain directory tree reachable with `ls` and `grep`.

**How memories are written.** Writes are triggered by the host at conversation boundaries — SessionStart injects, Stop and SessionEnd distil, PreCompact evicts — rather than left to the agent's judgement. `packages/core/src/agent_memory/core/distill.py` is headed "One boundary, end to end: batch, render, reconcile, ask, apply, repair, advance. The asking is a callable — text in, text out — supplied from outside the core (Invariant 5). Everything around it is deterministic." So the core never calls a model; the executor does, either by borrowing the host agent's own CLI or by talking to a user-supplied endpoint.

The reasoner runs as a **tool-use agent over one toolkit**. `docs/design/write-negotiation.md` defines the toolkit: `recall` (search current memory, list matches by handle), `read` (open one active memory in full) and `submit operations`. The design is explicit that the toolkit "imposes no look budget or forced final turn", that a handle becomes nameable only once the reconcile sheet or a tool result has shown it, and that "Tools never write the Store: accepted operations reach it through the single write path". A run that ends without an accepted submission "writes nothing and leaves the archive backlog and Watermark untouched". The README adds that the full trace is copied first, so "missed by the distiller" never means "lost by the system".

**How memories are evaluated and consolidated.** The **Manage** layer is the piece the project distinguishes itself on. `packages/core/src/agent_memory/core/manage.py` is headed "Sleep-time consolidation, value-based forgetting, tree evolution. The layer everything else exists to make possible." A sleep is two halves. The deterministic half runs first and is rule-only: `_normalise_dates`, `_settle_weights` (from usage), `_add_cooccurrence_links`, `_merge_exact_duplicates`, `_merge_near_duplicate_groups` and `_cluster` — recorded as actions with names such as `date-normalised`, `weight-settled`, `link-added`, `duplicate-merged`, `clustered`. The judged half then drafts **proposals** of five kinds (`merge`, `supersede`, `split`, `delete`, `abstract-review`), sends them to a reasoner, and applies the accepted ones through `decide()`. The reasoner "can only choose from the menu the core drafted, is capped per kind per sleep, and never removes a file"; accepted counts are bounded by `_caps()` (`max_merges_per_sleep`, `max_supersedes_per_sleep`, `max_splits_per_sleep`, `max_deletes_per_sleep`), a proposal whose source changed during review is withheld, and every sleep leaves a dream report and — "when the store lives in a repository" — a git commit.

The authority split is described in `CLAUDE.md` invariant 6: "Manage never destroys information. Every Manage operation is reversible: T0 is rule-only (dates, weight, links, directories), T1 is decided by the library executor and only creates new files or marks old ones invalid, each kind capped per sleep, one git commit per sleep. Physical removal is a human-run command that Manage cannot reach." The README phrases the same rule as authority tiers: "an unattended pass may add and update, deletion only ever arrives as a proposal you confirm" — and `mem proposals` / `mem decide <id> --accept` are the human side of that.

The reasoner's reply is a **grammar, not a conversation**: `packages/core/src/agent_memory/core/reasoning.py` states that "Anything that does not parse as a verdict on an open proposal is discarded, so a reasoner that rambles, hallucinates an identifier, or is steered by something written inside a memory can only ever fail to decide — never decide something that was not on the table." The experimental native-tool path is narrower still: `packages/core/src/agent_memory/core/manage_toolkit.py` exposes exactly three run-scoped tools (`list_proposals`, `read_evidence`, `submit_verdicts`) with the docstring "Run-scoped tools for reviewing Manage proposals without mutation authority."

**Why there is no LLM client in the core.** Invariant 5 in `CLAUDE.md`: the core contains no LLM client, and judgement "lives in the executor package, which reasons through the host's own CLI by default, or an explicitly configured, user-owned model endpoint". `packages/executor/src/agent_memory/executor/reasoners.py` states the two options and their failure modes: a host reasoner "spends the agent the user is already running: no key, no second bill, and the reasoning shows up in that agent's own transcript"; an endpoint reasoner "answers on a cron at three in the morning when no agent session exists, at the cost of a credential and a network hop". The README says the same in the header badge: "dependencies: zero API keys". The hosts module names four dialects — `claude-code`, `codex`, `hermes`, `muse-code` — with default models `claude-haiku-4-5-20251001` for Claude Code and `gpt-5.6-sol` for Codex, and it holds each dialect to disabling that host's own memory layer, because "two memory systems in one run make the score unattributable".

**Provenance and raw evidence.** Every memory carries provenance pointers into archived session messages, and `mem --json trace <name> --pointer 'sessions/<session>#<start>-<end>'` opens a cited raw range; `docs/design/raw-evidence-reads.md` draws the boundary between an explicit provenance read and the default retrieval policy. The README states the standing caveat plainly: "Returned role and message time are archived metadata, not proof that a fact is true, confirmed, or effective at that time."

**Config and interfaces.** `config.toml` holds every knob, split into `[executor]`, `[executor.write]`, `[executor.manage]`, `[manage]` and `[index]` tables; the README documents `reasoner = "host" | "endpoint" | "none"`, `host`, `host_provider`, `tool_mode = "auto" | "native" | "text"`, `timeout_seconds`, `manage.review_raw_session_evidence`, `manage.auto_dream` and `manage.claim_lease_seconds`. The CLI is the universal surface (`mem recall`, `read`, `context`, `trace`, `record`, `correct`, `supersede`, `merge`, `delete`, `sleep`, `proposals`, `decide`, `jobs`, `cron`, `setup`, `doctor`, `rebuild`); the optional MCP server exposes `memory_recall`, `memory_read`, `memory_trace`, `memory_record`, `memory_correct`, `memory_supersede`, `memory_merge`, `memory_delete` and `memory_feedback`. The README notes the asymmetry: "Anything that can run a shell command needs neither: the CLI is the universal fallback, and it is the wider surface — `context`, `sleep`, and the proposal ledger have no MCP tool yet."

**Durability of writes.** A boundary distillation is a durable job: the hook enqueues it, a worker runs exactly it, and a crash is recovered from the queue by the next lifecycle event. `mem jobs list/show/retry/cancel/gc` and `mem distill --drain` are the surfaces; each run appends a JSONL trace with transport, batches, rounds, tool-call digests, applied and rejected operations and usage, with bodies redacted unless `write.jobs.trace_bodies` is set.

## Evidence

**Code-inspected.** The store, recall, distill, manage, reasoning, context, injection, indexer and search-index modules; the write and manage toolkits; the executor's reasoner and host drivers; the harness's arms, exam, judge, interop and systems modules; `CLAUDE.md`; the design docs under `docs/design/`; the CI workflow; and the red-team test file were read as source. The behaviours described in "Mechanism" — the write path, the eligibility-before-relevance order, the score formula, the per-kind caps, the verdict grammar, the three-tool Manage boundary — are established by that source.

**Tests and CI.** The repository contains 268 tracked files, of which 126 are Python test files under `tests/` (95 unit, 27 system, 3 red-team). `.github/workflows/ci.yml` runs on `ubuntu-latest` and `windows-latest` and executes `ruff check .`, `mypy`, and `pytest -q --cov=agent_memory --cov-report=term-missing --cov-fail-under=85` — an 85% coverage floor as a hard gate. `pyproject.toml` registers `stress` and `redteam` pytest markers. `tests/unit/test_indexer.py` includes `test_rebuild_after_deleting_the_index_returns_the_same_recall_set` and `test_rebuild_is_idempotent`, which is the enforcement behind the README's claim that "`rm -rf .index/ && mem rebuild` loses zero knowledge — enforced by a test, not promised in a doc". `tests/redteam/test_poisoning.py` is a poisoning suite: it plants an injection payload in a memory and asserts the store set is unchanged after a Manage sleep, that the archive survives, and that the poisoned record is returned as an ordinary scored hit rather than obeyed.

**README claims, not independently verified.** The README's "Proof it works" section reports measurements on LongMemEval-S with a bounded haystack (120 episodes, `claude -p` with Haiku 4.5 as host, one calibrated Sonnet 5 judge, two exam replays per arm):

| arm | pooled accuracy | paired vs agent-memory |
|---|---|---|
| agent-memory W2 | 127/240 = 52.9% | — |
| MemCore W2 | 86/240 = 35.8% | +37/−17, p=0.009 · +35/−14, p=0.004 |
| no memory | 7/120 = 5.8% | +61/−4 · +60/−4, p<0.001 |

The README states its own limits in the same section: "Absolute numbers are not comparable to published LongMemEval scores — the haystack is bounded to 12 sessions per episode"; "The system-to-system row differs in write and read together, so it is an end-to-end comparison and licenses no attribution to either half." A second claim: "One store, three hosts: all 9 ordered writer/reader pairs across Claude Code, Codex CLI, and Hermes pass… Pooled net contribution over no memory: 2/36 → 13/36, p=0.0074." The harness code behind these exists in the repository — `arms.py` defines the five arms W0–W4 (W0 no memory, W1 boundary write blocking the task tail, W2 boundary fork off the critical path, W3 cold read of the archived transcript, W4 inline write), `exam.py` documents the agentic and fixed exam modes and the ±7-per-120 replay variance, `judge.py` holds the ABSENCE/STANDARD/FACT rubric, `interop.py` implements the writer/reader pairs, and `systems.py` defines the `agent-memory` and `memcore` dialects with the attribution guard. **But the raw run records are not in the repository.** The README says the protocol and ledger "live in `docs/experiments.md` and `experiments/` in the working tree. They ship with the source, not with git history" — and `.gitignore` lists `experiments/` and `docs/`, while `docs/experiments.md` returns 404 on the default branch. The measurements are therefore reported without any artefact a third party can inspect: no episode list, no run records, no judge votes, no ledger.

Two smaller README claims are stated with their own trade-off attached: the optional vector index improved "Recall@5 from 79.0% to 86.6% (+7.6 percentage points), while median retrieval latency increased from 5.1ms to 139.2ms", with fixed-context answer replays "17/24 versus 18/24 and, on the expanded set, 28/36 versus 27/36", and the README concludes "The existing answer-level experiments do not establish an end-to-end accuracy improvement, so vector retrieval remains optional." A Chinese-language check reports ASCII-only recall answering 2/10 queries against 9/10 for the `cjk` tokenizer and 10/10 with Chinese vectors — a five-memory, ten-query check, not a benchmark.

**What is absent.** There is no benchmark harness result for the Manage layer's own contribution: nothing in the repository isolates the effect of sleep-time consolidation on accuracy, and the "Consolidation" comparison the project's wedge rests on is asserted in `CLAUDE.md` rather than measured. There is no third-party reproduction of any figure above.

## Limitations

**Stated by the project.** `CLAUDE.md` invariant 6 gives the reasoning: "memory poisoning is a persistent attack surface; with no human in the loop, reversibility, rate limits and audit are what keep an unattended run safe." `docs/TODO.md` lists open items in the maintainers' own words, including that the duplicate keeper is not revalidated under the same writer lock as T0 invalidation, that "CLI labels alone do not identify a human" for permanent GC, import and cross-store changes, that a decision and a fact with the same key fields derive the same name so the second write is refused, and that harness Claude Code runs with tools enabled still load the user's MCP servers, "and any memory-like server contaminates attribution". The README adds a boundary on the raw-evidence path: "The Memory Source Hash covers the provenance pointer but not the referenced Session file bytes, so this boundary does not defend against out-of-band malicious modification of historical files on the Store filesystem."

**Assessed from the reporting.**

- **No artefact behind the headline numbers.** The `experiments/` tree and `docs/experiments.md` are absent from the default branch and gitignored, so the LongMemEval figures, the 9 interop pairs and the vector-fusion comparison cannot be re-derived, audited or refuted from the repository. `CLAUDE.md` asserts "Verify empirical claims by experiment before asserting" and points at `docs/experiments.md` as the protocol; the protocol is not published.
- **The comparison is end-to-end and self-declared as such.** The README itself says the agent-memory vs MemCore row "differs in write and read together… and licenses no attribution to either half". The project's differentiator is the Manage layer, and the measurement does not isolate it.
- **A bounded haystack is a write-strategy study, not a corpus-size one**, on the README's own account (12 sessions per episode).
- **The judge is a single calibrated model.** One Sonnet 5 judge with the rubric in `judge.py` scores both arms; there is no second judge, no human adjudication of a sample, and no reported judge agreement.
- **Replay variance is comparable to the differences claimed.** `exam.py` states that repeated replays of one frozen configuration "moved by +/-7 answers per 120 episodes, enough to bury any difference between memory configurations" — 7 of 120 is the same order as the 17-point gap between arms, which is why the fixed exam exists. Whether the reported per-arm differences clear that bar is not stated.
- **The environment is a moving target.** There is no release, no tag and no PyPI artifact; the version is `0.1.0` and the default host models named in the source (`claude-haiku-4-5-20251001`, `gpt-5.6-sol`) are current hosted models whose behaviour changes under the vendor.
- **Single-vendor control, no independent review.** The store is Tigerless's design, the harness is Tigerless's, the judge is a hosted third-party model used without any published agreement, and no security review of the system is in the repository.
- **Host coupling is real and partially unresolved.** The four host dialects are pinned to specific CLIs and versions (Muse native requires 1.4.4; Hermes native requires 0.22.2), native Write mode depends on `run.toolset` MCP selection in Muse, and Codex hook behaviour on Windows is listed as unconfirmed in `docs/TODO.md`.
- **No access control.** `docs/plans/memory-management-audit.md` records it directly: "No RBAC, actor authentication, approval service, policy engine, restore command, guaranteed snapshots or host sandbox is implemented. Shell access can bypass tool menus." A store shared by several hosts is a store whose contents any of them can rewrite.
- **Corrections can lose wording.** The audit names it: "Correct/split can still lose old wording without Git", and multi-file Manage failures are not transactional ("a whole Manage sleep remains nontransactional"). Reversibility rests on the git commit, which requires a git-backed store.

## Competing approaches

Only alternatives the repository names.

**The architectural line the project positions against.** The README's "Two lines, one store" section names two precedents and positions agent-memory between them: a **retrieval engine** — embeddings, a knowledge graph, a ranking pipeline — which "finds the right thing, but hands the agent an opaque chunk it cannot inspect and a store it cannot migrate off"; and a **plain filesystem** — markdown the agent reads directly, browsable with `ls` and `grep` — which "is legible and costs nothing to run, but does not rank, and stops scaling the moment the tree outgrows a listing".

**MemCore.** The benchmark table's comparison arm is `MemCore W2`, and `packages/harness/src/agent_memory/harness/systems.py` implements it as a second system dialect — a separate `memcore` binary, a `memcore create` command, a `MEMCORE_HOME`/`MEMCORE_DIR` layout and a `SKILL.md` file, with `MEMCORE_WORKING_MEMORY_TOP_K = 7` and a 120-second call timeout. So the comparison is against a named, separately runnable system, not a description of one.

**The vector-index option as an internal alternative.** The README presents BM25 as "the low-latency baseline retrieval path" and the optional vector fusion as a deliberate trade: better Recall@5, roughly 27× the median latency, and no established end-to-end answer-level gain.

**The two judgement transports.** `reasoners.py` frames the choice as host-borrowed reasoning versus an owned endpoint, and `docs/design/write-negotiation.md` frames the tool transport choice as native function calling versus a line-oriented text protocol for hosts without a verified MCP posture.

Within this knowledge base the related records are [[concepts/preservation-aware-agent-improvement]], which this project instantiates as a file-level validity-interval and supersede chain, and [[projects/envopt]], a comparative reference; the wider cross-briefing comparison is in [[evaluations/briefing-synthesis-2026-11-03-to-09]]. These are analyst-level comparisons, not verified dependencies.

## Implications

The following is analysis by the KB maintainers.

The most transferable idea is the separation of *when* judgement happens from *where* it lives. agent-memory's write path is deterministic and trigger-driven — a boundary event fires it, the core owns the file and the write path, and the model is confined to proposing operations through a fixed toolkit. The sleep-time layer then runs on its own clock with its own authority tiers. For anyone designing agent memory, the practical lesson is that the interesting engineering is in the *boundaries* — who may write, who may delete, what the model is allowed to propose and what a human must confirm — not in the retrieval algorithm. The five-tool Manage reviewer, which cannot mutate anything, is a concrete instance of [[concepts/structural-constraint-over-instruction]] applied to a memory system.

Second, "files are the truth, every index is a rebuildable cache" is a portability property with a measurable acceptance condition (`rm -rf .index/ && mem rebuild` losing zero knowledge), and the repository enforces it with a test. For teams considering a vector store as the system of record, this is the counter-pattern: the expensive, hard-to-migrate artefact is made disposable.

Third, the honest negative result is more useful than the headline. The README reports that vector fusion buys 7.6 points of Recall@5 and a 27× latency penalty, and that the answer-level replays did not move (17/24 vs 18/24; 28/36 vs 27/36) — and then leaves the feature off by default. That is the behaviour [[concepts/protocol-relative-scores]] warns about: a retrieval metric moved, an outcome metric did not, and the decision followed the outcome metric. The same discipline would be needed to judge the Manage layer, and the project has not yet applied it there.

Fourth, the poisoning suite is the right place to look for how a memory system treats its own contents: a poisoned memory is expected to come back as an ordinary scored hit and to change nothing about what the Manage layer does. Note the limit the README states itself — archived session files are not covered by the source hash, so "local-first" is not the same as "protected".

Fifth, the measurement design carries a lesson that outlives this project. The harness separates *experience* (living through sessions) from *exam* (answering from the store in a fresh session), and it offers a fixed exam in which the harness itself performs the recall, precisely because agentic replay varies by ±7 answers per 120 episodes. Any comparison of memory systems that lets each system drive its own retrieval is measuring the host's search behaviour as much as the memory. That is the shape of [[concepts/evaluator-circularity]] in an agent-memory setting, and the repository's own docstrings say so.

## Reproducible experiment

No experiment was run for this page. The protocol below is for a reader with a disposable environment; the first two steps use the repository's own harness entry points.

1. **Install and index.** `git clone`, `uv sync --all-packages`, `mem init`, then write a handful of memories with `mem record --type decision --field project=... --abstract "..." --body "..."`. Confirm `mem --json recall "<query>"` returns hits with paths and that `mem read <name> --level outline` returns headings only. This establishes the substrate the rest of the protocol depends on.
2. **The rebuild invariant.** `rm -rf ~/agent-memory-store/.index && mem rebuild`, then re-run the same recall and require the same hit set. This is the acceptance condition the repository's own test asserts, and it is the property the whole design rests on.
3. **The three-way memory comparison.** Using the repository's harness (`packages/harness`), run the arms the README's table rests on — W0 (no memory), W2 (boundary write, off the critical path) and, if the `memcore` binary is available, the MemCore arm — over a bounded episode set, with the **fixed** exam rather than the agentic one, since `exam.py` documents that agentic replay varies by ±7 answers per 120 episodes. Report pooled accuracy, write coverage (`coverage.py` computes this deterministically from the stores a run left behind) and the per-arm run records, which the upstream repository does not publish. Pass criterion: the fixed exam reproduces the README's ordering — agent-memory above MemCore above no memory — with per-arm counts and a paired test stated. A directional match is informative even if the absolute numbers differ, since the haystack bound makes the absolute figures non-comparable anyway.
4. **The missing Manage ablation.** Add a condition in which the sleep-time Manage pass is disabled and the store only accumulates boundary writes, and compare accuracy and store size against the full system on the same episodes. This directly tests the wedge the project claims and the README explicitly declines to attribute. Pass criterion: if disabling Manage changes nothing, the differentiator claim is unsupported on these tasks; if it changes a lot, the effect should be reported per-task rather than averaged.
5. **Poisoning.** Plant a memory whose body carries an instruction-shaped payload, then run a Manage sleep and a recall, and check that the store set is unchanged and that the payload is returned as data. The repository's `tests/redteam/test_poisoning.py` gives the expected shape; a difference in behaviour between the test fixture and a live store is the finding.

Substituting available models for the pinned 2026-era hosted defaults is unavoidable, and the substitution, the haystack bound and the exam mode must be reported with the results.
