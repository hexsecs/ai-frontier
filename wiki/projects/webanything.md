# WebAnything

## What it is

WebAnything is a framework for turning a specified real website into a local, resettable environment that web agents can train and be evaluated in. Given a real site, an entry URL, a permitted access scope, and a construction budget, it produces a local reconstruction that aims to preserve the site's observed presentation, interactions, and state changes within a declared *site contract* — the required pages, workflows, and checkable outcomes the reconstruction is responsible for. The source is accessible only through browser observations; no private backend code is available. The paper is by Tianci Xie (Zhejiang University) with Zikun Cai (Nanyang Technological University) and five co-authors at Shanghai Qiji Zhifeng Co., Ltd, and appeared on arXiv in October 2026.

The paper frames the problem as two gaps. The **Source-Grounding Gap**: reconstructing structure, resources, and behavior when backends are inaccessible — screenshots and model priors alone omit the state relationships that make a site behave like itself. The **Verification and Feedback Gap**: a builder's self-checks overlook source-inconsistent defects, and a discrepancy between reconstruction and source may be an implementation error *or* insufficient observation — two causes that need different responses (local repair versus additional source capture).

The central differentiator from human-assisted mirroring is automation. For the historical 85-site Full Coverage subset, the authors report that after initial configuration and necessary authorization, the collection contains no recorded per-site manual implementation, debugging, or repair. At pool scale, the authors report 244 website artifacts across 14 application domains and 53 categories, and 12,984 executed and accepted tasks built on top of them. Each released environment packages a local implementation, resources, initial data, runtime configuration, and reset interfaces: shared state connects related pages, create/modify/save operations affect later interactions, and fixed initial data plus state restoration give repeatable task starting conditions.

## Mechanism

**Explorer–Builder.** A single coupled Explorer–Builder agent receives the real URL and manages exploration, evidence collection, and local reconstruction in one context. Evidence is a triple of page structure/appearance, resources/dependencies, and before/after action observations. For each visited state, the agent associates page structures, computed styles, element geometry, screenshots, and resource references, and links actions to the visible feedback and state changes that follow them. Distinct interaction states at the same URL — a menu closed versus expanded — are kept as distinct evidence constraining different implementation requirements. Structural observations constrain layout and components; resource observations ground fonts, images, and media; behavioral observations constrain navigation, filtering, and state modification. The Builder organizes these into local components, routes, and shared object relationships (the released environments use a Flask/SQLite architecture). When available observations do not establish a required outcome, the system seeks additional evidence rather than treating an inferred behavior as observed. In the recovered records for the historical batch, the Builder and Verifier primarily used gpt-5.6-sol with xhigh reasoning, with some Builder calls on gpt-6-astra — so the batch did not use a single model. Two coverage policies exist: *Full Coverage* expands accessible page types, interaction states, and neighboring branches from the entry URL; *Just-in-Time Coverage* prioritizes the dependencies of a given task set. The reported construction experiments use Full Coverage.

**Independent Verifier and evidence-aware refinement.** The Builder implements and self-checks a candidate, which is then *frozen* — bound to a digest — and examined by an Independent Verifier in a separate context. The Verifier obtains rendering and operation results anew, compares them against source evidence and the site contract (pages, controls, resources, workflows, persistence, restoration), and cannot edit candidate code. Freezing binds findings to the inspected implementation and prevents verification-time repair from changing the target. Discrepancies are routed by evidence sufficiency. If existing evidence establishes an expected outcome the candidate fails to reproduce, the route is **Local Repair**: the Builder receives the affected page or control, the executed action, expected and observed outcomes, and supporting evidence. If evidence is insufficient to establish the target outcome, the route is **Targeted Recapture**: a concrete observation request revisits the relevant source region, and the newly captured structure, resources, or behavior constrains the next implementation. After either path, the controller re-freezes the updated candidate and the Verifier repeats the affected checks plus applicable regression tests.

**Task supply.** A task pipeline reads a mirror's pages, visible objects, native operations, and seed data to formulate goals — retrieval, filtering, detail verification, comparison/aggregation, state modification. Public task records carry a task ID, instruction, site, starting URL, and login/reset requirements; hidden specifications hold required objects, query parameters, source evidence, expected results, and output contracts. Information tasks check normalized answer fields, sets, or orderings; state-changing tasks check post-operation application states. Acceptance is execution-based: a task becomes an accepted task only after a visual agent actually executes it through a fixed browser harness and an independent task evaluator checks the final answer against hidden success conditions using terminal DOM, screenshots, and state evidence. The authors keep task generation, evaluator construction, execution-based acceptance, trajectory collection, and training-sample export as separate counting stages throughout — a discipline the evidence section below relies on.

## Evidence

Everything in this section is **author-reported** from a single arXiv preprint by the system's own authors; no result has independent third-party replication. The "independent" verifier and evaluators are independent contexts within the authors' own setup, and the blind audit is a human annotation study the authors arranged.

**Scale, automation, and cost (RQ1).** The 244-artifact pool was frozen on 2026-10-09, deduplicated by site identity, and is explicitly not a preregistered random sample with fixed quotas. For the historical 85-site Full Coverage subset, outcomes under differing historical versions of the acceptance criteria were 59 passed, 15 source-blocked, 6 failed, and 5 with missing reports. Recorded model-call cost for 84 sites totals $220.62 (mean $2.63, median $1.60 per site) — a lower bound excluding unpriced calls, browser execution, and system overhead, and not extrapolated to all 244 sites.

**Source-state fidelity (RQ2-A): a clear win.** On five sites matched against human-assisted WebHarbor (Apple, arXiv, Cambridge Dictionary, ESPN, Hugging Face Papers) across 14 historical reference states, WebAnything scores higher on all three aggregate metrics: Pixel Similarity 0.9240 vs. 0.8083, SSIM 0.7904 vs. 0.6260, and Text F1 0.8541 vs. 0.2617. A blind human audit of the same states gives WebAnything 12 wins, 2 ties, and 0 losses on overall fidelity; on discrepancy severity, WebAnything scored 12/14 equivalent and 0/14 severe (mean 0.143) against WebHarbor's 0/14 equivalent and 6/14 severe (mean 1.429). Excluding the two sites whose historical references have rendering defects (Apple, ESPN), SSIM is 0.8051 vs. 0.6885 — the direction is unchanged. A separate four-state comparison against VeriEnv's LinkedIn clone also favors WebAnything (Pixel 0.9574 vs. 0.9436; SSIM 0.8190 vs. 0.7637).

**Interaction validity (RQ2-B): the tradeoff.** On the WebHarbor-matched subset of offline tests — navigation, retrieval, forms, state mutations, recovery, with external network disabled — WebAnything *trails* the baseline it beat on fidelity: capability coverage 75% vs. 80% (15/20 vs. 16/20 planned capabilities) and all-test pass 63.3% vs. 76.7% (19/30 vs. 23/30), though executed-test success is close (95% vs. 100%). On a separate VeriEnv-matched subset, selected WebAnything pool artifacts lead instead: all-test pass 29/33 vs. 21/33 and coverage 100% vs. 90.9% — but four of those five artifacts were imported from existing directories rather than necessarily built by the WebAnything pipeline, which weakens attribution. The authors' own framing is the honest summary: source fidelity determines what agents observe, while interaction validity determines what they can execute, and higher visual correspondence alone does not establish broader functional coverage.

**Verification feedback (RQ2-C): suggestive, not strong.** Of 229 historical Builder–Verifier report pairs across 69 sites, 219 had passing Builder self-checks; independent verification of those 219 passed 25.57%, failed 63.47%, and found 10.96% source-blocked — so self-checks clearly miss a great deal. The Verifier identified evidence-supported discrepancies in 39 report pairs across 22 sites, and issue-level inspection confirms 18 independently reverified resolution records across six sites (14 local implementation repairs, three runtime repairs, one request-lifecycle issue). The strictness caveats are in Limitations; the headline is that independent checking finds real defects self-checks pass, but the records do not quantify the loop's causal effect, and the authors report no causal effect for recapture.

**Task supply (RQ3-A).** The 12,984 executed and accepted tasks come from two disjoint collections: 6,172 across 74 sites and a newer 6,812 across 229 sites (93.1% of the 244 × 30 per-site target; 15 pool sites have none). Accepted counts describe accepted outputs, not the success rate of all proposals or attempts. In the earlier collection, 77.8% of tasks involve information retrieval, 99.8% are multi-page, and actual trajectories average 10.4 tool steps (P90 21).

**Downstream training (RQ3-B): gains with a regression.** Fine-tuning Qwen3.5-9B on 5,856 WebAnything interaction trajectories (the newer 6,812 tasks were not used), against the same backbone under the authors' fixed harness, single-run and descriptive (no significance testing): on REAL, success rises from 22/91 to 31/91 (+9.9 pp) on jointly valid tasks, and +8.8 pp on the full 102-task denominator. On Odysseys-Easy, Rubric Avg rises 19.71% → 25.96% (+6.25 pp). On WebArena-Verified under strict scoring, Overall rises 16.41% → 29.74% (+13.33 pp), with Mutate up sharply (10.51% → 42.01%, +31.50 pp) — but **Retrieve regresses from 20.75% to 12.00% (−8.75 pp)**. In a same-backbone comparison of training-data sources on 189 jointly valid Odysseys-All tasks, the WebAnything-trained model leads on Rubric Avg (10.44 vs. WebHarbor 6.93, VeriEnv 6.42) and Task Avg (11.70 vs. 7.79, 7.53), though absolute levels are low for all three.

## Limitations

- **The largest fidelity gap sits on the weakest-measured metric.** Historical Text F1 — where the headline gap is widest (0.8541 vs. 0.2617) — is computed from full-page text with normalization, but the source side is frozen HTML *replayed with JavaScript disabled* while mirror text comes from JavaScript-enabled captures. The authors disclose this archival rendering asymmetry and retain the scores; the direction and size of the resulting bias are not quantified.
- **The format-relaxed rescoring is one-sided.** Noting that strict scoring penalizes JSON-format deviations, the authors rescore the SFT model's WebArena-Verified outputs ignoring format judgment: Retrieve passes rise from 12.00% to 32.31% (+20.31 pp). But the relaxation is applied only to the SFT outputs — there is no relaxed baseline and no relaxed Overall — so it cannot establish that the strict-scoring Retrieve regression is purely a formatting artifact. The regression stands as reported; the explanation is plausible but untested.
- **Quality evidence covers roughly ten of the 244 pool sites.** Fidelity rests on five sites and 14 states (plus four LinkedIn states); interaction validity on two disjoint five-site subsets. All 244 startup records have an HTTP 200 response and a homepage screenshot, but 131 of the 244 received no review beyond that; of the 113 reviewed more deeply, only 70 were without confirmed anomalies (9 flagged presentation issues, 26 with signals awaiting diagnosis, 8 special records) — diagnostics even found byte-identical *blank* homepage screenshots for two sites. The headline "244 artifacts" is an inventory count, not a validated-quality count.
- **No unified construction success rate exists.** Neither the 244-site pool nor the 85-site subset has a complete attempt cohort under uniform acceptance criteria, so the paper does not compute one; the 59/15/6/5 outcome split for the 85 sites mixes differing historical criteria versions.
- **The verification-feedback evidence is soft.** Of the 39 claimed Builder–Verifier discrepancy pairs, only one is strictly candidate-matched (same candidate, same semantic target); the other 38 are non-strict pairs where candidate identity, check scope, or runtime conditions differ. Confirmed repairs total 18 records across six sites, and the authors note these include shared mechanisms and recurrences — they are not independent samples. Recapture efficacy is explicitly not established.
- **The blind audit is small and consensus-based.** Three annotators formed labels through discussion over 14 states from five sites, and no inter-annotator agreement statistic is reported, so the audit's reliability cannot be assessed independently.
- **Builder and Verifier are same-family models** — primarily gpt-5.6-sol for both in the historical batch — so their independence is contextual and procedural, not model-diverse; correlated blind spots are possible. The same model also serves as the Odysseys judge.
- **Downstream results are single-run and subset-based.** All SFT comparisons are descriptive with no variance or significance estimates; headline denominators are jointly-valid subsets that exclude infrastructure failures; and Odysseys evaluation sites overlap training source sites at the host level (Amazon, Apple, Google, YouTube), so site-level familiarity cannot be fully excluded despite instruction-level decontamination. Training validation is at the 9B scale only, and the timeliness of mirrors under continuing source-site change is not evaluated.
- **Distribution is license-constrained.** Public accessibility does not grant reproduction rights; the authors restrict environment distribution to content licenses and authorizations, and only three demo sites are bundled with the released code — the 244 reconstructed site trees remain in a separate artifact store.

## Competing approaches

- **WebHarbor** — human–coding-agent collaborative mirroring; the primary baseline for both the fidelity win and the interaction-validity loss, and the comparison that defines the tradeoff this page reports.
- **VeriEnv** — cloned environments with SDK-based task verification; baseline for the second interaction subset and the data-source comparison.
- **Generative construction from specifications or references** — WebFactory, InfiniteWeb (task-centric test-driven development), WebArena-Infinity, and WebGen-Agent (VLM appearance feedback plus GUI testing with backtracking), which build environments without WebAnything's source-grounding requirement.
- **Capture-and-replay** — World of Bits and WARC-Bench; Weblica is the closest hybrid, combining replay with source-grounded synthesis.
- **Screenshot-to-code** — the pix2code / Pix2Struct / WebSight / Design2Code line, which reconstructs appearance without behavior or state.
- **Self-hosted benchmark environments** (WebArena, REAL, WebShop, WorkArena, OSWorld, and similar) are the demand side rather than construction competitors: hand-built environments whose cost is what automated construction is meant to undercut.

## Implications

If the fidelity results hold up, environment supply for web agents becomes a construction problem rather than a curation bottleneck: a recorded lower-bound cost around $2.63 per site (excluding overhead) changes the economics of generating training tasks at scale, and resettable local mirrors give reproducible evaluation conditions that live sites — drifting, rate-limited, sometimes hostile — cannot. The interaction-validity loss is the standing warning for consumers of any reconstructed environment: visual correspondence and functional coverage are separate axes, and an environment that *looks* right can still fail to *do* the things tasks require. Procurement-style advice follows directly: demand both metrics, on matched sites, before training on a mirror.

The paper is also a useful disclosure template. Its counting discipline (generation, acceptance, trajectories, and training exports as separate units), its explicit refusal to compute a unified success rate without a uniform cohort, and the repository README's "evidence boundary" section — stating plainly that HTTP 200 plus a screenshot establishes only startup/rendering observations — are practices environment papers rarely follow, and they are what make this page's tradeoff reportable at all. The weakest part of the work is symmetric: the verification loop is the mechanism the paper most wants to credit, and it is the part with the softest evidence. Whether independent verification and recapture actually cause the fidelity advantage, rather than merely accompanying a strong builder, remains an open experiment — see [[techniques/evaluation-and-simulation]] for the KB's wider treatment of evaluation design.

## Reproducible experiment

The code is public (MIT) as the `webanything` package and CLI, with a frozen 244-site inventory manifest and three runnable demo sites; per KB policy it was not cloned or executed for this page, so the following is a proposed protocol, not a performed one. A minimal replication of the paper's central tradeoff: pick one small, publicly accessible site within the tool's permitted scope; construct it in Full Coverage mode; freeze the candidate and run the Independent Verifier; then score the reconstruction against the live source on both axes — Pixel Similarity, SSIM, and Text F1 over a handful of matched states (rendering the source reference under the same JavaScript conditions as the mirror, to avoid the paper's asymmetry) — and run a fixed offline interaction test set (navigation, retrieval, a form, a state mutation, state restoration after reset) reporting capability coverage, executed-test success, and all-test pass as separate denominators. The prediction to test: fidelity metrics land high while all-test pass trails them, reproducing the paper's gap between what the mirror shows and what it does. A stricter variant additionally candidate-matches every Builder–Verifier pair, testing whether the discrepancy yield survives the strictness the historical records mostly lack.
