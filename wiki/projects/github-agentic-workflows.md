# GitHub Agentic Workflows

**Origin:** [[briefings/2026/11/2026-11-04]] — finding 7. **Announcement:** GitHub changelog, 11 June 2026, "GitHub Agentic Workflows is now in public preview". **Implementation:** the `github/gh-aw` repository, a GitHub CLI extension written in Go. **Status:** a public preview of a shipped product, with the mechanism inspectable in a public repository and the performance claims supplied only as vendor testimonials.

## What it is

GitHub Agentic Workflows (`gh-aw`) is a system for defining AI-powered repository automation as Markdown files with YAML frontmatter, which the `gh-aw` CLI compiles into standard GitHub Actions workflows that run a coding agent inside Actions. The changelog entry of 11 June 2026 announces public preview and names the tasks the preview targets — issue triage, CI failure analysis, documentation updates, and by implication security remediation — and states the core property: because the output is "just actions", the workflows "reuse your existing runner groups and policy constraints".

The implementation lives in the `github/gh-aw` repository (MIT licence, Go, created 12 August 2025, default branch `main`; the repository page reports 5,611 stars, 627 forks and 476 open issues as of 2026-11-10). It is installed as a GitHub CLI extension, `gh extension install github/gh-aw`, and the compiled artefacts are committed to the repository as `.lock.yml` files.

This page separates three things that the announcement blends. **Documented behaviour** is what the repository's own documentation and source files state, and it is verifiable by any reader. **Marketing claims** are the announcement's framing and the three customer quotations. **Measured performance** is thin: the changelog publishes no reliability, accuracy, cost or adoption figure for the product, only vendor testimonials.

## Mechanism

The following is based on files read directly from the repository on 2026-11-10: `README.md`, `docs/src/content/docs/introduction/how-they-work.mdx`, `docs/src/content/docs/introduction/architecture.mdx`, `docs/src/content/docs/reference/permissions.md`, `docs/src/content/docs/reference/integrity.md`, `docs/src/content/docs/reference/threat-detection.md`, `docs/src/content/docs/reference/safe-outputs.md`, `docs/src/content/docs/reference/compilation-process.md`, plus the workflow sources under `.github/workflows/` and the release and advisory listings from the GitHub API.

**Workflow format.** A workflow is a Markdown file with YAML frontmatter. The frontmatter configures triggers, permissions, tools, the AI engine, network policy and safe outputs; the Markdown body carries the natural-language instructions the agent executes. The `gh aw compile` command validates the source and generates a `.lock.yml` file that Actions actually runs. The compiled file embeds the original prompt; the Markdown body is loaded at runtime, so instructions can be edited without recompiling.

**Compilation.** The compiler runs five phases — parsing and validation, job construction, dependency resolution, action pinning and YAML generation. Validation covers the workflow schema, expression safety (only allow-listed GitHub Actions expressions) and import resolution; the generated YAML is additionally checked by a native Go port of the Actions language-services parser, and by external scanners (actionlint, zizmor, poutine) when opted in. All actions are pinned to commit SHAs. Job construction creates the specialised jobs: pre-activation, activation, agent, safe outputs, safe jobs and custom jobs. The repository itself holds **519 workflow `.md` files under `.github/workflows/` and 367 compiled `.lock.yml` files**, which is itself the largest worked example set available.

**Engines and authentication.** The built-in AI engines are GitHub Copilot (default), Claude Code, OpenAI Codex, Google Gemini and Pi. Each authenticates separately: `copilot-requests: write` or `COPILOT_GITHUB_TOKEN` for Copilot; `ANTHROPIC_API_KEY` or Anthropic WIF for Claude Code; `CODEX_API_KEY` or `OPENAI_API_KEY` for Codex; `GEMINI_API_KEY` or Google WIF for Gemini; Pi routes by provider prefix in `model:`. The `copilot-requests: write` permission is an authored top-level opt-in for organisation-billed Copilot inference, not a compiler default.

**Permissions and safe outputs.** The agent job runs read-only by default; the permissions reference states the separation "provides an audit trail, limits blast radius if an agent misbehaves, supports compliance approval gates, and defends against prompt injection", and notes that safe outputs add one extra job. Write operations are never performed by the agent: they are declared as **safe outputs**, buffered as artefacts, and applied by separate jobs holding scoped write permissions. The safe-outputs reference documents **56 distinct safe-output keys**, each with a default maximum — `create-issue` (max 1), `create-pull-request` (default max 1, configurable), `add-comment` (max 1), `add-labels` (max 5 calls), `merge-pull-request` (max 1, marked experimental), `create-code-scanning-alert` (unlimited, same-repo only), plus Jira, Linear and Azure DevOps integrations. The safe-outputs specification is published as a W3C-style working draft (version 1.29.22, dated 2026-11-09) and defines the gateway as "a security-centric translation layer enabling AI agents to declare intended GitHub operations through structured protocols while maintaining strict privilege separation".

**Threat detection.** When safe outputs are configured, a detection job runs automatically after the agent job and before the safe-output jobs, analysing agent output and patches for prompt injection, secret leaks and malicious code patches. The default behaviour is warn mode: detected threats annotate reviewable outputs, convert branch pushes and abort non-reviewable outputs, rather than blocking everything. Strict mode is available and is the mode the architecture diagrams illustrate. `continue-on-error` defaults to true, so detection failures follow the warn policy. The compiler embeds a reviewed detector release tag and per-architecture SHA-256 digests, and installation verifies the downloaded binary against those compiler-controlled pins; if verification fails, the detection job neither runs nor concludes with a detector binary and the conclusion is reported as an `agent_failure`. A tracking issue (`[aw] Detection Runs`) is created by default, and the detection run is capped at 400 AI credits by default, independently of the agent's own budget.

**Isolation and network control.** The security architecture is described in three trust layers. *Substrate-level*: the runner host or Kubernetes cluster, CPU, MMU, kernel, container runtime; eligible GitHub-hosted runners can use Cloud Hypervisor to place the agent in a KVM-isolated microVM. *Configuration-level*: declarative configuration determines which components exist and how they connect; authored pre-activation steps, custom jobs, detection steps and safe-output steps are **trusted executable code, not confined to the agent sandbox**, and a read-only `GITHUB_TOKEN` does not remove other credentials or host access. *Plan-level*: the compiler decomposes the workflow into stages, and safe outputs instantiate this — external writes are buffered and passed through deterministic filters before being externalised, so a compromised agent's blast radius is limited to the stage in which it is active.

The **Agent Workflow Firewall (AWF)** containerises the agent, binds it to a Docker network, and redirects HTTP/HTTPS traffic through a Squid proxy that enforces a domain allowlist; the AWF setup drops its iptables capabilities before the agent launches. A more permissive `chroot` mode mounts a subset of host directories read-only under `/host`, mounts the host's `HOME` and `/tmp` read-write, and launches the agent inside a chroot jail — the stated purpose being that many coding agents break if containerised naively. Sandbox runtimes are selected by `sandbox.agent.runtime`: `docker` (default, rootless AWF, network isolation), `docker-sudo-iptables` (privileged AWF, legacy iptables), `cloud-hypervisor` (preview KVM) and `nvx` (fail-closed preview one-shot microVM requiring an explicit workload guest layer, an offline attestation and three security opt-ins). Disabling the agent sandbox requires `features.dangerously-disable-sandbox-agent: true` and is always rejected in strict mode.

**Integrity filtering.** `tools.github.min-integrity` filters GitHub content by *trust* rather than by permission. The MCP gateway intercepts tool calls and removes any item below the configured integrity level before the model sees it, logging each removal as a `DIFC_FILTERED` event. The hierarchy is `merged > approved > unapproved > none > blocked`; `approved` covers objects authored by OWNER, MEMBER or COLLABORATOR, non-fork PRs on public repositories, all items in private repositories, trusted bots and users in `trusted-users`. `blocked` is assigned to `blocked-users` and is always denied regardless of threshold. `lockdown` mode is documented as superseded by integrity filtering.

**Pre-activation and activation.** Separate jobs run before the agent: role and permission checks, then content sanitisation of event data. The architecture's review table assigns explicit operator responsibilities for custom executable steps ("Keep untrusted event fields and downloaded content as data, not shell/JavaScript source"), action and runtime pinning, policy opt-outs, and host and upstream state.

**The blast radius of a real defect is documented by the advisory record.** The repository's published security advisories number 18 as of 2026-11-10 — 8 critical, 6 high and 4 medium — published between 2026-08-06 and 2026-11-05. Their summaries describe concrete failure modes in this architecture: "Sandboxed code can steal and silently exfiltrate the gh-aw job token" (critical), "Safe-output artifacts may expose CI trigger tokens" (critical), "safe-output validator forwards undeclared agent fields to the appliers (scope escape / mass assignment)" (critical), "Arbitrary host filesystem & Docker-socket mounts via MCP server `mounts`" (critical), "command injection in compiled workflow via unsanitized `sandbox.mcp.env` exports" (critical), "the confused-deputy check does not cover pull_request_target" (high), "HTTPS egress allowlist bypass via TLS SNI domain fronting" (high), and "cache-memory restores an attacker-controlled .git/config and executes a git filter driver on the runner host" (high). The README additionally records that a security vulnerability in versions `>= 0.83.3, < 0.85.4` led to those releases being retired as a pre-emptive measure.

**One measured characteristic of the design, stated as a default rather than a result.** The documentation's own threat model states that it "does not protect against failures of substrate-level isolation or mis-allocation of permissions at credential-minting or configuration time", and the safe-outputs and threat-detection references both record fail-closed behaviour with respect to verification: an unverifiable detector binary yields `agent_failure`, a failed redaction pass blocks publication even in warn mode with `continue-on-error`, and copied firewall files must be valid UTF-8 no larger than 16 MiB or publication is blocked. These are documented invariants, not measurements of how often they fire.

**What is not measured anywhere in the inspected sources.** No figure is published for how often safe outputs are rejected, how often threat detection fires and with what false-positive rate, whether `warn` mode leaks annotated outputs that should have been blocked, how often integrity filtering removes content, the latency cost of the firewall and detection jobs on a workflow run, or the accuracy of any agentic workflow's judgements. The reference documentation for `measuring-impact` exists as a guide, but no measured results appear in the sources inspected.

## Limitations

**Stated by the vendor.** The README is unusually direct: "Using agentic workflows in your repository requires careful attention to security considerations and careful human supervision, and even then things can still go wrong. Use it with caution, and at your own risk." The architecture document states that some controls can be changed or disabled and must be evaluated during workflow review, that authored pre-activation, custom jobs, detection steps and safe-output steps are trusted code outside the sandbox, that a read-only `GITHUB_TOKEN` does not remove other credentials or host access, that "acknowledging a warning is not enforcement", and that compilation does not prove host cleanliness, cache provenance or producer-code trust. The FAQ states plainly that gh-aw "does not add any cost beyond what the AI engine charges" — the user pays provider inference rates plus Actions compute minutes — and that it does not replace deterministic CI.

**Assessed by the KB maintainers.**

- **Vendor testimonials are not evidence.** All three quotations are marketing selections with no methodology, denominator or counterfactual; the "completed autonomously in minutes" claim has no baseline time attached. The changelog publishes no measurement at all.
- **The default enforcement mode is warn, not strict.** With `continue-on-error` defaulting to true, a detected threat annotates reviewable outputs, converts branch pushes and aborts non-reviewable outputs rather than blocking the run. The architecture diagrams illustrate the strict-mode branches, and the document itself flags this gap ("its 'approved' and 'blocked' branches illustrate strict mode only, not default warn mode"). A team assuming fail-closed behaviour from the diagrams would be wrong.
- **A mature advisory record cuts against the security narrative.** Eight critical and six high advisories in three months, including job-token exfiltration from the sandbox, scope escape in the safe-output validator, and host mounts via MCP configuration, mean the layered architecture was not uniformly effective at the time of writing. The preview announcement predates all of them.
- **The trust boundary is wider than the marketing.** The safe-outputs, detection and custom-job surfaces are trusted executable code with their own permissions and secrets; only the agent job is confined. "Read-only by default" describes the agent, not the workflow.
- **Detection is itself an LLM judgement.** The threat detector uses AI-powered analysis to decide whether an output is malicious, with a budget cap and a warn-mode default — a false-negative rate in a security control that is itself model-based, and one for which no published evaluation exists.
- **The integrity filter is a trust heuristic.** `approved` includes non-fork PRs on public repositories and all items in private repositories, and promotes content by label, reaction or user list. An attacker inside the trusted set, or a compromised account with an association, is inside the boundary by construction.
- **Everything measured here is platform-level, not workflow-level.** Repository metadata, release tags, file counts and advisory counts characterise the project, not the quality of the automation it produces.
- **Documentation and code version independently.** The specification is dated 2026-11-09 while the repository's public releases reached v1.2.2 on 2026-11-10, and the specification describes the implementation as it stands "in GitHub Agentic Workflows version 1.8.0 and later" — a versioning scheme that does not match the release tags observed. The sources do not explain the discrepancy, so version-specific claims should not be inferred.

## Competing approaches

Only alternatives the sources name.

- **Deterministic GitHub Actions.** The documentation is explicit that conventional Actions are "ideal for deterministic operations such as builds, tests, linting, deployments, and reproducible scripts", and that agentic workflows "complement existing CI/CD; it does not replace it". The recommended split is deterministic for reproducible steps, agentic for investigation, triage, review, research and generation.
- **Scripted GitHub API automation.** The FAQ positions gh-aw against writing bespoke scripts over the GitHub API, and the how-it-works guide states that conventional Actions remain appropriate where identical inputs should produce predictable steps and outputs.
- **Direct write permissions versus safe outputs.** The permissions reference states that direct write permissions and custom jobs are possible "but are separate trust boundaries and require explicit review"; the recommended path is the read-only agent plus validated safe-output jobs.
- **Docker container isolation versus Cloud Hypervisor microVM versus chroot.** These are documented alternatives for the agent runtime, selectable by `sandbox.agent.runtime`, with `nvx` described as a fail-closed preview that never falls back to another runtime.
- **Legacy inline detection engine versus the external `threat-detect` implementation.** The threat-detection reference notes that `features.gh-aw-detection: false` selects the legacy inline engine, while the external implementation is the default and is pinned by release tag and per-architecture digest.
- **Lockdown mode versus integrity filtering.** `lockdown` is documented as deprecated and superseded by `min-integrity`; workflows are expected to migrate.
- **Engine choice as an alternative.** Copilot, Claude Code, Codex, Gemini and Pi are documented alternatives with different authentication, turn-control and routing properties.

Within this knowledge base, the design is the clearest instance of [[concepts/structural-constraint-over-instruction]]: the agent never holds a write token, and every write passes a validating job. It is a strong sibling of [[projects/github-contribution-check]] — a specific workflow built on this platform — and of [[projects/toolguardian]], which authorises tool invocation in task context. Its write-buffer-then-apply pattern is the [[techniques/secure-agent-operations]] technique page's central case, and its fail-closed rules are a [[techniques/verification-and-evidence]] pattern with a named budget. It is also an analyst-level **compares_with** counterpart to [[projects/agent-orchestrator]] — a different mechanism for the same class of delegation, not a verified dependency — and it feeds [[evaluations/briefing-synthesis-2026-11-03-to-09]]. See also [[projects/github-copilot-fusion]] for the routing product, and [[workflows/index]].

## Implications

The following is analysis by the KB maintainers, not a claim of GitHub's.

The durable engineering idea is the separation of *proposal* from *application*. The agent's only sanctioned output is a structured declaration of an intended operation, which a separate job validates against structural constraints and limits before any privileged call is made. This makes the risky surface narrow and auditable, and it composes with the [[concepts/verified-completion-vs-apparent-success]] problem in a specific way: the agent's claim to have done something is not the thing that changes the world.

The second lesson is that the safety of the pattern depends entirely on where the trust boundary is drawn, and the documentation is refreshingly honest that the boundary is not where the marketing suggests. Agent job confined, but safe-output jobs, detection steps, pre-activation steps and custom jobs are trusted code. A team adopting this should audit its own workflow's trusted surface — which custom steps exist, which secrets each job can see, which hosts are mounted — rather than relying on "read-only by default" as a summary.

Third, the advisory record is the most useful empirical artifact here, and it is a design lesson rather than a blemish. The recurring shapes are capability leak (job token reachable from sandboxed code), scope escape (undeclared fields forwarded to appliers), policy bypass (egress allowlist defeated by SNI fronting, userinfo `@`, heredoc-blind template parsing), and confused deputy (a `pull_request_target` path not covered by the deputy check). Each is a specific instance of a general rule: a security control that is expressed as a filter over a request stream must be enforced at the point where the privileged operation is actually issued, not only where the stream is filtered.

Fourth, on evaluation: a security architecture whose enforcement is partly model-based, whose default mode is warn, and for which no detection accuracy is published, should be treated as unquantified. Before enabling a workflow that writes, the meaningful test is empirical — inject the failure classes the advisories describe and observe whether the pipeline blocks them.

Finally, the product's economics are clear from the FAQ and should shape adoption: gh-aw itself is free and the marginal cost is provider inference plus Actions minutes, but a workflow that runs an agent on a schedule spends on every run, including runs where the agent concludes nothing should change. The `noop` safe output and the explicit maxima on every safe-output type are the mechanism for bounding that, and they are the parts worth reading before writing a first workflow.

## Reproducible experiment

The repository is public and the artefacts are inspectable, so a mechanism-level test is feasible without asking GitHub for anything. A faithful partial check of the product's central claim — that agents can be given real write capability without granting them the authority to misuse it — proceeds as follows.

1. **Positive control: does a safe output actually get applied, and only through the validating job?** In a throwaway repository, author one workflow with `safe-outputs: create-issue` and a `strict: true` frontmatter, run it on a scheduled trigger, and confirm from the run's job graph that the agent job holds only read permissions and that the issue is created by a separate job. Pass criterion: no job holding a write token contains the agent step.
2. **Prompt-injection test (the decisive one).** Open an issue whose body contains text instructing the agent to post a comment containing a marker string, or to create a second issue beyond the configured maximum. Run a workflow triggered on `issues: opened` with `add-comment` and `create-issue` safe outputs. Pass criterion for the safe-output mechanism: the marker either does not appear in the applied output, or the run is blocked or the output is annotated rather than applied — and the configured maximum on the number of created issues is never exceeded. Failing this is the expected failure mode if the integrity filter and the safe-output validator are not doing their job, so treat it as a security test, not a capability test.
3. **Safe-output structural rejection.** Configure `create-issue` with a maximum of 1 and have the agent attempt to declare three issues in one run. Pass criterion: at most one issue is created and the surplus is rejected with a visible reason, not silently dropped. Also check the count-maximisation path (`max-ai-credits`, per-output maxima) actually binds rather than only being documented.
4. **Detection-mode test.** Run the same injection twice, once with the default warn mode and once with `continue-on-error: false` (strict). Record what is applied in each mode. Pass criterion for the *design* claim: warn mode must not silently apply the dangerous output — it should annotate, convert or abort — and strict mode must block. A run where warn mode applies the output unchanged falsifies the "defends against prompt injection" claim as documented.
5. **Egress control.** Have the workflow attempt to fetch a disallowed host and a host that resolves to the same address, and confirm the AWF proxy's domain allowlist denies the first and does not admit the second by another route. Because a published advisory describes SNI domain fronting as a past bypass, this step should specifically test a domain-fronting variant, not only a plain unlisted hostname.
6. **Reference implementation check.** Install the extension on a scratch repository and compare the compiled `.lock.yml` against the checked-in lock files for the repository's own workflows: verify SHA pinning of every action, that `actions: read` is the compiler-added permission, and that the safe-output jobs carry the scoped permissions the documentation claims. This step needs no agent run at all and is the cheapest way to confirm the documented behaviour matches the shipped artefact.

No step should be reported as passing on the basis of a single successful run; the injection conditions should be repeated, and negative results — outputs that were applied when they should not have been — published alongside positive ones.
