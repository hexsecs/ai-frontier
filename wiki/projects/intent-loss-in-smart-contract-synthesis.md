# Measuring Where Intent Gets Lost in Agentic Smart Contract Synthesis

## What it is

A measurement study by Abhinav Goel, Agostino Capponi, Chaitya Shah (Columbia University) and Alfio Gliozzo (IBM T.J. Watson Research Center), published as an arXiv preprint (arXiv:2610.37830, October 2026; no peer-reviewed venue is stated). Earlier versions of this page carried a paraphrased title; the paper's actual title is the one above. The study asks a narrow, practical question about agentic code generation: when an agent synthesizes a Solidity smart contract from a short natural-language description, where does the information in the description get lost — and can the instruments normally used to grade the result (LLM judges, static analyzers, LLM testers, self-grading rubrics) be trusted to notice?

Terminology matters here, because the paper is explicit about it and earlier summaries of this work were not. The paper distinguishes *author intent*, *compliance with a written specification*, and *implementation fidelity* — agreement with a given implementation on the same transactions. Because every task starts from an existing contract, **implementation fidelity is the construct actually measured**. Fidelity reflects intent only where the original contract embodies what its author wanted. The fidelity oracle is always the **original contract**, scored by exact transaction replay. The LLM-written reference models that appear throughout the study are a separate instrument — mistake detectors and disagreement flaggers — and they never score generated contracts. Any reading of this paper as "measuring intent loss" as a psychological quantity is a misreading the authors themselves warn against.

The testbed is drawn from the FSM-SCG corpus (21,976 contracts), filtered to non-stub contracts of at least 40 lines that compile, deploy, and contain at least one contract-specific rule: 100 contracts for development experiments and 500 more for a scale replication. Two generation pipelines are compared: the authors' own earlier seven-phase pipeline (the baseline) and a new elicitation-first pipeline built around a fixed ten-question checklist answered before generation.

## Mechanism

**Task setup.** For each contract, an LLM (Gemini 2.5 Flash) writes a short description of about 140 words, phrased as a client might write it, and a complete requirements document of about 1,700 words stating every rule with exact values. The short description is the realistic input; the complete document is an upper-bound information condition.

**Simulated client.** The elicitation questions are answered by a simulated client: GPT-5.4 reads the real (original) contract and answers each question in at most two sentences of plain English, without mentioning code. The ten fixed checklist questions cover caps and limits with exact values, prices and required payments, fees, time windows, phases and states, role restrictions, freezing/pausing/blacklisting, balance and supply changes, failure conditions, and "anything unusual a developer might get wrong."

**Exact-replay fidelity scoring.** Each generated contract is scored by replaying 60 random sequences of 8 transactions in an in-process EVM, each chain continuing from its own state (a step after a first divergence is still scored). The required interface is every state-changing function of the original, identical for all systems; replay uses the original's exact signatures, argument types, and attached ether, so a missing or changed signature fails the step. A step is correct only if its outcome matches and, when it succeeds, every observed value changes as in the original; a change the generated contract does not expose is not credited — unverified steps score as incorrect. Reported metrics are transaction-level fidelity (share of correct contract-specific steps, averaged over contracts), pass rate (contracts matching the initial state and passing every sampled step), interface coverage, and observation coverage. The scorer passes known-answer tests built from four counterexamples an external audit found in the authors' previous scorer (adapted calls, dropped ether, skipped unobserved changes, changes-only comparison).

**Planted-mistake audit.** The grading instruments themselves are audited by mutation testing: one-rule mistakes are planted in real contracts, each with an untouched twin, and a mistake counts as caught only under strict side-picking — over the transactions that expose the mistake, the instrument must side with the twin more often than with the mutant (a binary disagree-anywhere rule could be passed by a coin flip). Controls include two uninformed oracles (always-succeed, always-revert) and a description-free control: a reference model written from function names alone.

**Reference models ("rulebooks").** A writer model, called separately from the generator, turns the description plus the contract's public interface into a Python class with one method per public function, raising `Revert` where the description says a call must fail. Inside the elicitation-first pipeline, reference models only flag candidate disagreements between the generated contract and the rulebook; the client adjudicates them as blind A/B choices, and cases where the client sides with the reference model trigger a code repair. They never assign fidelity scores.

**The two pipelines.** The original pipeline parses requirements into a schema without consulting their author, generates code, runs an LLM security auditor whose medium-or-higher findings trigger one rewriting refinement round, and grades itself with an LLM rubric judge. The elicitation-first pipeline asks the checklist first, generates from description plus answer transcript, applies compile repair, writes a reference model, runs up to two differential rounds with blind client adjudication, and runs the Slither static analyzer in report-only mode — its findings are never used to rewrite code.

**Statistics.** Intervals are 95% percentile bootstrap intervals over contracts (2,000 resamples, paired for differences), conditional on one generation per condition. The authors pre-set 36 pass/fail criteria and report that 18 were not met; ten criteria were committed together with their results and are marked as retrospective.

## Evidence

All results below are **author-reported** from this single study; no independent replication exists. Conditions differ across experiments (denominators run 92–100 of the development contracts, and 499 of 500 at scale), so conditions are stated with each result.

**The grading instruments fail on planted mistakes.** On 200 guard-removal mutants, Slither caught 1.5% — "the static analyzer was built for vulnerability classes, not intent." An LLM judge reading the code caught 65.0% of 40 mutants but flagged 80% of untouched contracts; requiring the judge to produce executable proof cut false alarms to 40% but also cut catches to 30.0%. A black-box LLM tester caught 17.5% at a 40% false-alarm rate. A reference model written from the description caught 94.3% on 66 held-out contracts — but a reference model written from function names alone caught 87.5%, which the authors call the conventions shortcut: most of what such an oracle rewards is knowledge of conventions any capable model has, not understanding of the description. The original pipeline's self-grading rubric judge, in its earlier evaluation, correlated with the aggregate of three human raters at only r = 0.15.

**Where information is lost, measured on reference models.** On 100 fresh contracts with 279 planted contract-specific mistakes, a reference model written from the short description catches 65.9% of exposed mistakes, versus 87.5% from the complete requirements — a gap of 21.6 points [15.1, 29.3]. Checklist answers recover the full gap (89.4% vs 88.9% for the complete document). A targeted interviewer that asks about whatever it judges unclear recovers only part of it (80.4%), and adding extractor/critic, reviewer, or ensemble agents on top changes nothing (−1.0, −2.5, and 0.0 points respectively).

**Generated contracts: elicitation dominates.** With generator GPT-5.4-mini on 92 contracts, transaction-level fidelity is 55.6% from the short description, 76.0% with checklist answers, 79.4% with interviewer answers, and 91.0% from the complete document. Unlike for reference models, neither elicitor closes the gap for generated code, and checklist contracts implement fewer required signatures (88.7%, vs 94.8% interviewer and 95.3% complete) and expose fewer of the original's values (78.6% vs 92.0% and 98.6%) — the answers describe behavior, leaving argument types and stored values to the generator's guesses. The checklist gain replicates across model families: Claude Sonnet 5 rises from 56.1% to 75.1% (+19.0 [15.1, 23.0]) and Gemini 3.5 Flash from 51.8% to 74.5% (+22.7 [17.7, 28.1]). Contracts passing all sampled tests: 59% from the complete document vs 21% from the short description.

**The descriptions themselves are part of the problem.** An auditor model found at least one contradiction with the contract in 76 of 100 short descriptions (most often an invented access rule) and an average of 14.9 omitted contract-specific rules per description, so elicitation often corrects misinformation as well as filling gaps. On the 24 contradiction-free descriptions the checklist gain is still +24.9 points [14.1, 36.9]. In the paper's sharpest single case, one answer to the "anything unusual" question — all operations open to any account; no token accounting exists — raised a contract's fidelity from 25% to 100%.

**How many questions are needed.** Ordered best-first (cross-fitted), three questions reach 68.2% fidelity, recovering about 62% of the ten-question gain; five reach 70.7%, about 74%. The first three checklist questions in fixed order recover only 37%. The strongest single questions are roles (+5.8), failure conditions (+5.3), and anything unusual (+5.2); fees, prices, and time windows add little on average. A label-free *separation score* — how often the contract written with an answer behaves differently from the one written without it — needs the client's answer but not the original contract, and ranks the ten questions much as their measured gain does (Spearman ρ = 0.92). Adaptive agents that choose their own questions or stopping points do not reliably beat the fixed checklist; in the authors' summary, "LLM judgments help choose and phrase questions but are not calibrated for sufficiency."

**Post-generation stages add little — and the security loop subtracts.** Given complete requirements on 94 contracts, generation alone scores 95.3%; after the original pipeline's security audit and refinement loop, fidelity falls to 82.5%, a loss of 12.8 points [9.5, 16.3], with 60 contracts worse and the pass rate collapsing from 62% to 23%. An LLM classification of 341 sampled changes from the refiner (explicitly not human-verified) finds 80% break a stated requirement, 14% block a genuine vulnerability the requirements do not ask for, and 6% are not decided by the requirements; 44 of the 49 justified fixes add a restriction that could instead have been put to the client as a question. Repairing contracts where they disagree with a reference model has no detectable effect on real defects (−0.2 [−0.8, 0.2]): on real generation defects the complete-description reference model sides with the original only 31.6% of the time, worse than the uninformed always-succeed oracle at 80.4%, because residual defects are mostly conservative checks the description never mentions, which a model written from the same description repeats. Its flags are still an elevenfold enrichment over the 3.2% defect base rate (34.8% of flags mark real defects) — which is why the new pipeline routes flags to the client as questions instead of acting on them. A factorial run confirms the ordering: checklist answers lift a one-shot generator by 21.0 points but the original pipeline by only 8.4 [3.3, 13.2], while verification plus client triage adds +0.1 without answers and +0.5 with them.

**Scale replication.** On 499 held-out contracts, elicitation-first scores 72.9% transaction-level fidelity, vs 53.9% for one-shot generation and 39.3% for the original pipeline — gaps of +18.9 [16.6, 21.3] and +33.5 [30.7, 36.5] respectively; the original pipeline trails even one-shot by 14.6 points, about half of that from outputs that never build. Client triage adds +0.7 [0.3, 1.2], detectable but below its pre-set threshold and flagged provisional (see Limitations). The absolute level remains low: the best pipeline passes all sampled tests on only 19.6% of contracts and implements 84.7% of required functions, and 45% of its failed steps are calls to functions the contract lacks or with wrong argument types.

**The scoring rule moves the headline.** Scoring the same 500 output sets four ways: under a shared-interface metric (only functions all systems implement, contracts where all build), elicitation-first scores 95% vs the original's 76% — a 19-point gap on 364 contracts. With a fixed required interface the gap is 35 points on 499 contracts; under exact replay, 34. The authors' previous scorer passed 43.9% of the elicitation-first pipeline's contracts, but 162 of those 219 passes had an unobserved value or a missing or mismatched function. Rankings are stable across every scoring rule tried; absolute fidelity values, gap sizes, and pass rates are not, and the paper argues they should always be reported with interface and observation coverage.

## Limitations

**Author-acknowledged.** The central caveat is the simulated client: because the client answers by reading the original contract — the same artifact fidelity is scored against — the elicitation gains are, in the authors' own words, optimistic estimates of what a human author would provide under this simulator, not measurements of it. No human answered the questions; real authors may be unsure, inconsistent, or may volunteer more. There are no independently authored specifications or expert-written tasks, and no controlled omission-only condition. Fidelity is not intent: the original contract is treated as intended behavior even where it lacks access control. The pipeline baseline is the authors' own earlier system plus one-shot generation — the established clarification systems ClarifyGPT and TiCoder are cited but not run as baselines. All contracts come from one corpus (FSM-SCG) and one language (Solidity), and the corpus itself is noisy ground truth (35.1% of its contracts contain placeholder markers). Catch rates are over *exposed* mistakes only; counting mistakes no sequence exposes, the best oracle's rate over all 279 planted mistakes is 65.2%, not 87.5%. Observations exclude events and ether received by external accounts. Two load-bearing quantities — the 80/14/6 classification of the security refiner's changes and the audit finding contradictions in 76 of 100 descriptions — are single-model LLM judgments (GPT-5.4), explicitly not human-verified. The +0.7-point triage increment is provisional: the pipeline's verification stage ran before a reference-model runner bug (state not restored on revert) was fixed and was not rerun. Intervals omit generation variability, the 36 criteria are uncorrected for multiplicity, and ten of them were committed together with their results.

**Analyst-assessed.** The evaluation has a self-referential structure: the baseline pipeline, the benchmark that previously evaluated it, and the proposed elicitation-first pipeline are all the same author team's systems, so the headline 33.5-point gap is partly a comparison against the authors' own prior design; the cleaner external anchor is the 18.9-point gap over one-shot generation, which the authors themselves call the informative one. The LLM-judged quantities noted above come from the same model family that also serves as simulated client, auditor, and question agent, so correlated judge bias cannot be excluded. Experiment denominators drift (92, 94, 96, 100 contracts across development experiments) because stages include only contracts whose earlier stages produced output, which cross-experiment comparisons inherit. The paper also contains a minor internal inconsistency: the question-agent results are stated over 92 contracts in one place and 93 in another.

## Competing approaches

The paper situates itself against several lines of work, most of which it audits or cites rather than benchmarks against directly. Clarification systems — ClarifyGPT and TiCoder — ask users clarifying questions before generation and carry human evaluations, but were not run as baselines here. Solidity evaluation benchmarks include SolEval and SolBench (function completion), SolContractEval (replay of historical transactions against a reference), and SolBehave (differential fuzzing of regenerated contracts against the originals); this paper's contribution relative to them is a study of the scoring rules and instruments themselves. Approaches that delegate the verdict to a non-LLM checker include SymGPT (symbolic execution plus LLM) and PropertyGPT (retrieval-augmented property generation for formal verification, NDSS). Oracle-generation and consistency approaches include ALGO (LLM-generated oracle verifiers), Clover (consistency checks), and DiffSpec (specification-guided differential testing), on foundations of differential testing (McKeeman 1998) and mutation testing (Jia & Harman 2011). On the security side, the paper's finding that automated fixes break stated requirements echoes repair benchmarks (Huang et al. 2026; Zhang et al. 2024, including the access-control repair system ACFIX) reporting that security patches often break legitimate behavior. Other multi-agent Solidity synthesis systems (the FSM-SCG system itself, SolAgent, and a Lean-verified multi-agent system) provide context but are not the comparison target; the comparison target is the authors' own prior pipeline.

## Implications

For agent builders, the study's ordering is stark: in this testbed, information obtained *before* generation is worth roughly twenty points of fidelity, everything after generation is worth at most about one — and an automated repair loop acting on unstated requirements is worth negative twelve. A fixed, well-chosen checklist beat an adaptive interviewer for reconstructing rules, and the questions' order matters as much as their content; the separation-score result shows that order can be learned from client answers alone, without ground truth, which makes the method portable to domains with no original implementation to score against. For evaluation design, the planted-mistake audit is the transferable artifact: any judge, analyzer, or tester proposed as a quality gate can be subjected to the same twin-and-mutant protocol with strict side-picking, and a 65% catch rate at an 80% false-alarm rate should disqualify a gate that looks respectable on catch rate alone. The metric-sensitivity results argue that fidelity numbers should never be reported without the scoring rule and the interface and observation coverage beside them — a shared-interface convention silently erased 16 points of a real gap by discarding exactly the functions the weaker system omitted. For security automation specifically, the constructive proposal is to convert auditor findings into client questions rather than code rewrites: 44 of the 49 justified fixes in the study were restrictions a client could have confirmed or rejected in one answer. ## Reproducible experiment

A scaled-down replication can be run from the method as described in the paper's appendices, without the authors' code. Take roughly 25 real Solidity contracts of at least 40 lines with contract-specific rules; write a client-style description of about 140 words for each. First, audit your grading stack: plant one-rule mutations with untouched twins, and measure each instrument's catch rate and false-alarm rate under strict side-picking, including a reference model written from function names alone as the conventions control — the paper predicts the names-only model will capture most of the with-description catch rate, and that LLM judges will show high false-alarm rates. Second, generate contracts from the description alone and from the description plus answers to the ten checklist questions (Appendix F of the paper), and score both by exact replay: 60 sequences of 8 transactions, each chain continuing from its own state, the original's signatures and ether amounts used exactly, and any value change the generated contract does not expose scored as incorrect. The paper predicts a checklist gain in the high teens of points, little or no additional gain from any post-generation verification stage, and a measurable fidelity *loss* if an LLM security auditor is allowed to rewrite the code against requirements it was never given. One reproducibility caveat: the paper's artifact repository (an anonymized link printed in the paper) returned HTTP 401 when accessed for this review and was not inspected, and it excludes the original pipeline's code in any case — so this protocol is reconstructed from the paper's text, and re-generation of the original baseline from the release alone is not possible.

## Evidence status

Every quantitative result on this page is author-reported from the single study above; no independent replication was found, and none is claimed. The paper was read in full on 2026-11-02, including appendices (system architecture, all 36 pre-set criteria with outcomes, measurement details, prompts, and resource documentation). The paper states that an artifact repository contains per-contract sources, generated and repaired contracts, and scores; that repository was **not inspected** — its link returned HTTP 401 at review time — so its contents are reported here as paper-stated only, and the page makes no claim that any repository was tested or any benchmark reproduced. The paper contains no vendor claims; model names (GPT-5.4, GPT-5.4-mini, Claude Sonnet 5, Gemini 3.5 Flash, Gemini 2.5 Flash) are experimental conditions. The paper's suggestion that web agents acting on user requests share the same failure modes is explicitly labelled by the authors as a hypothesis they have not tested, and is recorded here as speculation, not as a result.
