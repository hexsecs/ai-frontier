# Tracybot

## What it is

Tracybot is an open-source tracing tool that links LLM-generated source lines back to the conversation that produced them, and can export a conversation-derived record of a design decision. It is reported in the arXiv preprint "Tracybot: Preserving Developer Intent by Tracing Agent-Generated Code to Prompts" (arXiv:2611.09395, submitted 6 November 2026; cs.SE and cs.HC; preprint, no peer-reviewed venue is claimed). The paper lists seven authors — Răzvan Albu, Aliaksei Khval, Maxine Orlova, Danis Music, Filipe Araújo Veras Rosa, Lirong Yi and Ranim Khojah — affiliated with the University of Gothenburg and, for the last two, also with Chalmers University of Technology. The paper links the open-source tool at https://github.com/TracyTeam/tracybot and a demo video at https://youtu.be/Vg_a1F5eO04. An earlier artifact by the same group is a BSc thesis, "Tracybot: tracing LLM-generated code to prompts" (University of Gothenburg, 2026).

The problem it names is that in agent-assisted development the decisions and intent behind a change stay in the conversation, with no link to the code they produced — teammates cannot see it and it is easily lost. The paper cites Storey's term **intent debt** for the absence of explicit goals, constraints and rationale, and argues that intent is best documented at the moment a decision is made because recovering it later is difficult. Two pressures are named: regulation such as the EU AI Act pushes companies toward explicit AI crediting, and an eye-tracking study by the authors' own group (Khojah et al., ASE 2026) found that practitioners changed their reviewing behaviour when code was labelled as AI-generated, some using the prompt to guide their review — which the paper reads as an argument for treating the prompt as a software artifact. The paper's framing is that a label says how much of the code an agent wrote, while the prompt says *why*.

The tool records each change as a **Tasklet**: the build prompt that changed the code, the planning prompts that preceded it without changing any files, the agent's responses, and the resulting code changes. Its two headline features are (i) mapping line-level code changes made by coding agents to the Tasklets that produced them, and (ii) exporting a Tasklet as a decision record when the decision concerns the architecture of the project.

## Mechanism

The paper describes three components (Fig. 1): agent plugins, a tracing backend, and a VS Code extension. The tracing logic is deliberately separated from the plugins and the extension so that supporting another agent or editor requires only a thin adapter. The repository layout matches that split: `opencode-plugin/`, `claude-code-plugin/`, `codex-plugin/`, `vscode-extension/`, `tracking/`, `init.py` at the root, plus a `research-collector-worker/` and `docs/adr/`.

**Agent plugins.** Tracybot supports OpenCode, Claude Code and Codex, one plugin per agent, each with two parts: an *agent adapter* that records what happens during a session, and a *Tasklet builder* that groups the conversation and passes it, with the code changes, to the tracing backend. The adapter depends on what each agent exposes: OpenCode loads plugins into its own process and exposes the full session through its SDK, so the adapter can read every message directly, while Claude Code and Codex run *hooks* — short external commands triggered at fixed events such as after a file is edited or when the agent finishes a reply — so their adapters read prompts from the agent's transcript and the response from the final event. The Tasklet builder decides grouping: developers often discuss a change over several prompts before asking for it to be applied, and the final request is often a short instruction like "go with the first option", so recording only that request would lose the intent-bearing prompts. For OpenCode the builder uses the agent's Plan and Build modes to separate the two; Claude Code and Codex have no such modes, so their builders treat **up to five earlier prompts in the same session that changed no files** as planning prompts. The repository's `opencode-plugin/src/Tasklet.ts` defines the corresponding record type: a `Tasklet` with `id`, `sessionId`, optional `title`, arrays of `planOutputs`, a single `buildOutput`, and `questions`; each output carries `id`, `model`, `prompt`, `response`, `promptCreatedAt` and `responseCompletedAt`, and each question carries `header`, `options[{label, description}]` and `answer[]`.

**Tracing backend.** A Python script plus a set of Git hooks handle three events: an agent edit, a commit, and a history rewrite. *Snapshot creation*: right after the agent changes files, the backend stores the state of the tracked files as a hidden snapshot commit under `refs/tracy-local/*`. A snapshot of the developer's state is taken just before the agent's edits and at each pre-commit hook, so an agent snapshot contains only the agent's changes. The snapshots form a chain that never appears in branch history, so commits, `git log` and `git blame` stay as they would be without Tracybot; the chain is kept local because it may contain changes that are never committed. *Commit linking*: the post-commit hook links the new commit to its snapshot chain with a **Git note**, filters the chain to keep only snapshots of files that are part of the commit, stores the result under `refs/tracy`, and removes the raw local chain; only `refs/tracy` and the notes are pushed, so uncommitted or sensitive files are not shared. *History rewriting*: a post-rewrite hook merges tracking chains and attaches a new note to the rewritten commit, so it stays linked to its original snapshots.

Repository inspection of `tracking/tracy.py` establishes the mechanics of the snapshot: it captures the working tree (or, with `--index-only`, the staged index) into a tree via a temporary `GIT_INDEX_FILE` and `git add -A` / `git write-tree`; it skips work entirely when the tree is unchanged or matches the latest hidden snapshot; it reuses or creates a Tracy ID in `git config tracy.current-id` (a lower-cased UUID4); and it creates the snapshot with `git commit-tree`, parenting it on the previous hidden snapshot, or on the visible HEAD when the chain is empty. `tracking/hooks/post-commit.py` establishes the promotion step: it walks only hidden snapshot commits (`git log <local_ref> --not --branches --not --tags`, further excluding `ORIG_HEAD`), skips commits that carry notes (that is, user commits), filters each snapshot down to files present in the user's commit, rebuilds trees from the parent tree so unrelated files are preserved, writes the chain to `refs/tracy/<tracy-id>@<short-sha>`, attaches the note `tracy-id: …`, and deletes the local ref only when the working tree is clean. `tracking/README.md` documents the surrounding mechanics: `init.py` installs seven hooks (`pre-commit`, `post-commit`, `post-rewrite`, `post-fetch`, `reference-transaction`, `post-merge`, `pre-push`), local notes live in `refs/notes/commits` and remote-tracking notes in `refs/notes/origin/commits`, and the two are merged with `--strategy=union`, so a note present on only one side is preserved and conflicting notes are concatenated rather than discarded.

**VS Code extension.** On activation the extension checks that the opened project is a Git project, then offers to initialise it, which installs the backend's Git hooks and the plugins of the detected agents. *Line attribution* rebuilds the file's history from the normal commits, the Git notes and the snapshots, follows each line through that history, filters out changes made by the developer, and maps the remaining LLM-generated lines to their Tasklets; because the local snapshots are reachable through the refs, the mapping is available before the developer commits. Small developer edits — formatting, renaming — should not flip attribution from agent to human, so the extension compares the old and new content of each changed block (Git hunk) with BLEU similarity and a change above the similarity threshold (0.75, configurable) does not change the attribution. *AI Blame view*: a separate read-only tab beside the editor highlights LLM-generated lines; clicking one selects its Tasklet and shows the full prompts and responses, each message labelled Plan or Build, with clickable chunk ranges to jump to the other lines the same Tasklet changed and a list of the previous Tasklets for that line; an *All Tasklets* view lists Tasklets whose lines no longer exist. *Decision record export*: from the AI Blame view a Tasklet can be turned into an architectural decision record in the common MADR format, stored by default in `docs/adr`.

Repository inspection of `vscode-extension/src/utils.ts` pins the attribution heuristic precisely: `SIMILARITY_THRESHOLD = 0.75`; `bleuSimilarity` calls `bleu(tokenizeHunk(oldText), tokenizeHunk(newText), 4)` from the `bleu-score` package, i.e. character-level 4-gram BLEU, where `tokenizeHunk` strips a leading `+`, `-` or space diff marker, removes all whitespace and splits into individual characters; and `computeHunkSignificance` marks a hunk significant when its score is **at or below** 0.75, treating addition-only hunks as significant because BLEU has no reference to compare against and deletion-only hunks as significant because BLEU has no hypothesis to compare. A hunk above the threshold is therefore not significant and the attribution is preserved; a hunk at or below it is significant and the attribution changes.

Repository inspection of `vscode-extension/src/adr/buildAdr.ts` establishes that ADR export is deterministic and model-free: the file's own header comment states that everything is either copied from what Tracybot recorded or computed from the code, with the parts needing judgment left as TODOs. Concretely it caps excerpts at 600 characters and shown planning messages at 6, derives the title from the first non-URL line of the tasklet (80-character cap), writes frontmatter with `status`, `date`, `tracybot-tasklet`, `tracybot-status-basis`, and optionally `tracybot-agent`, `tracybot-model`, `tracybot-session` and `tracybot-commit`, renders *Context and Problem Statement* from the planning and build prompts and the agent's responses (quoted and redacted), renders *Considered Options* and *Decision Outcome* from the recorded questions and their chosen answers, and leaves *Decision Drivers*, *Consequences* and *Pros and Cons* as explicit TODOs. It also emits an *Evidence* table of files, lines in use and lines overwritten. The paper states the status lifecycle as *proposed* until the code is committed, *accepted* after that, and *superseded* once none of its lines remain; the ADR builder takes that status from a `computeTaskletStatus` helper (in `vscode-extension/src/adr/status.ts`, not inspected here) and records the basis of the computation in a `tracybot-status-basis` frontmatter line, refreshable by the "Tracybot: Refresh ADR Status" command without touching the record body.

## Evidence

All numbers in this section are **author-reported** from the single preprint; none has been independently replicated.

**Setup.** Tracybot was built in a two-cycle design science study. After the first cycle the authors held a semi-structured focus group with **five practitioners and two software engineering students** (seven participants in total) and demonstrated the tool on an example repository. After the second cycle, **24 participants** answered a survey; they judged screenshots of **five attribution scenarios** and rated the interface on a six-point scale.

| Item | Author-reported result |
|---|---|
| Focus group | 5 practitioners + 2 software engineering students (7 participants) |
| Survey participants | 24 (19 with at most two years of professional experience, 4 with 3–5 years, 1 with more than five) |
| Interface intuition rated 4 or higher (of six) | 17 of 24 (70.8%) |
| Tasklet design rated 4 or higher as a representation of intent | 21 of 24 (87.5%) |
| Scenarios where more than 83% agreed with the attribution shown | 4 of 5 |
| Participants' qualitative preferences | separate read-only tab over in-editor decorations; Git notes and hidden refs seen as safe; requests for attribution updates on user edits, Tasklet history, and marking/saving useful prompts (the last leading to the decision-record feature) |

The survey percentages are agreement with screenshots, not measured attribution accuracy: the paper reports no precision, recall or coverage figure for the line-to-Tasklet mapping, and the 83% figure is a per-scenario agreement rate with a traceability display, not a score against ground truth.

**Repository evidence.** The inspected tree establishes what the code is built to do, and nothing more. It contains unit tests alongside the implementation — `claude-code-plugin/src/{index,state,tracy,transcript}.test.ts`, `codex-plugin/src/{state,tracy,transcript}.test.ts`, and in the extension `src/test/{adr,adrCommands,buildHistory,extension,researchMode}.test.ts` plus per-module tests — and GitHub workflows that build each plugin and the extension (`build-oc.yml`, `build-cc.yml`, `build-codex.yml`, `build-vs.yml`, `release.yml`). These are tests of the tooling's own behaviour. The inspected code contains no ground-truth corpus, no benchmark harness, and no measurement of attribution correctness, Tasklet-grouping correctness, or the effect of having a trace on review outcomes; none of the paper's survey or focus-group numbers are reproducible from the repository alone.

## Limitations

**Stated by the authors.** Tracybot supports a limited number of agents and one editor. It traces only code generated through the agent integration and does not attempt to detect other AI-written code. Committed changes under `refs/tracy` are not automatically removed on tree rewrites, so the result can be unwanted dangling Git refs. The evaluation relied on a demonstration and screenshots: participants did not use the tool themselves. Future work is described as more hands-on — developers reviewing agent-written changes with and without Tracybot, to measure whether Tasklets and decision records improve their understanding of a change, and how full conversations compare with summaries — plus broader agent/editor support, a finer-grained attribution model, and rules for access to stored conversations. Participants additionally raised that the binary human-or-agent attribution is too simple for code an LLM wrote and a developer later modified (they asked for a layered view of authorship), that there is storage overhead for large repositories, and that traceability could be misused to monitor developers in software companies.

**Assessed from the reporting and the repository.**

- **Perception evidence only.** Both evaluation instruments are subjective and demonstration-based. A 70.8% interface-intuition rating and an 87.5% Tasklet-clarity rating are usability judgements about screenshots; neither is a measure of defect prevention, of provenance coverage, or of review quality. The paper itself names the hands-on review study as future work, which means the central benefit claim is currently untested.
- **No accuracy measurement exists in the source.** There is no reported precision, recall or line-coverage figure for the mapping, and no comparison of Tracybot's attribution against Git AI, Cursor Blame or PromptTrace on the same edits. The "more than 83% of participants agreed with the attribution shown" figure is the closest thing to a correctness signal and it measures agreement with the tool's own output.
- **The attribution heuristic is a similarity threshold, not a provenance oracle.** The inspected code decides whether a developer edit preserved AI attribution by a character-level 4-gram BLEU score of 0.75. BLEU is a bag-of-n-grams overlap measure: a developer rewrite that preserves n-gram overlap can keep AI attribution, and a formatting or naming change that breaks n-gram overlap can remove it. The paper's own participant feedback — that binary attribution is too simple for jointly authored lines — is a direct consequence of this design, and the "ghost line" machinery visible in `vscode-extension/src/history/buildHistory.ts` is a partial mitigation rather than a solved problem.
- **Tasklet grouping is agent-dependent and heuristic.** For OpenCode the plan/build split uses native modes; for Claude Code and Codex it is inferred from "up to five earlier prompts in the same session that changed no files". A build prompt that also edited a file, or a planning exchange separated by an unrelated edit, will group differently than a human would.
- **Provenance is stored in the same repository it describes.** Snapshots live under `refs/tracy-local/*` and promoted chains under `refs/tracy/*`, with prompts and responses in Git notes; the extension also offers an opt-in "Research Mode" that shares Tasklet history, and `vscode-extension/src/redact.ts` is used on the ADR path. The paper's own future-work list names "rules for access to stored conversations" as unsolved, and a participant warning that traceability could be misused for monitoring is unaddressed in the inspected code beyond redaction of exported excerpts.
- **Single source, but with a real artifact.** Unlike a paper-only project, Tracybot ships a working tool with tests and release workflows, so the mechanism is inspectable. That does not substitute for evaluation: the artifact demonstrates that the described plumbing exists, not that it improves anything.
- **Prior-art comparison is unverified.** The four-way differentiation against Git AI, Cursor Blame and PromptTrace (Table I, "as of October 2026") and the claim that "no other tool combines these features in the editor" are the authors' own; none of the three comparison tools was inspected here.

## Competing approaches

The paper's own comparison is Table I, "Tools that link code to prompts (as of October 2026)":

| Tool | In editor | Unit linked | What the user sees |
|---|---|---|---|
| Git AI | Yes | Agent session | Prompts summary |
| Cursor Blame | Cursor only | Agent session | Session summary |
| PromptTrace | Yes | Single prompt | Prompt and its diff |
| Tracybot | Yes | Tasklet (plan and build prompts) | Prompts and responses, lines it touched, and earlier Tasklets for the line |

The authors state four differences from that set, as author claims: a Tasklet links a line to exactly the planning and build prompt behind one change, whereas Git AI and Cursor Blame link to a whole session that may cover many unrelated tasks and PromptTrace links to a single prompt that can be uninformative when it is a short instruction relying on an earlier plan; Tracybot shows full prompts and responses rather than a summary, because a summary omits the options considered and the reasons for the choice; it keeps the history of Tasklets per line, so later changes do not hide earlier reasoning; and it exports a Tasklet as a decision record, which the authors did not find in the other tools. They state, as an author claim, that to their knowledge no other tool combines these features in the editor.

Cited as related work rather than compared head-to-head: Gotel et al. on traceability fundamentals, from which the paper takes the requirement-to-code lineage framing; Papineni et al. on BLEU, the similarity measure reused for hunk significance; Storey on intent debt, the problem framing; and the authors' own eye-tracking study of reviewing AI-labelled code.

Within this knowledge base, Tracybot sits on the intent-and-provenance side of a small cluster: [[projects/procgrep]] fingerprints the *procedure* an agent followed, [[projects/receipt]] supplies *process-state* evidence that a command actually did the work it claimed, and [[projects/cheme-as-code]] is an analyst-level comparison rather than a source-cited one. The shared question across all three is the [[concepts/verified-completion-vs-apparent-success]] problem: a reviewer's or reader's belief about what happened is not the same as a recorded fact about what happened.

## Implications

The following is analysis by the KB maintainers, not a claim of the authors.

The most transferable idea is not the tool but the *unit of attribution*. Git blame attributes a line to a commit; Tracybot attributes it to a Tasklet — a set of prompts and responses that constitute one decision. That is a smaller and more meaningful unit than an agent session, and it is the unit a reviewer actually wants. Any provenance system for agent-assisted work should be designed around the decision, not the conversation: the paper's argument that a summary loses the options considered and the reason for the choice is the load-bearing observation, and it maps directly onto the KB's own need for excerpts rather than paraphrases.

Second, the design keeps provenance *out of the user's history* by using Git's own extension points — hidden refs, Git notes, hooks — rather than a separate database or a service. The practical consequence, visible in the inspected hooks, is that provenance is versioned, diffable and forkable with the code it describes, and that a contributor who never installs Tracybot simply sees an ordinary repository. The cost is that the trace is only as durable as the refs, and dangling `refs/tracy` after tree rewrites is a known rough edge the authors list.

Third, the BLEU threshold is a useful negative example. It is the right *kind* of mechanism — an explicit, configurable, stated criterion for whether a developer edit destroyed agent authorship — but it is the wrong *measure*, because n-gram overlap is insensitive to meaning and sensitive to formatting in opposite directions. The paper's own "layered view of authorship" request is the natural fix, and any team adopting provenance tracking should expect to replace the similarity function with something structural (AST-level edit classification, or an explicit human attribution event) rather than tune the threshold.

Fourth, and most important for assessment: this tool produces a record, not a guarantee. A trace that says which prompt wrote which line makes a claim reviewable; it does not make the code correct, and the paper's evidence base is perception of clarity rather than correctness of attribution or of the resulting code. The appropriate adoption posture is therefore "make the claim inspectable", and the appropriate measurement is whether reviewers *act* differently — which the paper identifies as its own next step and has not yet done.

## Reproducible experiment

The artifact exists, so an independent check means using the released tool rather than reimplementing it. No such check is executed here; this is a proposed protocol.

1. **Ground-truth attribution audit.** In a scratch repository, drive a supported agent (OpenCode, Claude Code or Codex) on a task that touches several files, and keep an independent ledger of the exact lines the agent wrote (from the agent's own patch output, not from Tracybot). Then make three kinds of developer edit: (a) whitespace/formatting only, (b) renaming, (c) a full rewrite of one function. Compare Tracybot's AI Blame attribution against the ledger line by line, reporting precision, recall and the count of lines whose attribution flipped in each condition. The paper's design predicts flips only in (c); a material number of flips in (a) or (b) would falsify the 0.75 BLEU rule as a proxy for "small edit" — the specific claim the participants' feedback also doubts.
2. **Tasklet grouping check.** From a session with a multi-prompt planning exchange and a final "go ahead" build prompt, verify that the resulting Tasklet contains the planning prompts (and, for OpenCode, that Plan/Build modes are respected) and that a build prompt which itself edited a file is handled as the paper describes. Compare the grouping to a human reading of the transcript.
3. **Comparison against the alternatives the paper names.** On the same repository and the same agent session, run Git AI and PromptTrace if installable, and record the unit of attribution each exposes (session, prompt, Tasklet) and what a reviewer sees. This directly tests the Table I differentiation claim, which is currently author-asserted.
4. **Usability replication and, if feasible, the study the paper defers.** Recruit a comparable number of practitioners, show the same kinds of screenshots or a live demonstration, and re-measure the two headline ratings (interface intuition, Tasklet clarity) to see whether they land near 70.8% and 87.5%. A genuinely informative version would be the paper's future work: have reviewers work through the same agent-written change with and without Tracybot and measure comprehension of the change, which is the claim that would justify the tool.
5. **Dangling-ref and privacy check.** Amend and rebase commits in a scratch clone and check whether `refs/tracy` accumulates stale refs as the limitations section warns, and whether uncommitted or sensitive files ever reach a promoted chain or a pushed note.
