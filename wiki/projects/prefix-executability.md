# Prefix Executability

## What it is

Prefix Executability is an **evaluation protocol** for tool-using agents, proposed by Amir H. Rezaeian, Weiyi Sun, Yassine Benajiba, and Dan Roth of Oracle AI in an arXiv preprint submitted 29 October 2026 (arXiv:2610.40444; the work was funded by Oracle and no venue is stated). Its target is a blind spot in how tool-use benchmarks are usually scored: by final task success alone. A terminal outcome, the authors argue, "can obscure whether the intermediate tool-call trajectory was executable" — a later call "may be syntactically well formed but non-executable if it references a stale identifier, skips a required precondition, or applies an update before the corresponding state exists; a subsequent repair can still produce the desired final state while hiding where the trajectory first became invalid."

The protocol scores a predicted tool-call sequence prefix by prefix: is every initial segment of the trajectory still executable under the tools' schemas, state preconditions, and data dependencies? It separates three questions that a single success bit conflates — how long the rollout remains valid, where validity first breaks, and whether later actions recover from the break. It is deliberately reference-free: it "credits alternative executable action sequences without requiring one gold path and records first failure, survival, and recovery."

Two clarifications matter for reading the rest of this page, because an earlier summary of this work blurred both. First, the contribution is the *measurement*, not a runtime validator: the protocol is applied retrospectively, by a deterministic benchmark-side replay scorer, to trajectories agents have already emitted. Second, the paper does study one intervention — Dual-Loop, a pre-execution plan-validation architecture — but explicitly as "a controlled probe" of whether validation moves the new metrics, not as the contribution itself. As the Evidence section shows, the probe's results are the weakest part of the paper, and the authors say so themselves at unusual length. The durable claim is the measurement divergence: final success and prefix executability rank the same agents differently, and on some benchmarks they are barely related.

## Mechanism

**Executable prefixes.** A rollout is a predicted trajectory τ̂ = (a₁, …, a_T), where each action a_t is a tool invocation with arguments and s_t is the environment state immediately before it. "An action is executable if the selected tool is available, the arguments conform to its schema, all explicit preconditions hold in s_t, and any referenced intermediate values are present and type-consistent." A prefix τ̂_≤k is executable if every action in it executes successfully under the states induced by the prior actions. "This definition evaluates feasibility rather than agreement with a single reference trajectory."

The scorer that operationalizes this is deterministic and uses no LLM judge. Per action, the predicate V_j = 1 exactly when the tool is exposed, the arguments satisfy the declared interface and its validators, referenced values are available and type-compatible, required information has been obtained, applicable state preconditions hold, and the benchmark accepts the transition. Replay initializes from the benchmark's initial state and stops prefix replay at the first failed predicate; the full rollout is retained so final success and recovery can still be scored. On BFCL v3 the predicate is grounded by replaying in a copied state under the case-specific function namespace and the benchmark's evaluator semantics; on ToolSandbox it uses the tools visible at the relevant turn, their registered validators, and the recorded execution outcome and state transition. Prefix validity is absorbing — once an action fails, every longer prefix still contains that failure — so a later repair counts as recovery but never restores prefix survival. Each first invalid action also receives one primary-cause label (schema, dependency, precondition, state-consistency, or information failure, assigned by a deterministic tie-breaking precedence in that order); the labels are diagnostic only and do not enter the metrics. One edge case: an agent that terminates without emitting any tool call is represented as a length-one terminal no-tool action, executable only if the benchmark permits completion without tool use.

**The metric family.** Four quantities summarize a cohort of rollouts:

- **FED (First-Error Depth):** the depth k of the first non-executable prefix; FED = T+1 if every prefix is executable. A prefix of length k is executable exactly when FED > k.
- **PEC (Prefix Executability Curve):** the fixed-cohort survival curve PEC(k) = Pr[FED > k], estimated with the denominator fixed at all N rollouts for the condition. There is no censoring correction: a rollout that terminated before depth k is simply outside the event {T ≥ k}, so PEC@k is a joint reach-and-validity statistic — a decline can mean agents stopped early, not only that a call was invalid. A conditional eligible-depth variant, PEC_elig(k), is reported as a diagnostic only.
- **TER (Trajectory Executability Rate):** TER = Pr[FED = T+1] — the probability that the entire trajectory is executable.
- **RR (Recovery Rate):** RR = Pr[Y=1 | FED ≤ T] — final success conditional on at least one invalid prefix. Its denominator, RR-Eligible = N(1 − TER̂), is always reported alongside, because RR conditions on *organically occurring* failures (unlike injected-fault recovery studies) and is meaningless without knowing how often the condition enters the failure regime at all.
- **AUC-PEC:** the horizon-normalized area E[(FED−1)/T] ∈ [0,1]; it equals 1 for fully executable trajectories and rewards later first failures.

The family has exact structure: 0 ≤ TER ≤ AUC-PEC ≤ 1, and final success decomposes as Pr(Y=1) = q·s + (1−q)·r, where q = TER, s is success given a fully executable trajectory, and r = RR. That decomposition is the analytical heart of the paper: it implies no monotone relationship between TER and final success, so the two axes can rank methods independently — which is what the experiments then exhibit.

**The Dual-Loop probe.** A planner proposes a structured plan from the user goal, tool schemas, and a compact state summary; an LLM verifier checks the plan against a five-item checklist (tool and schema validity; dependency resolution, rejecting forward references, stale bindings, and type-incompatible reuse; information availability; explicit preconditions; state consistency). If verification fails, the planner revises using the feedback, up to K_val = 5 candidate plans; the approved plan then conditions a ReAct executor, which alone issues environment tool calls. Planner and verifier messages are method-side computation, not benchmark tool actions, and all prefix metrics are computed on the executed trajectory only. If no plan is accepted, the executor still proceeds, without an accepted plan as a strong constraint, and the rollout is still scored. Execution is separately capped at K_exec = 10 ReAct iterations. The paper stresses that the verifier's acceptance "does not establish that the emitted trajectory is executable" — the deterministic replay scorer, not the verifier, is the arbiter.

**Evaluation setup.** Four agent variants form a nested ladder: (1) ReAct; (2) Prompt Planning, where a plan is generated but not enforced; (3) Plan-Conditioned ReAct, where the plan is an explicit control signal; (4) Dual-Loop. Three LLMs drive all roles — GPT-5.4 (reasoning effort high), GPT-4.1, and Llama-4-Maverick-Instruct — with the least-stochastic provider-supported decoding (temperature 0 where exposed) and a 4,000-token response budget per call. Benchmarks: BFCL v3 multi-turn (stratified sample of 200 tasks, 50 from each of four categories) and ToolSandbox (200 supported scenario templates), giving 200×2×3×4 = 4,800 rollouts; plus a transfer audit on τ³-bench v1.0.1 (all 50 Airline and 114 Retail base-split tasks, 1,968 episodes). The same task IDs are reused across models and methods, so comparisons are paired at task level — though uncertainty is reported as marginal 95% task-level bootstrap intervals (10,000 resamples; Wilson intervals for RR), with paired intervals reserved for the separate sensitivity study. The authors warn explicitly: "Marginal-interval overlap does not establish paired significance, and we do not infer paired effects from it."

## Evidence

All results below are author-reported point estimates; bolding in the paper's main table marks column maxima and "does not indicate statistical significance."

**The divergence headline.** On the two static benchmarks, conditioning execution on an unverified plan buys final success at the price of trajectories that are mostly non-executable. Under GPT-5.4, "Plan-Cond. ReAct reaches the highest or tied-highest final success on BFCL and ToolSandbox (0.94 and 0.69), but its prefix reliability is much weaker than Dual-Loop's: TER is 0.47 and 0.48, and AUC-PEC is 0.54 and 0.52. Dual-Loop instead attains TER of 0.94 on both datasets and AUC-PEC of 0.96 and 0.95." Final success says the two methods tie on BFCL (0.94 each); prefix metrics say one of them executed cleanly 94% of the time and the other 47%. The gap widens under weaker models: Dual-Loop exceeds Plan-Conditioned ReAct in TER by 0.61 under GPT-4.1 and by 0.83 under Llama-4 Maverick on BFCL, and by 0.61 and 0.71 on ToolSandbox.

**Success built on broken prefixes.** The Llama-4 / BFCL cell makes the decomposition concrete. "Of 200 episodes, 10 were fully executable and all 10 succeeded; 138 of the 190 episodes with a prefix failure also succeeded. Thus TER is 10/200=0.05, RR is 138/190≈0.7263, and final success is (10+138)/200=0.74. Fully 138/148=93.2% of successful episodes reached the objective after an earlier invalid prefix." A benchmark reporting only final success would describe this condition as a 0.74-success agent; prefix scoring describes it as an agent whose trajectories were fully executable 5% of the time and which succeeded by recovering. Both descriptions are true; they support opposite conclusions about reliability. Note also the asymmetry the table exposes: on BFCL, plain ReAct's recovery rate is 0.00 under all three models — under BFCL's replay semantics a prefix failure is almost never followed by success for the non-plan methods — while Plan-Conditioned ReAct recovers at 0.73–0.90. Plan conditioning looks less like carelessness and more like a generate-then-repair strategy that terminal scoring happens to reward.

**Early-depth collapse.** The survival curves show the failure is not a late-trajectory phenomenon. "BFCL PEC@4 for Plan-Conditioned ReAct is 0.42, 0.33, and 0.05 across the three model conditions, versus 0.82, 0.82, and 0.78 for Dual-Loop." Under Llama-4, Plan-Conditioned ReAct's PEC@1 is already 0.53 — it fails at the very first call in roughly 47% of episodes — before collapsing to 0.05 by depth 4. Dual-Loop's curves start at 0.97–0.98 and degrade gently. (The authors' caveat applies: PEC@k mixes reaching depth k with being valid there.)

**The counterweight, at full strength: the transfer audit.** On τ³-bench — an interactive benchmark where a simulated user gives feedback and state changes mid-task — the validation advantage does not replicate, and the paper reports this without softening it. With GPT-5.4, Plan-Conditioned ReAct again has the highest final success (0.51), but plain ReAct has the highest TER/AUC-PEC (0.95/0.95); under GPT-4.1, Prompt Planning leads final success (0.51) while ReAct leads TER/AUC-PEC (0.84/0.91); under Llama-4, Dual-Loop is the *lowest* of the four variants on TER, AUC-PEC, and final success simultaneously. The authors' verdict: "The Airline/Retail audit does not establish the consistent validation advantage observed on BFCL-v3 and ToolSandbox. A possible explanation is that BFCL emphasizes pre-specified composition, whereas interactive user feedback and state changes in τ³-bench can make advance plans stale. This is a testable interpretation, not an identified causal mechanism." The divergence thesis survives the audit — outcome and prefix rankings still separate — but the *intervention* thesis does not: whatever Dual-Loop's validation buys on static, pre-specified tasks, it buys nothing measurable in the interactive setting.

**The counterweight, continued: the paired sensitivity null.** The paper's only fully paired analysis varies the verifier while holding everything else fixed: same 164 Airline/Retail tasks, same GPT-5.4 planner and executor, an identical initial plan across conditions, 100,000 paired task-bootstrap resamples. The result is a null. "All paired 95% intervals for TER and AUC-PEC changes include zero. The GPT-5.4 verifier at K_val=5, for example, changes TER by +0.006 [−0.018,0.030] while adding 40.7k tokens and 176.9s" relative to its paired Plan-Conditioned rerun. Worse for the intervention story, two configurations significantly *reduce* final success: deterministic acceptance (the executor is simply told the plan was accepted, with no verifier call) lowers it by 0.073 [−0.140,−0.012], and a GPT-4.1 verifier at K_val=5 lowers it by 0.085 [−0.165,−0.006]. The authors again state the limit themselves: "These findings delimit the benefit of validation in this environment; they do not prove equivalence or isolate verification logic from extra computation." Costs complete the picture: in the τ³ audit, Dual-Loop's mean per-episode tokens and latency relative to Plan-Conditioned ReAct are approximately +3%/+22% (GPT-5.4), +12%/+7% (GPT-4.1), and −3%/−1% (Llama-4) — modest, but spent on an effect the paired study cannot distinguish from zero in that environment. Per-method cost telemetry exists only for the τ³ audit; the BFCL/ToolSandbox grid has aggregate runtime only.

## Limitations

The authors' Limitations section is unusually complete, and this page reports it before adding anything. On coverage: "The study is an audit rather than a complete leaderboard evaluation: BFCL-v3 and ToolSandbox each contribute 200 sampled tasks, ToolSandbox is restricted to supported local-tool scenarios, and τ³ coverage is complete only for the Airline/Retail base splits. Task-level intervals do not measure within-task repeated-seed variation." On the protocol's assumptions: "Executability assumes explicit schemas, preconditions, and benchmark-accessible state. Partially observed web or GUI environments may require state estimation or learned preconditions, and executability does not certify semantic correctness." On the intervention: "The intervention combines validation/revision with extra inference. The sensitivity study varies verifier capacity and budget, but its acceptance wrapper changes executor guidance; it does not fully separate validation logic from compute or context effects." And on scope, from the discussion of broader impacts: prefix executability "does not by itself certify semantic correctness, safety, privacy, or fairness" — an executable trajectory "can still be unsafe, biased, privacy-violating, or misaligned with user intent." The verifier itself "can miss hidden-state constraints, underspecified intent, or semantic requirements outside the tool interface, and can reject executable alternatives."

Several further constraints are evident on inspection. The headline divergence claims rest on point-estimate orderings with marginal confidence intervals; the authors decline to infer paired effects from them, so the main grid establishes that the rankings *differ as measured*, not paired-significant effect sizes. One rollout per task under near-deterministic decoding means within-task stochastic variation is unmeasured everywhere. The execution cap K_exec = 10 bounds trajectory length on the static benchmarks, so mean FED values (maximum ≈6.4) are relative to a short scored horizon. RR is easy to misread in secondary citation: Plan-Conditioned ReAct's high RR reflects entering the failure regime up to 190 times out of 200, and quoting RR without RR-Eligible would invert the conclusion — the paper guards against this, but downstream summaries may not. Finally, the Dual-Loop gains are environment-bound even within the paper: they appear on two static benchmarks emphasizing pre-specified composition, never on the interactive one. Any claim that pre-execution validation improves executability in general goes beyond what this paper's own transfer audit supports.

## Competing approaches

The paper positions prefix executability against prior *evaluation* protocols qualitatively — there are no numeric head-to-head comparisons against them; all numbers compare the paper's own four variants. Against reference-based exact-call and trajectory matching, prefix metrics are reference-free and localize the first invalid prefix instead of penalizing alternative executable trajectories. Against final success alone, they expose what the success bit hides — the paper's core exhibit. Step-wise skill decompositions such as T-Eval diagnose component abilities (planning, retrieval, instruction following) rather than executable-prefix survival. ToolSandbox's own milestone scoring checks required and prohibited state conditions but does not localize first non-executability over depth. Trajectory benchmarks that match against references or use LLM judges (TRAJECT-Bench, TRACE) trade determinism for coverage; prefix metrics are benchmark-grounded and judge-free. Process-reward benchmarks (ToolPRMBench, AgentProcessBench) assess step quality against learned models or human labels, where prefix metrics test execution feasibility directly. Procedure-aware evaluations such as the "corrupt success" audit cover procedural integrity alongside utility and efficiency; prefix metrics isolate feasibility alone. The closest relative is recovery evaluation under deliberately injected faults (Beyond Success Rate): RR here instead conditions on failures observed organically in the rollout.

The substantive competitor to the paper's intervention is inside its own ladder: unverified plan conditioning. Plan-Conditioned ReAct matches or beats Dual-Loop's final success in several blocks (BFCL GPT-5.4 tie at 0.94; ToolSandbox GPT-5.4, 0.69 vs 0.63; τ³ GPT-5.4, 0.51 vs 0.46) at lower cost — while scoring drastically lower on TER/AUC-PEC in the static benchmarks and no worse in the interactive one. One further alternative is acknowledged but not evaluated: schema-constrained decoding, which "can prevent malformed arguments, while prefix checking additionally covers object existence, provenance, state preconditions, and transition acceptance." The absence of that matched baseline is a stated gap, not an oversight the paper hides.

## Implications

For benchmark consumers, the immediate implication is interpretive: a final-success number is a mixture — Pr(Y=1) = q·s + (1−q)·r — of clean execution and recovery, and two systems with identical success can sit at opposite ends of that mixture. Where the deployment cares about the trajectory itself (auditable tool use, side-effecting APIs, settings where an invalid intermediate call is costly even if later repaired), TER, AUC-PEC, and first-failure depth are the relevant quantities, and this paper supplies a deterministic, judge-free way to compute them on two existing benchmarks.

For agent builders, the evidence cuts in an uncomfortable direction. The configuration that terminal scoring rewards most on static benchmarks — condition on a plan, recover freely — is the one whose trajectories are least often executable, and the obvious remedy, verifying the plan before execution, shows large gains exactly where the environment is static and pre-specified and no measurable gain where a user interacts and state shifts. Combined with the paired null, the paper reads less as an endorsement of pre-execution validation than as a demonstration that *which evaluation axis you choose decides which architecture looks best* — and that claims about validation need an interactive benchmark in the evidence set before they generalize.

For evaluation methodology, the transferable pieces are the discipline rather than the numbers: report the failure-regime size next to any conditional recovery rate; keep the scorer deterministic and separate from any model-based verifier being tested; and treat a transfer audit to a differently-structured benchmark as part of the claim, not an appendix afterthought. The paper models all three, including publishing the audit that undercuts its own intervention.

## Reproducible experiment

Two checks are extractable. The first is an arithmetic self-check against the paper's published tables, requiring no code: take the BFCL / Llama-4 / Plan-Conditioned ReAct row (TER 0.05, RR-Eligible 190, RR 0.73, final success 0.74) and verify (i) RR-Eligible = N(1 − TER̂): 200 × 0.95 = 190; (ii) the decomposition 0.05 × 1 + 0.95 × (138/190) = 0.74; (iii) TER ≤ AUC-PEC (0.05 ≤ 0.15), repeating (iii) across the main table. This verifies the metric family's internal consistency on reported numbers; it does not re-derive them from raw rollouts, which are not released.

The substantive check is a protocol replication. BFCL v3 multi-turn and ToolSandbox are public, and the scoring predicate is fully specified in the paper's §2 and Appendix C: run any agent with deterministic decoding on a subset (the 50-task multi_turn_base category is a natural start), log the predicted call sequences, then replay each sequence prefix-by-prefix — exposed tool, argument binding and validators, reference existence and type, information availability, preconditions, benchmark acceptance of the transition — stopping prefix replay at the first failure to record FED while retaining the full rollout for final success. TER, AUC-PEC = mean((FED−1)/T), and RR follow from the (T, FED, Y) records. The paper's Appendix C.2 contact-removal example — a rejected identifier argument, then search, then successful removal, with per-action validity (0,1,1) but prefix validity (0,0,0), FED=1, and Y=1 — serves as a unit test for an implementation. Exact numerical agreement with the paper's main table is not attainable: the stratified task-ID lists for the BFCL and ToolSandbox samples are unpublished (only the stratification rules are given), so a replication tests the protocol and the qualitative divergence, not the point estimates.

## Evidence status

Every quantitative result on this page is **author-reported**: all four authors are at Oracle AI, the work was funded by Oracle, and there is no independent replication. The paper releases **no code and no data** — no repository for the replay scorer, the instrumentation, or the Dual-Loop implementation, and no rollout logs or task-ID lists; the three benchmarks are pre-existing third-party artifacts. The protocol itself is specified completely enough (§2 and Appendix C) that an independent implementation is feasible, which raises the evidence ceiling for the *metric family* above what the unreleased code would otherwise allow; the specific point estimates, however, rest on the authors' uninspectable instrumentation and marginal-interval reporting. The paper's internal counter-evidence — the τ³ transfer audit and the paired sensitivity null — is reported above at the same prominence as its headline, because the authors reported it that way; a page that cited only the static-benchmark divergence would misrepresent the source.
