# FINCOSMOS: An Open-World Evaluation Paradigm for Agents in Finance

## What it is

FINCOSMOS is an open-world evaluation paradigm for language agents doing financial work, reported in the arXiv preprint "FinCosmos: An Open-World Evaluation Paradigm for Agents in Finance" (arXiv:2611.07464, submitted 5 November 2026; cs.AI, cs.CL, q-fin.CP; preprint, no peer-reviewed venue claimed). The paper lists seventeen authors: Yupeng Cao, Xueqing Peng, Lingfei Qian, Haohang Li, Yangyang Yu, Anke Xu, Wenbo Cao, Yan Wang, Yuechen Jiang, Yuyan Wang, Zhuohan Xie, Yankai Chen, Zehan Li, Jimin Huang, Xue Liu, Jian-Yun Nie and Sophia Ananiadou. The acknowledgment section states that the research was supported by the NVIDIA Academic Grant Program using 32K A100 GPU-hours on Brev, and thanks the Fin AI community.

The paper's argument is that existing benchmarks each close the world somewhere — fixing the task, the data or the timeline — and thereby *remove* the three silent failures the authors care about instead of measuring them: a strategy the user never asked for, unverified data, and a backtest that uses the future, each of which yields a report as convincing as a correct one. FINCOSMOS keeps all three open. A simulated user holds a hidden strategy; the agent receives no data and must acquire it from the Web; a fixed data cutoff turns respecting time into a checkable property; and grading needs no reference answer because programs verify point-in-time correctness and recompute every reported metric.

The authors state three contributions: the first open-world evaluation framework for agents doing financial work, together with a released benchmark of ten frozen tasks, the task generator, the evaluator and a public live leaderboard (https://leaderboard.fincosmos.com.co); an argument that each part of the design is needed; and an evaluation of four coding agents showing that none completes the workflow but that an agent can learn the tasks from the benchmark's feedback.

## Mechanism

The framework has three components. The **Strategy Generator** samples a hidden strategy and turns it into a task. The **User Simulator** plays the simulated user, who holds the strategy and reveals it only when asked. The **Evaluator** grades what the agent delivers and returns diagnostic feedback. The hidden strategy is *sealed*: only the simulator and the evaluator can see it, and no feedback to the agent reveals it.

**Task formulation.** A task is a triple τ = (p, b, c): a persona p, the hidden belief b, and test conditions c = (t_cut, A, T, Δ) fixing the data cutoff t_cut, the channels A through which the agent may reach data (but no data itself), the maximum number of agent turns T and the per-turn time limit Δ. These are frozen with the task so scores stay comparable.

**Sessions and deliverable.** A session is h = (u_0, a_1, u_1, …, a_n, u_n) with n ≤ T. The user opens with a vague request; in each turn the agent may use its tools freely for up to Δ and then returns a message m_t and a set of delivered files F_t (data tables, code, backtest results, reports). The session ends when the user is satisfied or a limit is reached and records one end reason. Agents connect through a generic interface with three calls — start, send, finalize — so any agent design can be evaluated. Only what the user receives is graded: the deliverable D = {m_t} ∪ ⋃F_t. The execution log and the agent's workspace are recorded too, but only to detect violations such as data postdating the cutoff; the paper states explicitly that they can make a check fail and never make it pass.

**Strategy space.** A hidden strategy fixes one choice for each of six components of a quantitative strategy: stock selection (factors in four families — fundamental value/quality/growth, technical momentum/short-term reversal/low volatility, information sentiment/analyst revisions/insider buying, biotech event catalyst proximity/FDA outcome/pipeline momentum — plus combination methods equal weight, IC-weighted, double sort, gradient boosting), market timing (buy-and-hold, moving-average crossover, time-series momentum, mean reversion, event-driven, sentiment timing; exposure all-in/all-out or continuous), portfolio construction (equal weight, market-cap weight, risk parity, mean-variance; covariance sample, shrinkage, factor-based), risk control (none, stop-loss with position caps, drawdown gate, volatility targeting, VaR/CVaR limit, tail hedge), execution (single fill, TWAP, VWAP, POV, implementation shortfall) and transaction cost (none, fixed basis points). Coherence rules C exclude nonsensical combinations — the paper's example is that risk parity and mean-variance weighting require a covariance estimator. The space has |B| ≈ 3.8 × 10⁶ strategies before parameter values are drawn. Each option carries a difficulty δ(o) ∈ {0, …, 3} and a strategy's difficulty is the sum over components. Sampling is seeded, so a strategy is reproducible and new ones can be drawn on demand; the released benchmark freezes the first ten sampled tasks (seeds 0–9) for the leaderboard.

**User simulator.** The simulator is a language model on Claude Opus 4.8 with low reasoning effort. Three personas are used — a retail investor, a generalist analyst and a biotech specialist — and their prompts forbid evaluation vocabulary such as "point-in-time" and "cutoff"; the user states the usable date in plain words and never says it will be checked. Let H be the items the belief voices, O ⊆ H the items in the opening request and S_t ⊆ H the items stated by turn t. The disclosure rule is S_t \ S_{t−1} ⊆ Q(a_t): after the opening, the user states only what the agent asks about or proposes. Asked for a specific value, the user gives it directly; when a proposal conflicts with the belief, the user objects and says what it wants; when a deliverable deviates, the user names the wrong part without restating the strategy. The simulator may close a session only when every core goal is met with cited evidence — a backtest of this strategy on real data whose return, Sharpe ratio, maximum drawdown and number of trades trace back to trade dates and prices, and a report covering summary, method, results and limitations.

**Evaluator.** Each session is graded on 45 dimensions in seven categories. Five categories are scored: data (6 dimensions, 1 veto), strategy (12, 7), backtest (8, 4), assessment (5, 1) and user experience (6, 2) — 37 dimensions on a 0–4 scale with an anchored description per level. Cost (3 dimensions) and process transparency (5) are reported but not scored. Program judges grade 17 dimensions, an LLM judge 19, and both together 6; where an LLM grade has a program counterpart, the program bounds it (s_j = min(s_LLM, s_P)), so professionalism cannot exceed the share of metrics that state their basis. Pre-veto quality is Q = (25/|K|) Σ_k (1/|J_k|) Σ_j s_j ∈ [0,100], giving every category equal weight. Fifteen dimensions are vetoes with pass thresholds θ_v; pass = ∏_v 1[s_v ≥ θ_v], Score = Q · pass, and AC = pass · 1[e = satisfied] · 1[grading complete]. Sessions that hit a turn or resource limit have no result and score 0.

**The four key check groups.** *Data provenance:* the agent receives no data, so every series it delivers must be traceable to a source such as a URL or an API call with its query parameters, and untraceable data earns no credit; programs also measure missing values, gaps, duplicates, stale prices and outliers. *Point-in-time correctness:* every dated row in the delivered data is dated no later than t_cut and a single late row fails the veto; every fill comes on a later date than its signal; fundamentals used at entry were announced no later than the entry date. *Independent recomputation:* the program does not trust the reported equity curve — it rebuilds returns from the delivered trade log, or from the weight log and prices, and compares every reported metric with its own value within fixed tolerances such as 0.02 for returns and drawdowns and 0.5 for the Sharpe ratio; a missing trade log or price series fails the veto. *Strategy fidelity and elicitation:* for each component, every item of H_k is checked against D, each claim must be backed by a quote found in D, and a later retraction cancels an earlier claim; the fidelity score is capped at 1 if any missing item was stated by the user and at 2 if the missing items were never stated, and with threshold θ_k = 2 a missing stated requirement fails the session.

**Feedback.** After a session the agent receives the score, source and evidence of every dimension. The feedback is *leak-free*: for the data and strategy categories, whose evidence would reveal the hidden belief, the agent receives scores without reasons, the single exception being point-in-time strictness, which depends only on t_cut. Program judges also score every turn, giving a per-session score trajectory, and a task may be attempted again. Every score is stored with the evaluator version and a hash of the scoring code so results stay comparable as the evaluator is refined.

## Evidence

All numbers in this section are **author-reported** from this single preprint; none has been independently replicated.

**Setup.** Four coding agents, each with a recent vendor model: Claude Code with Claude Opus 5.5, Codex with GPT-6.1 Sol, Gemini CLI with Gemini 3.8 Flash, and Kimi Code with Kimi K3 (open-weight). As a baseline, Claude Opus 5.5 answers the same requests without tools. Memory features are off, so nothing carries over between sessions. Each agent runs in a sandbox with the same environment and prompt instructions, is allowed to search and retrieve web pages and run code in its working directory, and is equipped with the "Financial Modeling Prep" MCP server containing 247 commonly used financial APIs; search and web-scraping tools come from the respective vendors. Each session consists of up to six rounds of 300 seconds. All ten tasks involve U.S. stock trading. The LLM judge runs on Claude Opus 5.5 through the Claude CLI with default settings. The protocol is ten tasks × three independent sessions per agent = 150 sessions. Differences between agents are tested with paired permutation tests over tasks with Holm–Bonferroni correction.

Codex (37.2) and Claude Code (37.1) are indistinguishable (p = 0.99); Codex scores above Gemini CLI (22.2) and the bare model (20.2) and both differences survive Holm correction (adjusted p = 0.02), while Claude Code's gap to the bare model does not (adjusted p = 0.10). Gemini CLI and Kimi Code (22.3) do not differ from the bare model, which has no tools at all (p ≥ 0.44). The bare model earns its quality from the strategy (49.8) and user-experience (44.6) categories, which reward a well-described plan, while scoring 0 on data and 4.6 on backtest. Quality falls with task difficulty (Spearman ρ = −0.24, p = 0.007), from 41.6 on tasks of difficulty up to 10 to 26.6 on tasks of difficulty 15 and above. Time is a binding constraint: 70% of agent turns run into the 300-second limit. Cost varies more than quality — Codex reads 3.2 M input tokens per session, nearly three times Claude Code for the same quality, while Claude Code is the most expensive at API prices ($2.24 per session against about $0.80 for the others).

**Silent failures.** The simulated user was satisfied in 35 of the 150 sessions (23%), and all 35 fail at least one veto, each caught by a program check. Most fail for substantive reasons: 29 delivered no trade log or no prices, so their returns cannot be rebuilt (veto 3.2); 15 used data after the cutoff or filled trades before their signal (1.1, 3.1); and 15 delivered a strategy other than the user's (2.1–2.7). 33 of the 35 fail at least one of these three. The two strict completeness checks — process completeness (3.8) and the verifier audit (3.7) — fail in nearly every session (120 and 119 of the 120 agent sessions) and do not separate the agents. Without them, 2 of the 150 sessions would be accepted, both by Codex. These sessions look convincing: their pre-veto quality is 50.8 against 21.0 for the other sessions of the four agents (p < 0.001), and their user-experience score is 69.6 against 35.0.

Had grading used only the vetoes the LLM judge decides (2.7, 4.1, 5.1, 5.6), 17 of the 35 sessions (49%) would have been accepted, so the acceptance rate would have been 11% instead of 0; in 10 of those 17 every failed veto is recomputation, the audit or the process check. By user sign-off Gemini CLI ties for first with 10 of 30 sessions, but none of them passes the LLM-judged vetoes (Fisher's exact test, p < 0.001), while Codex keeps 8 (p = 0.005 against Gemini CLI). The numbers in these reports also cannot be checked: in 29 of the 35 sessions no trade log or prices were delivered, and in the 5 sessions where the program could rebuild them, none matches the report. Against the agent's own equity curve, reported metrics match in only 10 of the 35 sessions; 11 contradict the curve and 12 report metrics without delivering one. The paper's worked example (Figure 1) is a Kimi Code session with a pre-veto quality of 47.9 in which the model ranks stocks by 21-day momentum where the user asked for short-term reversal, and the report gives a maximum drawdown of −18.96% while the delivered curve shows −21.91%, beyond the 20% stop the user asked for.

Agents break most often at the two ends of the workflow. Only 25 of the 120 agent sessions deliver the user's strategy, and none delivers trades that reproduce its reported returns: the 5 sessions whose returns can be partly rebuilt, all by Codex, score 1 of 4.

**Elicitation.** On average a task's belief voices 6.7 items, the opening request states 2.6–3.7 of them, and by the end of a session the user has stated 4.5–5.4. Agents therefore raise only 54–64% of the details they were not told, and the delivered strategy does not match 66–83% of the details that were never stated. More questions help: clarification coverage correlates with pre-veto quality (Spearman ρ = 0.25, p = 0.007). The fidelity vetoes fail in 38–52% of sessions for components with real choices, most often stock selection (52%), while the ambiguity veto (2.7), which requires one executable definition for every rule, fails in 68%; transaction cost, whose options are only none or a fixed rate, fails in 9%. Per-turn program scores show slow progress: failed program vetoes fall from 5.3 after the first turn to 3.8 after the sixth. Only 58 of the 120 agent sessions reach a fourth turn; of the 62 that end earlier, the user walks away in 51.

**Can the benchmark be trusted?** All 150 sessions are valid: the program validated every simulator decision before it reached the agent. Grading failed for 2 sittings, which were rerun under the same conditions. The 60 annotated sessions comprise 13 for each of the four agents and 8 for the bare model, stratified by end reason; agent names are masked and the experts see automatic grades only afterwards. Both experts flag a task-critical simulator error in the same 3 of the 60 sampled sessions, most often the user ending the session while the agent was still working; the user walks away in 41 of the sampled sessions, so at most 3 of these exits are premature. The experts attribute 53 of the 60 failed sessions (88%) to the agent, 3 (5%) to the simulator and 4 (7%) to the evaluator. On the calibration set the LLM judge agrees with the experts at κ = 0.87, close to the two experts' agreement at κ = 0.93.

**Learning from feedback.** A "Claude + Memory" configuration — Claude Code with a memory that persists across sessions — reads the leak-free report and per-turn program scores after each graded session and edits the memory before the next. No task is accepted at the first attempt and the median task fails 8 vetoes in its first session. The agent reaches acceptance on all ten tasks after a median of 34.5 sessions per task (range 12–132, 506 sessions in total), and every accepted session passes all 15 vetoes under the current rubric. For the median task the agent fails 6.3 vetoes per session over its first five sessions and 2.6 over its last five before acceptance; progress is not always smooth, and on three short runs the last five sessions fail as many vetoes as the first five or more before the task passes in a single step. Throughout practice the simulated user is satisfied in a median of 34% of sessions, long before the deliverable passes the vetoes. Of the 155 learning steps in the latest round, 115 (74%) edited the memory, with 4.5 edits per step on average. The last veto to clear is most often strategy ambiguity (2.7), in 6 of 10 tasks; it fails in 77% of the 496 sessions before acceptance and in 28 of the 42 sessions that failed exactly one veto.

## Limitations

**Stated by the authors.** The benchmark freezes ten tasks with three sessions per agent, and its grammar covers long-only U.S. equity strategies with a fixed-cost model. The simulator, the judge and one evaluated agent come from the same model family; program checks and expert annotation limit but do not remove this risk. Most agent turns hit the 300-second limit, so longer turns may let agents get further. Program checks cannot prove that every figure is real, and feedback scores can leak information about the hidden strategy across attempts, so leaderboard results should come from frozen agents.

**Assessed from the reporting.**

- **Single source, no artifact inspected.** Everything rests on one arXiv preprint (v1, 5 November 2026). The paper states that the benchmark of 10 frozen tasks, the task generator, the evaluator and a live leaderboard are released, but no repository URL for them appears in the inspected text, so nothing here was run or checked against a released artifact.
- **Zero is a floor, not a comparison.** No agent was accepted, so the headline number has no spread: there is no ranking among agents by acceptance and no evidence about what an accepted session would look like. The diagnostic layers (quality, per-step passes, veto shares) carry all the signal, and they are graded on the same 0–4 rubric.
- **The grader is part of the experiment.** The paper's own counterfactual is the strongest result: grading by user sign-off (23%) or by LLM-judged vetoes (11%) yields different acceptances and a different agent ordering than grading by all vetoes (0%). The choice of which vetoes to enforce is a design decision that determines the headline, and it is not itself validated beyond the two experts' 60-session annotation.
- **Two strict vetoes dominate.** Process completeness (3.8) and the verifier audit (3.7) fail in 120 and 119 of the 120 agent sessions, i.e. in essentially every session, and the paper notes they do not separate the agents. Without them 2 sessions would be accepted. This makes the acceptance result partly a statement about two completeness requirements rather than about the three silent failures the paper is about.
- **Small annotation sample.** The expert study covers 60 sessions (13 per agent plus 8 for the bare model) and a 30-session calibration set; the κ = 0.87 judge agreement and the 88% attribution to agents rest on that sample, and the two experts are paid team members rather than independent annotators.
- **Turn limits shape the result.** 70% of agent turns hit the 300-second limit and only 58 of 120 sessions reach a fourth turn, so the workflow-breakdown numbers describe agents that were cut off, which the paper itself flags as a possible cause of premature user exits.
- **The learning result is a leaderboard artifact of the design.** 506 sessions to learn ten tasks is a large budget, and the agent practices each task until first acceptance on the same task it is learning — so the reported transfer is within-task learning under a leak-free feedback signal, not generalization to new tasks.
- **Cost comparability is limited.** API-equivalent costs are reported for Codex and Kimi Code running on subscription plans, so the USD column mixes pricing models and understates the true cost of those two.
- **Domain narrowness.** Long-only U.S. equities with a fixed-cost model, one asset class, one data vendor (Financial Modeling Prep) and one cutoff per task; the transfer of these results to crypto, fixed income, non-U.S. markets or multi-asset work is untested.

## Competing approaches

Only approaches the paper itself compares against or cites as related.

**Financial benchmarks (Table 1).** FinBen and MultiFinBen (QA over curated documents and price series), FinDeepResearch (research queries with expert ground truth), AlphaForgeBench (strategy implementation with curated data), CLQT (closed-loop, cost-aware, strategy-consistent portfolio management), InvestorBench (agent trading decisions in historical or live markets), AMA (live multi-market trading arena), Herculean (agentic financial intelligence) and τ-banking (a banking domain with a knowledge base and discoverable tools). FINCOSMOS's claimed difference is that each of these opens at most one of intent, data and time, while FinCosmos opens all three, grades by program-verified invariants wherever possible, and samples new tasks from a grammar rather than a fixed pool. The paper also cites FinTrace (trajectory-level tool-call evaluation on predefined tasks), AlphaOpsBench (coarse hypotheses but no user to ask), FinanceBench, FinQA, FinSight, RealFin and ShiJianBench.

**Open-world and user-simulated evaluation.** τ-bench pairs a tool-using agent with an LLM-simulated user; its successors add τ²-bench (dual-control environment), τ-Voice (full-duplex voice) and τ-Knowledge (unstructured knowledge). The paper's reading of this family is that the user's intent is hidden but the world is closed — the agent works over a fixed database and is graded against a target state — citing UserBench and Ambig-SWE in that group. On the web side it cites WebArena, Mind2Web, GAIA, BrowseComp and the WebAgent survey, and notes that these state the task in full even when it is personalized. On deep research it cites DeepResearch Bench and PaperBench with LLM judges, noting their known biases and gameability, and cites LiveBench and GDPevo as benchmarks that refresh their tasks to avoid staleness. It also cites the evidence that LLM-simulated users are unreliable proxies (Seshadri et al., "Lost in Simulation") and that stronger assistants make weaker simulators (Naous et al.), which is why FinCosmos uses its simulator as an examiner under fixed disclosure rules and validates it with human experts.

**Look-ahead bias.** Bailey et al. on the probability of backtest overfitting; Drinkall et al.'s Time Machine GPT and He and Lu's chronologically consistent LLMs as model-side remedies; Glasserman and Lin on GPT sentiment look-ahead; Lopez-Lira et al. on memorization; Li et al. on "Time Travel is Cheating" and Zhang et al. on the AlphaForge one-switch benchmark as benchmark-side remedies; Ulesov et al.'s clean-control calibration, Li et al.'s "When Alpha Disappears", Wang et al.'s "Summoning the Oracle", and Zhang et al.'s "Evaluating LLMs in Finance Requires Explicit Bias Consideration". FinCosmos's differentiation is that it checks the data and backtest each agent builds and delivers, with programs rather than LLM auditors, and fails any run that violates point-in-time correctness. The paper also notes that models memorize financial values from before their training cutoff, that LLM trading agents can profit from leaked outcomes, and that effective cutoffs can lie months before the dates vendors report.

**Judge reliability.** The paper cites LLM-as-a-judge work with known biases (Zheng et al. on MT-Bench and Chatbot Arena; Mahmoud et al. on reward hacking in rubric-based RL; Chen et al. on null models achieving high win rates) as the reason for recomputing numbers by program rather than judging them, and for the expert comparison of judge and simulator.

Within this knowledge base, FINCOSMOS is the sharpest instance of [[concepts/verified-completion-vs-apparent-success]] in a domain where the cost of a silent failure is capital: the paper's central claim is that user sign-off and an LLM judge both count a wrong deliverable as a success. It also operationalises [[concepts/scoped-assurance]] — the assurance is scoped to the veto set and to the frozen task — and [[concepts/protocol-relative-scores]], since the acceptance rate is a property of the grader's veto set, not of the agent alone. Two further relationships are analyst-level rather than author-endorsed: a benchmark that grades a delivered artefact against a hidden specification has a natural companion in [[projects/weavebench]], and the practice of feeding rejected or unaccepted runs back into the evaluation set is tracked in [[experiments/hidden-acceptance-regression-ingestion]]. This page also contributes to [[evaluations/briefing-synthesis-2026-11-03-to-09]]. These links are evidence-guided conceptual comparisons, not assertions that the projects cite, implement or depend on each other.

## Implications

The following is analysis by the KB maintainers, not a claim of the authors.

The most transferable idea is that the grader should be constructed so that it *cannot* be satisfied by a good-looking artifact. FinCosmos does this by making the evaluator recompute the agent's numbers from the agent's own files and by making the specification a hidden object that only the agent can elicit. Both halves matter: the recomputation catches fabricated or miscomputed metrics, and the hidden specification catches the strategy the user never asked for. A team building an internal version of this should copy the *shape* — hidden intent, self-sourced data, programmatic recomputation, and a veto set that includes completeness — rather than the finance specifics, because the shape is domain-independent and the specs are not.

Second, the paper's counterfactual is the sharpest methodological warning in the set: the same 150 sessions produce 23% "success" under sign-off, 11% under an LLM judge and 0% under program checks, and the choice of grader also reorders the agents. Any benchmark that reports one headline number without stating which grader produced it is reporting a protocol-relative score — the concrete case of [[concepts/protocol-relative-scores]] — and a leaderboard whose veto set is not published is not auditable. The paper's design of storing the evaluator version and a hash of the scoring code with every score is the minimum discipline for this.

Third, the elicitation numbers give a concrete design target for interactive agents. Agents raised 54–64% of the unstated details, and the delivered strategy failed to match 66–83% of the details never stated — that is, most of the strategy the agent guessed, it guessed wrong, while the pre-veto quality score still looked respectable (20–37 out of 100). The correlation between clarification coverage and quality (ρ = 0.25) is weak but points the same way: a workflow that does not ask cannot be right about what was not said. This is the [[concepts/abstention-as-first-class-verdict]] problem in an unusual place, because the agent has no way to know it has guessed wrong — unless the evaluator is built to punish the guess.

Fourth, the failure distribution is more useful than the zero. Agents pass the middle of the workflow about half the time in isolation and fail at both ends, and the one step nobody passes is reproducibility: zero of 120 sessions delivered trades that reproduce the reported returns, even though 63 passed the no-look-ahead step. That suggests that for this class of agent, "generate plausible numbers" is a solved-enough problem that "make the numbers checkable" is the binding constraint, and that a delivered artifact without a machine-checkable audit trail is not a deliverable.

Fifth, the learning result should be read narrowly. It shows that a leak-free, per-dimension diagnostic signal is sufficient to drive a memory-based agent to acceptance on tasks it could not pass — 506 sessions over ten tasks, with the user already satisfied 34% of the time. It does not show transfer to unseen tasks, and the paper is explicit that feedback can leak information about the hidden strategy across attempts and that leaderboard results should come from frozen agents. The practical lesson is that graders should publish what they withhold and why, so that a learner can be told "the strategy was not what I asked for" without being told the strategy.

## Reproducible experiment

No artifact was run by the KB maintainers, and no source in this page was executed. The released benchmark, generator, evaluator and leaderboard are stated by the paper but no repository URL was found in the inspected text, so any check means reimplementation from the method and appendices, or running against the released leaderboard if a URL becomes available. A feasible independent test of the paper's central claim:

1. **Grader-swap on a small task set.** Construct 30 tasks of your own with a hidden specification, a data cutoff date, and fabricated or conflicting source material. Grade the same agent sessions three ways: user sign-off, an LLM judge over semantics only, and programmatic recomputation plus completeness vetoes. Pass criterion: the paper's pattern — sign-off accepts a substantial minority, the LLM judge accepts fewer, and program checks accept none or very few. If sign-off and program checks agree, the hidden-specification construction has failed to create a gap and the benchmark is not testing what it claims.
2. **Reproducibility as the decisive metric.** Require every session to deliver a trade log and prices, rebuild the returns, and count sessions whose reported metrics match the rebuild within the paper's tolerances (0.02 for returns and drawdowns, 0.5 for the Sharpe ratio). The paper's finding is that this single check fails in every one of 120 agent sessions. A comparable count in your setup is a strong replication of the paper's most consequential negative result; a materially higher count would indicate that the paper's tasks are easier to satisfy.
3. **Elicitation measurement.** Instrument the conversation so that the set of specification items H, the opening items O and the items stated by the end S are all machine-extractable, then report clarification coverage |S \ O| / |H \ O| and the assumption rate over H \ S. The paper's reference values are 54–64% coverage and a 66–83% mismatch rate on unstated items. Pass criterion: your coverage should land in that band; a much higher figure would mean your simulator discloses more than the paper's disclosure policy allows, which would change what the metric measures.
4. **Leak-free feedback ablation.** Run the same agent twice over the same tasks, once with reasons attached to the strategy and data scores and once with the paper's leak-free rule (scores without reasons, except point-in-time strictness). Measure how many sessions reach acceptance and how many sessions are needed. This tests the paper's claim that learning is possible under the leak-free rule and, equally, how much of the learning depends on withheld reasons.
5. **Crossover sanity check.** Include a no-tools baseline. The paper's finding is distinctive: the bare model scores 0 on data and 4.6 on backtest but 49.8 on strategy and 44.6 on user experience, and is statistically indistinguishable from two of the tool-using agents on pre-veto quality. If your no-tools baseline does not look fluent-but-empty, your grader is probably reading the report rather than the files, which is exactly the failure the vetoes exist to catch.

Substituting available models for the paper's 2026 hosted backbones is unavoidable; the substitutions, the grader configuration and any task differences should be reported alongside the results.
