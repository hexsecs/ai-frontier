# Agent skills and memory

## What it is

Agent skills and memory are the two forms of persistent, human-readable state that a frozen model reads at run time and that some process — the model itself, a compiler, a curator, an evolution loop — writes between runs. A *skill* is a stored procedure: instructions, a workflow, or compiled code that tells the agent how to perform an operation it will meet again. A *memory* is stored content: knowledge modules, experience records, compiled context, or an instruction file the agent loads at session start. In every system on this page the model's weights never change; whatever improves, improves in the store. That is the corpus-level claim recorded as the concept [[concepts/improvement-lives-in-external-state]]: the locus of improvement is external state, and freezing the artifact is what makes the improvement inspectable, reversible, and portable.

The technique family's real subject, though, is not storage but *admission*. The deepened pages divide sharply by what stands between a candidate artifact and the trusted store. At one end, SkillCompiler admits a synthesized program only after isolated validation against a declared contract; ClinGeX admits a clinical skill only after it passes a frozen, skill-specific test suite; KARMA retains a knowledge patch only if it improves a fixed validation set, restoring a snapshot otherwise. At the other end, a coding agent's project memory file is admitted by the filesystem: it sits in the repository root and is auto-loaded, unchecked — and the one controlled study of that channel finds its measured effect indistinguishable from chance. Between the ends sit weaker gates: FilingLoop validates the *form* of a skill update but never its performance, and Context as Infrastructure validates compiled artifacts for provenance but reports no measured capability effect for them at all.

So the synthesis this page defends is conditional: skills and memory are a real improvement mechanism when admission to the store is gated — by validation, by tests, or by measured gain — and the corpus's null results cluster exactly where the gate is absent or where the store's effect is never measured. The sibling concept [[concepts/capability-locus]] records the standing caution: which component carries a system's quality is an attribution question each system must answer by ablation, and several pages here answer it only partially.

## Mechanism variants

**Compiled program skills — [[projects/skillcompiler]].** SkillCompiler decomposes a skill into fine-grained operations, judges each against explicit executability criteria (representable inputs and outputs, a specifiable procedure, observable preconditions, independently verifiable effects), and compiles the qualifying operations into deterministic programs. A synthesized program is validated in an isolated environment — it must execute, conform to its contract's input/output schema, and satisfy its postconditions under a declared check — before it enters the persistent Program Asset Bank. Only validated programs enter the skill skeleton; operations that fail a criterion remain LLM reasoning steps. Any change to an implementation, behavioral contract, or supported conditions requires revalidation of the affected realization before admission. Learning is local and trace-driven: an operation that met its check is retained even when the task failed, and only the failing operation's conditions, bindings, or guidance are revised.

**Tested skill libraries — [[projects/clingex]].** ClinGeX's library of 105 clinical-genomics skills was built by curation plus a builder–evaluator loop: candidates were harvested at web scale, prioritised by rubric scoring, and finally included by consensus of eight clinical experts; each prototype was then compiled into a `SKILL.md` package and exercised by an evaluator that generated 5–20 skill-specific test cases spanning valid, boundary, alternative-representation, batch, non-applicable, absent-record, malformed-input, and simulated-failure inputs. Failures returned to the builder for revision, up to five cycles. Only skills passing all frozen tests entered the deployed library — the library is closer to a tested codebase than to a prompt collection, a distinction the Evidence section shows is measurable.

**Evolving knowledge modules — [[projects/karma]].** KARMA keeps its store as six typed knowledge modules (three text modules, two ordered rule lists, one schema module) rendered into the frozen agent's prompt. Edits are atomic tuples, schema-checked by a registry that is the only write boundary, and journaled with before/after values. A deterministic verifier partitions each batch's trajectories into successes, semantic failures, and infrastructure errors; failures are routed to candidate modules by fixed hand-written mappings; an LLM Critic proposes changes and an LLM Evolver emits at most three edits per cycle. Retention is the gate: the candidate patch is kept if and only if its gain on a fixed validation set meets a threshold (θ = 0.01), and the pre-edit snapshot is restored on rejection or error. The hold-out set is never exposed to the loop and is evaluated exactly once, at the end.

**Procedure documents under structural validation — [[projects/filingloop]].** FilingLoop's Reviewer and Filer roles carry Markdown skill documents that an editor model rewrites from requirement-level grading feedback after each batch. The update rule is validate-or-keep: validation checks structure, YAML validity, and role identity, and rejects known company identifiers, private source paths, and long exact copies of reference text; if no valid update emerges in three attempts, the incumbent skill is kept. Crucially, validation never selects updates by held-out performance — the gate certifies form and provenance, not benefit. FilingLoop is kept on this page as the weakest-gate instance: it demonstrates that a store can be disciplined, leak-filtered, and still performance-blind.

**Compiled context stores — [[projects/context-as-infrastructure]].** Context as Infrastructure compiles a corpus once, upstream of any query, into typed artifacts — claim–evidence pairs, navigation trees, graphs, timelines, synthesized articles, durable memory — each registered with source version, offsets, and validation status. Its admission discipline is provenance: an exact-presence span check discards any claim whose evidence span cannot be located in the source ("the model may propose, but the source disposes"), and invalid units are dropped rather than repaired. Derived artifacts are read-only and never written back into the source. This is memory as governed infrastructure — and, as the Evidence section records, the paper's own deployment ledger reports no measured effect for the memory artifact family.

**Gated admission — the shared mechanism.** Mining pass 1 resolved the admission pattern as a technique seed, *gated admission*: a candidate artifact becomes consequential only after passing a gate, and the corpus exhibits two forms. The **structural** form checks the artifact itself, deterministically, before it acts: SkillCompiler's contract validation and ClinGeX's frozen test suites are the skill-store instances, and the register records the same shape elsewhere — typed objects consumed by deterministic code in AgenticDS, validated model-emitted JSON in A2UI (whose validator returns a standardised `VALIDATION_FAILED` error), interface-compliance checks before any training run in GARDEN, and FilingLoop's validate-or-keep. The measurement-side instance is [[projects/seq-k]]: under Seq@K an attempt is credited only when it passes the task verifier, and the verifier's feedback is the discrimination test a failed attempt must answer before re-presentation — rubric-aware feedback repaired 73.8% of failed criteria, against 34.4% for a binary pass/fail verdict and 36.5% for ungated retries with no feedback at all, which is what a gate that merely says "no" is worth. The **behavioral** form judges by measured runtime outcomes: KARMA's retain-iff-gain with snapshot rollback is the pure instance, and EvoTeam applies the same logic socially — a provisional team is admitted to the team library only if its roster supports the required division of work and its collaboration structure looks reusable, while its Rule Reflector removes rules that no longer fit. Two claim-form residues from the register belong with the mechanism. First: each system's effective trust boundary is exactly its gate's schema — with the register's own bound, that a gate certifies form, not intent (a manipulated agent can build a deceptive interface entirely from trusted, validated components). Second: the gate, not the contents, is what separates a library from a prompt collection — ClinGeX's third-party skill libraries scored in the same 74.0–78.4% band as its other single-strategy conditions, below the gated in-domain library's 83.2%. Neither canonical system isolates its gate experimentally — ClinGeX's ablation bundles gating with domain curation, and SkillCompiler has no ungated-admission condition — so the gate's separate contribution is asserted by the pattern across systems, not measured within one.

**The ungated baseline — [[projects/security-impact-of-coding-agent-memory-files]].** Project memory files (CLAUDE.md, AGENTS.md) are the control condition the corpus happens to contain: persistent text, auto-loaded at session start, with no validation, no tests, no retention decision — the file's own framing, in the vendor documentation the study cites, is *context*, not enforced configuration. Whatever such a store does, it does ungated. The study planted adversarially written files and measured the result; the Evidence section gives the numbers, and they are the reason this page's thesis is conditional rather than celebratory.

## Evidence and measured effects

All results in this section are **author-reported** from the projects' own papers; none has been independently replicated, and each page linked above separates its claims accordingly.

- **Compilation carries the effect (SkillCompiler).** On ALFWorld, removing the Programmer — no program synthesis, qualification, or invocation — collapses success from 98.26% to 53.48% at 7.36× the token cost, while removing the skeleton or the optimisation loop costs only ~2.7 points each. Execution instability falls with compilation: EIR@3 drops from 32.00% (SkillOpt) to 11.00% on LiveMath. SkillCompiler tops all six model families tested, by 6.02–11.90 points over each family's strongest baseline.
- **A tested library beats untested ones (ClinGeX).** With the base model held fixed, the full skill architecture scored 83.2% on 426 evidence-grounded QA items, versus 72.2% for the plain model and 74.0–78.4% for five single-strategy conditions including two third-party skill libraries. On the temporally held-out clinical benchmark, ClinGeX reached 71.7% macro-averaged concordance against 45.7% for the strongest comparator. (The architecture ablation is LLM-judged on model-generated items — a weaker evidence form than the rule-scored benchmark, as the project page notes.)
- **A regression gate retains real gains, imperfectly (KARMA).** Across 18 domain–model settings, gated evolution raised the untouched hold-out score from 30.19 to 39.15 on average (+8.96 points), improving 16 of 18 settings; removing either evidence channel (successes or failures) more than halved the gain. A worked rejected cycle shows the rollback firing: validation fell 41.25 → 34.38 and the snapshot was restored.
- **A form-only gate yields modest, localised gains (FilingLoop).** Evolving beat Fixed on requirement fulfilment, 24.28% → 27.96% (+3.68 points), with the gain concentrated in revision (conditional Filer accuracy +10.36 points) rather than discovery (+1.41 points). Harmful-revision prevalence moved 5.8% → 4.5%, a difference the project page flags as weak evidence.
- **Governed context buys cost, not accuracy (Context as Infrastructure).** No compiled variant produced an accuracy improvement distinguishable from run-to-run variation; the uncompiled BM25/grep harness already answers 85% of BrowseComp-Plus and 91% of FRAMES. The one measured win is economic: claim–evidence substitution cuts total query tokens by 91% on a hit and adds 1.9% on a miss, a 38% average reduction. The deployment ledger for the other artifact families — memory included — reports *no measured effect* on every row.
- **Ungated memory does not measurably steer (memory files).** Planted memory files moved the share of secure completions by −8 to +6 percentage points across three agent configurations, with no consistent direction — four of the six shifts were *increases* — and every shift inside the band the authors say cannot be told from chance; in the paired analysis, the baseline was the secure completion in 15 discordant pairs and the with-file completion in the other 15.

## Failure modes and bounds

- **Gates screen; they do not guarantee.** KARMA's gate selects on a fixed 160-case validation set, and two of its 18 settings still regressed on hold-out (Kimi-K3: −3.13 and −1.88 points), each after a single early patch; the paper concedes the gate "does not guarantee hold-out improvement." No aggregate accept/reject statistics across KARMA's 108 gated cycles are reported, so the gate's operating characteristics are known from case studies, not rates.
- **Validated is not reliable at run time.** SkillCompiler's Program Invocation Success is 88.84% — roughly one in nine invocations of a *validated* program still fails — and its validation is, by the authors' own statement, "evidence of local behavior, not exhaustive branch coverage or semantic equivalence." Its persistence claim is also the least-tested part of the design: cross-skill reuse (54.85%) rests on per-seed denominators of 10–14 programs, and no compile-fresh-versus-bank-reuse ablation exists.
- **The gate is never isolated.** As recorded under gated admission, no system ablates its gate alone. ClinGeX bundles gating with expert curation and domain fit; SkillCompiler's decisive ablation removes synthesis, qualification, and invocation together. The cross-system pattern is consistent, but a reader should know the mechanism's effect size within any single system is unmeasured.
- **Ungated stores steer silently when they steer at all.** The memory-files study's sharp result is disclosure, not code: of 18 sessions whose reasoning explicitly identified the planted file as an attack, only 4 named it in the final message, and recognition did not protect the code — across those sessions security was lost against baseline in 3 and gained in 2. A store with no gate also has no audit point at which influence is recorded.
- **The nulls have their own gaps.** The memory-files study has no benign-file control, so it cannot separate "an instruction file's mere presence changes behaviour" from "malicious guidance changes behaviour" — the attribution question its near-null makes central. Context as Infrastructure never measures its compilation build cost, so its amortisation argument cannot be checked against its own deployment.
- **Experience can travel badly.** EvoTeam exists because naive cross-task reuse hurt: continuing a strong baseline across heterogeneous tasks underperformed target-only training on all three metrics examined. KARMA's transfer matrix shows the same asymmetry — one domain's evolved knowledge (Automotive) lowered every other domain's score. A gated store controls what enters; it does not control where the contents generalise.
- **The frozen reader bounds the artifact.** EvoTeam states that effective use of stored experience "depends on the base model's ability to correctly interpret and apply the stored guidance," and [[concepts/capability-locus]] records the unresolved HERA–AgenticDS contradiction on exactly this point: in one system the corpus carried quality, in another the model did. Stores and readers are complements, and this corpus never varies the reader while holding the artifact fixed.

## Open questions

- What does the gate alone contribute? A within-system ablation — same store, same contents pipeline, gate present versus absent — is missing from every page here, and is the single experiment that would convert this page's cross-system pattern into a measured effect.
- Does persistence itself pay? SkillCompiler asserts a reusable program bank but never ablates it; whether stored artifacts beat recompiling or regenerating per task, net of validation cost, is open for skills and unmeasured (build cost included) for compiled context.
- Can a gate certify more than form? The register's bound — gates certify form, not intent — is untested as a design problem: no page here attempts semantic or intent-level admission checks on stored artifacts, and the memory-files channel shows why the question matters.
- Where is the reader threshold? No page varies the frozen model's capability against a fixed artifact, so the minimum reader strength at which a given store stops helping is unknown — the experiment [[concepts/capability-locus]] identifies as the field's missing factorial.
- Do gated stores compound across transfer hops? Every exhibit is a single develop-then-freeze cycle; whether an artifact improved in a second task family keeps its gains, or accumulates the negative-transfer failures KARMA and EvoTeam document, is unmeasured.

## 2026-11-12 cross-briefing synthesis: query-time evidence versus procedural guards

[[projects/just-in-time-agent-memory]] preserves raw history for iterative, query-conditioned reconstruction (https://arxiv.org/abs/2609.34385); [[projects/lifelong-materials-agent-memory]] instead reports reusable failure-derived execution guards in materials-science tools (https://arxiv.org/abs/2608.11224). These are complementary **author-reported** mechanisms, not a demonstrated integrated improvement. JAM's retrieval does not itself gate what becomes executable; materials memory does not prove its guards transfer safely to unrelated tasks. Existing KARMA negative-transfer results and the memory-file near-null remain counterevidence to any universal claim that persistent memory improves outcomes. No independent replication or head-to-head test is recorded.

**Reproducible proposed test:** On 25 fixed repository tasks with repeatable failures, compare raw-history query-time retrieval, reusable preflight guards, both, and neither; hold model/tool budget constant; measure independently verified success, guard false positives, retrieval provenance, negative transfer, tokens and retries. This extends the earlier gate-isolation question rather than replacing it.

## November 13 update: trainable file-operation memory

[[projects/coding-agent-memory-post-training-ii]] (https://arxiv.org/abs/2611.14009) reports on-policy distillation that teaches a policy when to write, search and reuse ordinary workspace files across context resets. This differs from gated persistent skill admission, JAM's query-time retrieval and reusable failure guards. The reported 2.97× relative gain on CAMG-II is author-reported, not evidence that ungated memory is safe or that results transfer to production. Earlier null and negative-transfer findings remain counterevidence. Proposed controlled test: fixed interrupted coding tasks comparing prompted files, learned file operations and no persistent memory with identical budgets and independent acceptance checks.
