# Multi-agent orchestration

## What it is

Multi-agent orchestration, as the stub framed it, is the set of mechanisms by which several agents work as one system: "typed handoffs, evolving teams, and task-aware model routing." Those three phrases came from three different projects' summaries, and the stub's seven candidate links were inferred relatedness from a summary-level pass — vocabulary co-occurrence, explicitly not evidence.

Tested against the deepened project pages, the finding is the one recorded in [[evaluations/relation-discovery-2026-11-02]]: **the theme dissolved**. In that evaluation's words, "seven associations produced no evidenced cross-project orchestration relation. Shared vocabulary — teams, roles, coordination — was not shared mechanism." No two projects in the corpus exhibit the same orchestration mechanism with two-sided evidence behind it; the one orchestration-specific concept candidate, EvoTeam's team-as-persistent-asset, remains a single-source hold.

What survives is narrower and, this page argues, more useful than the theme was. Four projects each contain a real, describable coordination mechanism — but a *different* one in each case: an evolving library of teams with team-scoped handoff rules ([[projects/evoteam]]), a fixed role pipeline exchanging typed objects ([[projects/agenticds]]), independent parallel exploration reconciled by hierarchical aggregation ([[projects/explorerepair]]), and human–bot teaming run through an audit-first policy gateway ([[projects/openbot]]). Three further candidates were demoted on inspection: [[projects/dittany]], for which multi-agent applications are the *object* being repaired rather than a technique it practises; [[projects/github-copilot-fusion]], a genuine production model router whose entire performance record is vendor claims; and [[projects/garden]], whose "agents" are reinforcement-learning policies, not orchestrated LLM agents. Orchestration in this corpus is a property of individual systems. The transferable content is a handful of per-system mechanisms, two well-measured negative results, and one recurring dependency — on verification — that belongs to another page's theme.

## Mechanism variants

**Evolving team library with team-scoped handoff rules — EvoTeam.** EvoTeam maintains a library of reusable teams, each pairing a natural-language description of the collaboration requirements it supports with a candidate roster drawn from a global agent pool. Per task, a Team Selector matches the task's collaboration requirements (division of work, complementary roles, verification needs — not topic similarity) against team descriptions; a Composer builds a provisional team if none matches; a Chairman recruits the execution team from the roster, decomposes the query into subtasks, and can reassign subtasks mid-run. The design's core is a scoping asymmetry: interaction rules — what task information and evidence a handoff message must convey, including uncertainty and fallback guidance — are *team-scoped* and evolve only inside their team, while individual agent skills are global and shared across teams. After execution, three reflectors evolve rosters and team descriptions, the team's rules, and agents' skills; a provisional team is admitted to the library only if its roster supports the required division of work. This is the corpus's richest orchestration mechanism, and the only one where "handoff" is a governed, evolving object rather than a message format.

**Typed contract pipeline — AgenticDS.** AgenticDS orchestrates three fixed LLM roles — Planner, Engineer, Critic — in a bounded loop of at most three rounds. Its discipline is that "every language model decision instantiates a typed object before deterministic code consumes it": the Planner emits a typed plan (query branches, declared graph paths, hard constraints versus soft preferences, acceptance thresholds), the Engineer compiles it into a protocol of predefined operators and is the only role that touches the retrieval index, and the Critic scores a fixed-format evidence package and returns typed diagnoses that bound what the next round may repair. The stub's "typed handoffs" phrase fits this system most literally. But note what the typing is *for*: the paper's stated enemy is the free-form tool-calling agent in which "the same model that selects a dataset also declares it a match." The contracts exist to make verification possible — as the ablations below confirm.

**Independent exploration plus hierarchical aggregation — ExploreRepair.** ExploreRepair's three agents never communicate during exploration at all. A structural agent (code knowledge graph), a semantic agent (reconstructed developer intent), and an executable agent (a self-built proof-of-vulnerability test) each run the same ReAct scaffold independently on the same vulnerable revision and return a trajectory and a candidate patch. Orchestration happens afterwards: each trajectory is distilled into a short role-specific lesson; a Lesson Aggregator and a Patch Aggregator synthesize separately, in parallel, from the lessons and the diffs respectively; and a final Aggregator reconciles the two syntheses against the repository. Coordination here is portfolio management — diversity purchased through independence, then merged — rather than interaction.

**Governed endpoints and human takeover — OpenBot.** OpenBot treats a Bot as any endpoint speaking the AG-UI protocol and puts a single policy gateway on the server between Bots and everything they can act on: every action returns to the server first, the gateway evaluates a CEL policy over fields describing the attempted action — including `initiator.kind` (person, deployment, routine, responsibility, memory, *handoff*) — writes the audit row, and only then lets the action execute. There is no path that acts without the record existing first. The orchestration-specific element is the designed fallback: when a Bot hits a login wall, a 2FA prompt, or a bot check, it files a help request and a person takes control in the same panel; while a person is driving, Bot actions are refused rather than queued. This is orchestration as governance infrastructure — it coordinates *who may act and under what record*, across people, routines, and Bots — rather than coordination logic among agents.

**Demoted candidates.** Dittany contributes no orchestration mechanism: it is a runtime repair layer interposed on *other people's* multi-agent applications (30 open-source apps across six frameworks), deriving expected contributions from task contracts and repairing failed executions. It appears in the evidence and failure sections below because it is the corpus's only large-scale field data on how orchestrated systems behave — but the link is orchestration-as-object, not technique membership. GitHub Copilot Fusion is a real, generally available per-prompt model router with three execution patterns (single, cascade, critique), and it is the only candidate that is literally "task-aware model routing" in production; it is demoted because every performance figure for it is a vendor claim with no published methodology, operating statistics, or failure data — its mechanism is documented, its effects are not evidenced, and the claims are labelled as vendor claims where they appear below. GARDEN is demoted on a category distinction: its cooperating agents are MAPPO policies trained by reinforcement learning, and its LLM is a single reward engineer; nothing about handoffs, routing, or team composition in the LLM-agent sense is present to transfer.

## Evidence and measured effects

Every quantitative result in this section is **author-reported** from the projects' own papers, with no independent replication, except Fusion's figures, which are **vendor claims** and labelled as such. The pattern across the kept projects is that the measurements credit something other than coordination itself.

**ExploreRepair carries the strongest architecture-isolating evidence — and it indicts generic orchestration.** On PatchEval (N = 169), the full system reaches repair success rates of 39.6% (GPT-5.6-Luna) and 71.6% (DeepSeek-V4.1-Flash), against 32.5% / 57.4% for a single ReAct agent and 30.8% / 53.3% for a 3-in-1 agent running all three mechanisms inside one trajectory. The generic multi-agent baseline — subagent delegation without evidence specialization — scores 30.2% / 55.6%, *below the single agent on both models*. What the ablations reward is not multi-agent structure as such but independence plus specialization plus separate synthesis: the explorers' union covers more instances than any single explorer, and aggregation creates repairs none of the three explorers found individually (11 vulnerabilities with DeepSeek, 3 with Luna). They also bound the recipe: the final reconciliation step adds only +0.6 / +2.4 points over the stronger intermediate aggregator, so most of the value sits in the separate syntheses, not the merge of merges. (The paper's headline margins over prior repair systems rest on baselines the authors adapted and weakened; the within-system comparisons quoted here are the load-bearing ones.)

**EvoTeam's evidence supports its scoping claim in exactly one setting.** When one system evolves over a mixed stream of 116 instances from all its benchmarks and is frozen for holdout evaluation, EvoTeam beats its strongest relative, Meta-Team, on all six metrics, 59.58 to 55.55 on average — the setting where cross-task reuse of coordination knowledge either helps or hurts. Under per-benchmark evolution the same comparison is a near-tie (+0.55 points on average), and EvoTeam loses LOCA-Bench outright (63.75 vs 69.58). Ablations credit the team-scoped rules (+10.00 points on GAIA, +8.75 on LOCA-Bench over templates alone), and the motivating preliminary study shows naively carrying evolved collaboration experience across tasks *hurting* on all three metrics examined — but those numbers appear only in a figure, the evolution splits are 16–20 instances per benchmark, and no significance reporting accompanies sub-point margins. The evidenced claim is "coordination knowledge transfers badly when global, and quarantining it by team fixes that in a mixed stream" — a claim about where experience lives ([[concepts/improvement-lives-in-external-state]]), not about a coordination technique other systems share.

**AgenticDS's ablations credit the verifier, not the coordination.** Removing the Critic costs −0.149 NDCG@10, the largest single-component effect; removing the Planner costs −0.086, and typed graph expansion −0.084. Graph expansion actively *hurts* (−0.025 to −0.029) when its candidates bypass the Critic. The pipeline's three-role structure is real orchestration, but the measured load-bearing element is the dedicated checker reading a structured evidence package — the same shape as the verification findings elsewhere in this knowledge base (see [[techniques/verification-and-evidence]]).

**OpenBot contributes a mechanism and no measurements.** Its documentation contains no benchmarks, task-success figures, or evaluation of the gateway's effectiveness; the absence is itself the finding. Fusion's record is thinner still in kind: a vendor claim of 60 on a third-party coding-agent index, "within two points" of a named comparator at about half the API cost and tokens (all **vendor claims**, methodology unpublished). Dittany, finally, supplies the only population-level numbers about orchestrated systems in the corpus, from the outside: across 9,000 tasks on 30 real MAS applications, native execution achieves 58.01% task accuracy, and two of the four recovery baselines score *below doing nothing at all* (SupervisorAgent 48.39%, AgentTether 50.41%). Whatever orchestration these applications were doing, it left roughly two tasks in five failing, and detection of the failures was itself partial (79.18% recall).

## Failure modes and bounds

- **Generic delegation is an anti-pattern in the corpus's one direct test.** ExploreRepair's delegation baseline underperforms a lone agent on both models tested, while the specialized, independent variant tops the table. "More agents" is not an orchestration technique; what each agent is responsible for *knowing* is.
- **Aggregation amplifies correlated error.** In ExploreRepair's documented Synapse case (CVE-2021-39163), one explorer produced a passing repair, both intermediate aggregators adopted the same wrong authorization assumption, and the final aggregator followed them — discarding the correct fix. Independence at exploration does not survive aggregation layers that share assumptions.
- **Coordination knowledge negatively transfers.** EvoTeam's preliminary study and Skill-MAS's collapse in the mixed-benchmark setting (41.30 average, below the single-agent score on GAIA) show evolved handoff rules and team templates misfiring across task boundaries; scoping is the mitigation, and it is one system's mitigation.
- **Local repair of coordination failures is net-negative.** Dittany's ablation finds action-level repair alone scores 52.54% — below native execution's 58.01% — while graph-level repair (scope decided from the dependency structure) is worth +32.21 points when added. Failures in orchestrated systems are structural; patching the latest action treats them as local.
- **Every pipeline is bounded by its checker.** AgenticDS's expansion-without-verification result and EvoTeam's design (one model executes, selects, chairs, and reflects, with no independent assessment of evolved rule quality) mark the same bound from opposite sides: orchestration multiplies whatever the verification layer can and cannot see.
- **Governance has a default-shaped hole.** OpenBot's engine fails closed, but the shipped startup policy is `allow: ["true"]` — allow-all — until an operator replaces it, and a Bot endpoint's internal loop is outside the gateway by construction. Fusion carries a vendor-disclosed operational hazard of the same flavour: a cascade draft the judge rejects can leave its file edits in the user's workspace, unreverted.
- **Evidence bounds.** All results are author-reported; baseline provenance is mixed (ExploreRepair's adapted baselines, Dittany's mostly-literature rows for two of four baselines); several decisive margins rest on a handful of instances or lack variance reporting. No claim in this section should be read as replicated.

## Open questions

- **Does any orchestration mechanism transfer across systems?** No project in the corpus runs another's mechanism, so the question the original theme assumed answered has never been tested. The nearest testable form: does EvoTeam's team-scoping help a system that did not evolve its teams?
- **Is a team a persistent asset?** EvoTeam's framing — teams with identity, admission decisions, and local policy surviving roster revision — rests on one system's evidence and remains a single-source hold in the register.
- **What are the operating statistics of production routing?** Fusion publishes no pattern frequencies, escalation rates, or judge error rates; until a production orchestrator's internals are measurable, the industrial half of this topic is mechanism description only.
- **Can aggregation be made robust to correlated error?** ExploreRepair's failure case and Dittany's correlated-blind-spot configuration (one backbone runs host, checker, repair, and assessor) suggest diversity must be maintained through the merge layers, not just at exploration — no page in the corpus demonstrates a fix.
- Mining pass 2 over the later clusters may re-adjudicate the holds named here; until it runs, the dissolution verdict stands as recorded.

## Evidence status

This page is a synthesis over seven deepened project pages and the knowledge base's own evaluation page; it introduces no new sources and no external citations. The dissolution verdict is the evaluation page's, drawn from mining pass 1's register (26 concepts, 38 two-sided relations, 19 holds), and the per-project verdicts above are this page's application of that register's discipline to the stub's candidate list: a link is kept only where the deepened page exhibits a coordination mechanism of its own, and demoted where the relation is topical (Fusion), categorical (GARDEN), or object-level (Dittany). All quantitative claims are labelled at the point of use: **author-reported** for the six research projects, **vendor claim** for every GitHub Copilot Fusion figure, and **absent** for OpenBot, which publishes no measurements. No result on this page has independent replication, and nothing was executed or reproduced in its preparation.
